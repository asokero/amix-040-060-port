# The 68060 FPU on this kernel: measured, 2026-08-07

**Kernel:** `68060-260807-02` (the RTG relink of the accepted `-06` base — the FPSP comes from the
base link, so this measurement holds for `68060-260806-06` too).
**Machine:** real A3000, 68060 @ 66 MHz, `fpu_present = 1`.

## Summary

The 68060 has **no FP support package**. The 68040 FPSP is linked in and every entry is gated
`cmpl #40,cputype` (`prototypes/fpsp_glue040.s`), so on an 060 it falls through to `nullvect`.
Any FP instruction the 060 does not retire in hardware therefore dies with **SIGSYS** — which the
shell prints as **"bad system call"**.

This was previously a hypothesis with one indirect datapoint (`acomp` dying with status 0140,
`060-F0-MEASUREMENT-260805.md`), and the vector was never proven because the kernel prints a
vector only for SIGKILL kills. `test-tools/fp060probe.c` closes it in user space, one instruction
per child, no kernel code:

```text
fadd       survived        control: retired in hardware
fsqrt      survived        control
fintrz     survived        <- expected to trap; it does NOT.  The 060 retires it.
fsin       SIGSYS (12)
fetox      SIGSYS (12)
flogn      SIGSYS (12)
fmovecr    SIGSYS (12)
```

Both binaries were scanned with `scan060.py` first (216 / 268 decoded lines, clean), so no death
here is attributable to the vector-61 integer path.

## The load-bearing detail: `fmovecr` is how compilers load ordinary constants

`fmovecr` reads the FPU's on-chip ROM constants — `0.0`, `1.0`, π, e, ln(2), powers of ten. gcc
emits it for plain FP literals. So a program does **not** need transcendental maths to die on this
kernel; `x = 1.0;` is enough.

Measured in the same session, and it explains a result that looked contradictory at first:

```text
fputest060        Test A  PASS
fputest060 fork   Test C  rc=140 = 128+12 = SIGSYS, no output at all
```

Both are in one binary. The disassembly settles it:

```text
800004e4 <nsqrt>:
  800004f2:  fbnle 800004fe        branch taken when NOT (x <= 0)
  800004f6:  fmovecrx #15,%fp0     0.0 -- ONLY on the x <= 0 early return
  800004fe:  ...                   normal path: fmove/fdiv/fadd/fmul, all implemented

8000053c <forktest>:
  8000057a:  fmovecrx #50,%fp0     1.0 -- on the main path, executed immediately
  800005ec:  fmovecrx #50,%fp0
```

Test A passes because its executed path never reaches an unimplemented opcode. Test C dies before
its first `printf` because `acc = 1.0` compiles to `fmovecr #0x32`.

**Test C had never been run on the 060 before** — the battery runs plain `fputest`, which is
Test A. So the FP-context-switch-under-load path is still unmeasured on this CPU: Test C does not
currently get far enough to measure it.

## What this predicts for user programs

Any program that touches floating point at all — including via libc — can die with SIGSYS on the
060 while working fine on the 040, because on the 040 the FPSP is active and emulates exactly
these instructions. Reported symptoms consistent with this, not yet individually attributed:

* `wolf3d`: "bad system call — core dumped". Ran correctly on the 040 (ISSUE-37 acceptance,
  2026-07-28), so a program-side cause is unlikely.
* `xv` / X11R5 under the RTG kernel.

**Caveat, kept explicit:** SIGSYS also has a legitimate producer — a genuinely unimplemented
system call. This measurement proves that unimplemented FP → SIGSYS on this kernel; it does not by
itself prove that any particular program's SIGSYS came from FP. Attributing `wolf3d` needs one
more step (a `truss`-style trace, or the `nullvect` vector probe KNOWN-ISSUES already specifies).

## Consequence for the campaign

This is campaign **F3** (`060-CAMPAIGN-PLAN-260805.md`: "vector 11 / 060 FPSP; closes ISSUE-34b if
the hypothesis holds"), status *not started*. The hypothesis now holds on the instruction level.

F2 delivered the 060SP's **integer** half (vector 61, `MUL[SU].L` 64-bit forms). The FP half is
what remains, and the scope is now concrete rather than presumed: at minimum `fmovecr` and the
transcendentals, entered from vector 11, with the `cputype` gate flipped to admit the 060 through
an 060-specific glue rather than the 040 one.

One earlier claim stays retired: the original ISSUE-34b observation that `cc1` dies of SIGSYS does
**not** reproduce — `cc1` dies of vector 61 (F0). The FP half rests on `acomp`, on this probe, and
on Test C.
