# The first-silicon panic, symbolized — and the attempt-3 pre-registration

2026-08-25.  Scores against `docs/060-F4-M2-PREREG-260824.md`.  The artifact under test was
the F1 kernel `unix-060`, sha256
`82470ea2943ff420e5315d4aed46b270830cb07eb2f7f1c099fe43c4807c7ef7` — byte-for-byte
`unix-040` (`da8119ca1966193792c06ef7ccc6d37edcd039031ea3af730be0ba5d2f462703`, build id
`68040-260824-06`) with one byte changed: `cputype` 40 → 60 at `.data+0x187b4`.  Load base
`0x08000000` (shape M-A), read off the panic PCs themselves.

Per the pre-registration's §6 this is **not** one of the three kill-criterion attempts: a boot
that reaches the banner and dies afterwards is a finding, and this one is named to the
instruction.

## 3. Fault 1 — `initialize+0x5C`: the A3000 SCSI that this machine does not have

```
    d51c <initialize>:
    d522:  tstb   once_%0                  | run once
    d528:  bne    d5e8
    d534:  pea    %fp@(-4)                 | autocon(0x0202F003, 0, &device, &slot)
    d538:  pea    device
    d53e:  clrl   %sp@-
    d540:  movel  #0x0202F003,%sp@-
    d546:  jsr    autocon
    d550:  tstl   %d0
    d552:  beq    d564                     | not found        -> panic
    d556:  cmpil  #0x00DD0000,device
    d560:  beq    d572                     | found, as expected
    d564:  pea    LC%0                     | "a3091"
    d56a:  jsr    panic
    d572:  moveal device,%a0
    d578:  movew  #3,%a0@(2)               | <-- FAULTS
```

**`device` held `0x00DD0000`, not a sentinel, and the guarded panic six instructions above was
therefore correctly *not* taken.**  Two independent proofs:

* `psw = 0x2204` → **Z set**.  The last flag-setting instruction before the fault is the
  `cmpi.l #0x00DD0000,device` at `d556` (`moveal` and the faulting `movew` do not update CCR
  before completion, and the 68060 stacks the pre-instruction SR).  Z set means *equal*.
* **No `PANIC: a3091` line appears on the screen**, and `panic` prints.  `d56a` was not executed.

So `%a0 = 0x00DD0000` and the faulting store is `movew #3` to **`0x00DD0002`** — the A3000
motherboard WD33C93 SCSI register.  **This machine is an A4000.  Nothing answers at
`0x00DD0000`, the bus times out, and the 68060 takes a real access fault.**

Where `0x00DD0000` came from is stock `autocon` (`.text+0x19222`), which does not scan for this
board at all — it **synthesizes** it:

```
   19222 <autocon>:
   1923a:  bnew   19264                    | scan the real AutoConfig chain
   1923e:  movel  #0x07000000,%d7
   19244:  cmpil  #end,%d7
   1924a:  bccw   19264                    | 0x07000000 >= end -> scan
   1924e:  cmpil  #0x0202F003,%d6
   19254:  bnew   19264
   19258:  movel  #0x00DD0000,%a1@         | *device = 0x00DD0000
   1925e:  moveq  #1,%d0                   | "found"
```

The gate is `end > 0x07000000` — a *memory-layout* proxy for "this is a machine with fast RAM,
so the A3000 motherboard SCSI is present".  On an A3000 that proxy is always right.  On an
A4000 with a Z3660 the kernel binds at `0x08000000`, `end` is above `0x07000000`, the proxy
fires, and `autocon` reports a controller that is not there.  (The same gate, read from the
other side, is the known "the a3091 vanishes at 64 MB" behaviour: load the kernel low enough
and the synthesis stops firing.)

**This is exactly the emulation-forgives / silicon-faults class, with the polarity of the
access inverted from the one first proposed: it is a WRITE, not a read, and the address is a
real device address rather than a wild pointer.**

### Why the bench never saw it — discriminated, not assumed

The bench rigs are A3000-shaped: the emulated machine really does have a WD33C93 at
`0x00DD0000`, so the same instruction at the same PC executes and **completes**.  This is not
bus forgiveness — it is a genuine machine-model difference, and it is the reason the same
kernel lineage boots the bench 060 rig to multiuser.  The path is executed on both; only the
silicon has nothing to answer it.

`0x00DD0002` is below `0x40000000` and therefore inside DTT0's transparent identity window
(`src/pstart040.s:327`, "0-1GB data, cache-inhibited"), so the MMU is not involved and the page-fault
resolver never ran — **which is why fault 1 produced no `FAILEXIT` line of its own.**  That
absence is itself evidence for a hard bus error at a low, transparently-translated address, and
against any wild-pointer reading.

## 4. Fault 2 — `backtrace+0x9C`: the panic printer walked off the top of the stack

The `krnxflt` warning belongs to **this** fault, not to fault 1.  Its fields decode from
`src/krnxmemflt040.s`: `w=2` is the "no `kas` segment owns the fault address" exit (`:208`),
`depth=1` is this process's resolver depth, and `rw` comes from the SSW with **bit 0 set
meaning a pure READ** (`:31`).  `rw=1` is a read; fault 1 was unambiguously a write.  The
warning printing *after* the first backtrace, and the `va` it carries, both belong to the
second fault.

```
   595a4 <backtrace>:
   595fa:  printf("%x: ", frame)           | the frame address prints BEFORE it is judged
   5960e:  bsrl   bt_frame_ok              | our ISSUE-50 island: range + order + cap
   59628:  tstl   %d0 / beqw 5979a         | refused -> stop the walk
   5962e:  moveal %fp@(-4),%a0
   59632:  addqw  #4,%a0
   59634:  movel  %a0@,%d1                 | d1 = the frame's saved return address
   59636:  subql  #6,%d1                   | -> the call instruction to decode
   5963c:  moveal %fp@(-12),%a0
   59640:  movew  %a0@,%d0                 | <-- FAULTS
```

The last accepted frame is `0x40001FC0`.  This project already knows that number: it is
`u + 0x1FC0`, **the constant `_start` loads into `%sp`** (`relink-040.sh:290`) — the very top of
the kernel stack.  Its return-address slot was never written, so it reads **0**, and
`0 - 6 = 0xFFFFFFFA`.  Reading the instruction word there is above `0x40000000`, so it *is*
MMU-translated, the resolver did run, found no segment (`w=2`), and the panic became a double
panic.  Every number on the screen is now accounted for.

`bt_frame_ok` validates the **frame pointer** — range, strict ordering, even, 64-frame cap.
`0x40001FC0` passes all four honestly; it is a real frame.  What nothing validates is the
**return address read out of it**, which the walk then dereferences at `ret-6` and up to `ret`.

**A panic path may not dereference an unvalidated pointer.  The first panic's evidence is the
whole reason the path exists, and here it cost us the tail of the walk.**

## 5. The blocker behind both faults

`initialize()` ran at all only because the root open reached the `a3091` driver.  This
artifact's only SCSI driver **is** `a3091`, and this rig's root is `ced0s1` — card 1, the Z3660
piscsi controller.  Measured over the artifacts built since 2026-08-20:

| artifact | `FPI!` (F1 fpuinit) | `z3660` (piscsi driver) |
|---|---|---|
| the F1 kernel `unix-060` | 1 | 0 |
| `unix-040-…-hg-z3660-target-CARD1-ced0s1` | 0 | 69 |
| `PASSB-z3660`, `unix-040-z3660-target` | 0 | 69 |

**No kernel exists that both survives an LC060 and can reach this rig's root device.**  The F1
kernel has the FPU probe and no driver for the disk; the three piscsi kernels have the driver
and no FPU probe, and F1-M3 measured what that costs on an FPU-less part — the 85 s hang at the
Commodore copyright line.

This is a gap in the pre-registration itself, amended in `060-F4-M2-PREREG-260824.md` §1 by this
change: nothing on the nine-item checklist asked whether the artifact contains a driver for the
root device of the machine it was about to be booted on.

## 6. Attempt-3 pre-registration

Registered before the code and the build that it judges.

### 6.1 The artifact

The combination that has not existed until now: the F1 override set (the `fpuinit` probe, the
`fpu_present` body gates, the `sendsig` wrapper) **and** both Z3660 drivers, rooted on card 1.
`relink-040-z3660.sh` is a post-pass over any base kernel, so the composition is a pipeline and
not a merge:

```
sh relink-040.sh                                   -> build/unix-040          (FPUINIT060=1)
sh relink-040-z3660.sh build/unix-040 build/unix-040-f1-z3660
python3 build/stamp-card1.py …                      -> root = ced0s1
cputype 40 -> 60                                    -> unix-060
```

**Registered:** the two override sets do not collide.  `TOTAL complaints: 0`, `bindings
failing: 0`, no unresolved symbols beyond `edata`/`end`/`etext`, text/data contiguous, `.data`
size 4-aligned.  A collision — the same stock address claimed by both arms — is a **finding**,
not a build error to work around, and would be reported rather than patched over.

### 6.2 What the boot should do

* the banner, then `no fpu detected` — unchanged; silicon already proved the probe answers
  correctly on this part, and nothing in this change touches it;
* `fpi_n = 1`, `fpi_trap_n = 1`, `fpi_nofpu_n = 1`, `fpi_ok = 0`, `fpc_*_nofpu_n = 0` — the F1
  rows re-read at the new load base, and they must reproduce;
* the root open reaches the **`z3660`** driver, not `a3091`, and `initialize+0x5C` is therefore
  never executed.  **`0x00DD0002` is not written.**
* the boot proceeds past the root mount.

### 6.3 What may lurk behind it — registered honestly

**The next forgiveness-class fault is plausible, and we should expect one rather than be
surprised by one.**  This class is not a single bug; it is a property of a kernel written for
one machine and now running on another, on real silicon for the first time.  Every hardcoded
motherboard address in this kernel is a candidate, and `autocon`'s synthesis shows the shape:
an assumption that was always true on an A3000 and is simply false here.  Getting past
`initialize` buys the root mount, not the boot.

Registered so it cannot be re-scoped afterwards: **a second fault of this class at a different
PC is a success for this change, not a failure of it.**  The claim being tested is "the root
opens through the piscsi driver", and that claim is settled by whether `initialize+0x5C`
executes — which the counters and the panic PC answer either way.

### 6.4 The two guards

Both are judged separately from the boot:

* **`bt_frame_ok` rule 4** (the return address).  Registered: a panic on either CPU produces a
  backtrace that ends cleanly instead of double-faulting, `bt_badret` counts 1 for the
  top-of-stack frame, and `bt_lastbadret` holds the refused call-site address.  This code runs
  **only on a path that is already panicking**, so it cannot change a successful boot — which
  is the reason it is allowed into the attempt-3 artifact at all.
* **the `autocon` synthesis probe**, if it is built: registered as a **separate artifact**, not
  folded into the attempt-3 boot.  It is inert on the registered path (with the root on `ced0`,
  `a3091`'s `initialize` never runs), and a first-of-its-kind boot should carry one variable.
