## 2. Why each arm is its own stage, and what the primaries carry

**Its own stage, because a determinism proof taken over a stage that carries two changes measures
two things at once.**  Round 7 made `ucp` its own stage for exactly this reason; round 8 keeps two
arms in **one** script but they are mutually exclusive, so a build carries one change over the
round-8 base and §6 measures precisely that.

**Each primary carries `kvd`, `swa` and its arm** — the same base round 7's `ucp` was built over,
`build/unix-040-f7vs` (sha256 `d43a59cc…`, the kvd+swa base with **no** `ucp` and **no** `mcs`).  So
the chains are

```text
  f7vs  --(relink-040-f8.sh --ucp2)-->  f8a1     (Arm I)
  f7vs  --(relink-040-f8.sh --ucz )-->  f8a2     (Arm II)
```

and the one change each determinism proof measures is the last arrow.

**The additivity chain to round 7.**  868936f (the round-8 pre-registration) is additive over the
round-7 base — it added a document and nothing else — and these arms are additive over 868936f: they
are **new files** and touch no unit of the round-7 lineage.  So the whole round-7 chain reproduces
byte-for-byte apart from its build id, which §6 shows rather than asserts:

```text
  f7uft  --(f4arms --ufault --cache 60)-->        (round 5)
         --(f6 --kvd --swa)-->  f7vs              (round 6 arms)
         --(f7 --ucp)-->        f7vsu             (round 7 primary — reproduces)
  f7uft  --(f6 --swa)-->        f7swa             (round 7 fallback — reproduces)
```

**Neither `ucp` nor `mcs` is in an arm, and the script refuses rather than discovers it.**  `ucp2`,
`ucz`, `ucp` and `mcs` all define `savecontext` and `restorecontext`, so `relink-040-f8.sh` rejects
any input carrying `ucp_magic` or `mcs_magic`, with the reason, before it assembles anything.
Verified against `build/unix-040-f7vsu` (has `ucp`) and `build/unix-040-f7vsm` (has `mcs`): exit 1,
no output file, each with its own message; and `--ucp2 --ucz` together is refused as "exactly one".

## 4. Deviations from §4.1 / §4.2, stated rather than absorbed

Each is recorded in the unit's own header too.

**Arm I (`ucp2`):**

1. **A fifth metadata longword per slot, the save-time rotating fold** (slot+16).  §4.1 says the
   rotating fold's "save-time value goes in the shadow slot's metadata … a fifth" — this is it.  It
   also lets an operator read out both folds of a shadowed frame and re-derive them by hand, which
   is what bench row 4 needs to prove the two folds are **different functions** rather than one that
   never disagrees.  `ucp_doff` becomes 20 and the slot 824 bytes.
2. **`ucp_rot_b_*` latch the first rot-disagree-plain-pass event** (seq, ucp, stamp, slot, and both
   rotating folds).  §4.1 registers only the counter `ucp_rot_bad_n`; without a witness a non-zero
   count is the "null result that means nothing" this project refuses.  A one-shot, six longwords.
3. **`ucpev`'s 16-byte header is (seq, stamp, ucp, slot)** so the ring slot holding the save side is
   named in the evidence itself.  §4.1 does not specify the header.
4. Inherited from round 7 and kept: the save-time **plain** fold at slot+12, and `ucp_dup_n` /
   `ucp_hit_n` / `ucp_diffev_n`.

The rotating fold **cannot false-positive on a legitimate `ucontext` edit**: both folds cover
`mc_state[0..200]` only.  A handler rewriting resume registers writes `gregs` at `ucp+0x24`, outside
the fold.  A handler rewriting `mc_state` could not re-stamp the kernel's internal checksum, so its
object fails the **plain** fold and lands in the bad path, never the rot-disagree-plain-pass path.
A rot disagreement while the plain fold passes therefore means the XOR was preserved while the bytes
changed — an even-parity change to a stamped object, which is the invisible corruption and nothing
else.

**Arm II (`ucz`):**

1. **The re-stamp, and it is forced.**  `savecontext` is WRAPPED, so the stock `stampsum` has
   already run when this code gets control, and the FPU gate can only be read from `uc_flags` *after*
   that (savecontext writes `uc_flags`).  So the zeroing is necessarily on the far side of the stock
   stamp.  Left so, every restore of a zeroed object would fold non-`FFFFFFFF`, `ucp_bad_n` and
   `ucp_s_bad_n` would climb, and the guest would fail its own checksum on every signal and never
   boot.  So the arm re-computes `mc_state[200] = ~(XOR mc_state[0..199])`, which after zeroing
   `[4..199]` is `~(mc_state[0]^[1]^[2]^[3])` — exactly what stock's `stampsum` would write over the
   zeroed field, since `…ATT7-RESULTS…` §8.1 established our XOR fold **is** stock's fold.  The object
   is then self-consistent over zeros, **the detector is kept** (a post-save flip still breaks the
   fold), the guest boots, and §4.2's "the stamp stock computes already covers zeros" holds as a
   re-stamp.  Bench row 5's "`mc_state[0..3]` and the stamp are intact" is this.  **This is not a
   choice; the FPU gate's own requirement forces it, and it is recorded rather than absorbed.**
2. **`ucp_z_fpu_n` and `ucp_z_on` are additions.**  §4.2 registers `ucp_z_n` and `ucp_z_skip_n`;
   `ucp_z_fpu_n` makes Rig B's safety inertness a **positive count** (`ucp_z_fpu_n = ucp_save_n`,
   `ucp_z_n = 0`) rather than an inference from `ucp_z_n = 0` alone, and `ucp_z_on` is a one-word
   control that turns the zeroing off while the rest of the unit runs — which is **R14's registered
   control** for separating "value-dependent" from "the arm perturbed the timing".
3. **The layout row (`ucp_ms4..19`) necessarily reads 0 on this arm**, because it runs downstream of
   the zeroing.  That is a confirmation the zeroing reached the pre-wall save, not a defect.
4. Inherited from round 7 and kept: the fourth metadata longword `ucp_b_s_fold`, and `ucp_dup_n` /
   `ucp_hit_n` / `ucp_diffev_n`.

The three gates are built exactly as §4.2 registers them: **FPU** (`uc_flags` bit 3 clear, else
decline → `ucp_z_fpu_n`), **format** (`(mc_state[1] >> 12) & 15` ∈ {0,4}, else decline →
`ucp_z_skip_n`), **shown** (`ucp_z_n` counts frames zeroed; the shadow ring is read to confirm
`mc_state[4..199]` all zero with `mc_state[0..3]` and the stamp intact).

### 7.3 The fast tier and the expensive reads

Per boot: `swa` first (the only block guaranteed to have fired), then the `ucp` block in one `kpeek`
(with `ucp_sent0` read FIRST of it), then the `uft` head with the arm's wall reading beside it, then

* **On every Arm I boot** also read `ucp_rot_n` / `ucp_rot_bad_n` (R1/R2), the histogram
  `ucp_fmt_h0..h15` with `ucp_fmt_bad_n` (R3/R4/R5), and `ucp_r_at_wall` (R9/R10).
* **`ucpev` is read in full** — 804 bytes — on the first Arm I boot that latches, together with the

  the rest per the rig), and `ucp_b_bits` on any latched event (R11/R12/R13, bit 14 now visible).
* **Any boot whose wall address is not `4AFC0008`** reads the full sixteen `u_ar0` longwords first
  (attempt 7's owed protocol fix).

## 10. Registered cost, unchanged and not small

`ucp2` folds 201 longwords **twice** (plain and rotating) per `savecontext` and per
`restorecontext`, copies 804 bytes per save, and — the item to watch — runs a **four-slot ring scan
on every restore**, ~190,000 times a boot, so the two folds can always be compared.  `ucz` folds
201 per save and per restore, copies 804 per save, and on a *format-0/4, no-FPU* save adds a
196-longword `bzero` and a four-longword re-stamp.  **A boot in which the refusal does not occur
cannot be read as "the defect went away"** — it is one draw from a distribution these arms have
perturbed harder than round 7, and `…ATT7-UCP…` §10 is not repealed.

## 11. What this commit does NOT do

* **It scores nothing and boots nothing.**  Every R row of `…ATT8-PREREG…` §5 is still open.
* **It does not decide `ucp_sent0`.**  The killer is built and readable on both arms; it has not been read.
* **It ships no cure.**  §6 of the pre-registration forbids shipping C1 or C2 as a fix in any
  artifact of this round; `ucz`'s `bzero` is behind `ucp_on` and `ucp_z_on` so the default cannot
  become a silent behaviour change, and it does not stop the `SIGKILL`.
* **It does not retire `src/ucp_dbg.s` or `src/mcstate_dbg.s`.**  Both stand; `relink-040-f7.sh` and
  `relink-040-f6.sh` are unchanged and reproduce their artifacts.
* **It changes no driver source and flips no shipping default.**  `z3660_cache` stays baked at 60;
  `amix-z3660scsi` and `amix-z3660net` are untouched.
* **It does not build the `ucp_on` control** as a separate artifact; a one-word control is minted
  only if the session asks for it.
