## 1. The measured situation, in four sentences

silicon, no bus fault occurred, and the boot stopped one step further on at
`PANIC: swapconf lookupname /dev/dsk/ced0s2 failed - error 20` — a **guarded stock panic**, not a

off (`z3660_cache = 0`, the shipping default and §4.6's *predicted-FAIL* arm), with a UFS directory

cure gated off on 060 (`src/hgfault040.s:143-146`).

This round builds one artifact to **name** the mechanism and one to **test** candidate 1.

## 2. Why `error 20` is a different animal from `error 2`

`swapconf`'s first act is `lookupname(swapfile.bo_name, UIO_SYSSPACE, FOLLOW, NULL,
&swapfile.bo_vp)` — the first namei path lookup of the whole boot — and a non-zero return is
`cmn_err(CE_PANIC, ...)`.  Two histories meet at that one call:

| errno | meaning | history |
|---|---|---|
| 2 `ENOENT` | a **name** is not in a directory that was read as a directory | the 68040 signature, root-caused to a bad directory read, closed by `gen_strategy` PFN `<<11` → `<<12` (`src/hat-040-port-worklist.md:21`, `docs/ISSUE10-SETUPSH-WALL-260819.md:301`) |
| 20 `ENOTDIR` | a component on the way in **is not of type `VDIR`** | ours, 2026-08-25, first silicon |

`ENOTDIR` comes from `lookuppn`/`VOP_LOOKUP` refusing to walk *into* something whose `v_type` is
not `VDIR`.  It is therefore not a statement about the leaf `ced0s2` at all: it is a statement
about `/`, `/dev` or `/dev/dsk`.  **Which one, and what type it reads as instead, is the whole
measurement** — and it is exactly what a stale cache line over a freshly DMA'd directory or inode
block produces, because the mode field that decides `v_type` is a handful of bytes inside a block
the CPU may hold an out-of-date copy of.

## 3. The instrument — `src/swapconf_dbg.s`, rewritten

The file existed (2026-06, for the `ENOENT` era) and hardcoded `/dev/dsk/c6d0s2`.  Rewritten for
this round: the prefixes are card-independent literals and the leaf comes from
`swapfile.bo_name` itself, so the probe cannot disagree with what stock would have looked up, on
card 0 or card 1.

It does **two passes of five lookups with a whole-data-cache push+invalidate between them**, then
decides:

```
pass 1     "/"  "/dev"  "/dev/dsk"  <sibling>  <swapfile.bo_name>
           for every success: read v_type out of the returned vnode, then VN_RELE it
cpusha dc  0xf478 -- push every dirty line and invalidate (the src/dma_cache040.s idiom)
pass 2     the same five, into a second set of slots
verdict    pass-2 lookup of bo_name == 0  ->  tail-jump to swapconf_orig, i.e. let the REAL
                                              swapconf configure swap and boot normally
           otherwise                     ->  skip swap, return 0, say so loudly, boot on
```

`<sibling>` is `bo_name` with its last character replaced by `'1'` — on this rig `/dev/dsk/ced0s1`,
the **root** node, the one the running system demonstrably reads.  It is the control for the leaf.

Everything is also recorded in a counter block so a scrolled screen costs nothing:

```
kpeek 0811172C 28          (load base 0x08000000; swd_magic must read 53574421 = 'SWD!')

  +0x00 swd_magic     +0x18 swd_p1_root   +0x2c swd_vt1_root  +0x40 swd_p2_root   +0x54 swd_vt2_root
  +0x04 swd_n         +0x1c swd_p1_dev    +0x30 swd_vt1_dev   +0x44 swd_p2_dev    +0x58 swd_vt2_dev
  +0x08 swd_cacr      +0x20 swd_p1_dsk    +0x34 swd_vt1_dsk   +0x48 swd_p2_dsk    +0x5c swd_vt2_dsk
  +0x0c swd_vfsop     +0x24 swd_p1_sib    +0x38 swd_vt1_sib   +0x4c swd_p2_sib    +0x60 swd_vt2_sib
  +0x10 swd_rootvop   +0x28 swd_p1_swap   +0x3c swd_vt1_swap  +0x50 swd_p2_swap   +0x64 swd_vt2_swap
  +0x14 swd_vt_root                                           +0x68 swd_called   +0x6c swd_skipped
```

A `swd_vt*` slot reading `ffffffff` means that lookup failed, so no type was read.  A `swd_p*` slot
reading `ffffffff` means the probe never ran at all.

**Everything on the screen and in the counters is HEX.**  `ENOTDIR` (20) prints as `14`; `ENOENT`
(2) prints as `2`.  `v_type`: `VNON 0, VREG 1, VDIR 2, VBLK 3, VCHR 4, VLNK 5, VFIFO 6, VBAD 8`.

### 3.1 The discriminating signatures, registered verbatim

**Table A — pass 1, the prefix walk.**  Read the first row that matches.

| pass-1 reading | mechanism it names | candidate |
|---|---|---|
| `/=0  dev=0,t2  dsk=0,t2  s1=0  s2=0` (everything succeeds) | **non-reproduction.**  Not "no bug": the probe's own `cmn_err` output and its extra lookups sit between the failing read and ours, so a failure that does not reproduce under instrumentation is a *state-dependent* one.  That is the shape of a coherency defect and **not** the shape of a deterministic namei/path defect, which would fail identically every time | 1, weakly |
| `/=0  dev=14` | the **root vnode itself** is refused as a directory — `rootdir`'s type or ops are wrong.  `swd_vt_root` says what it reads as (`2` = VDIR is correct) and `swd_rootvop`/`swd_vfsop` say which filesystem owns it | **neither registered candidate** — a mounted-root/vnode-state fault, and a new finding |
| `/=0  dev=0,t2  dsk=14` | `/dev` resolved and is then refused as a directory: the inode read for `/dev` gave a wrong mode.  `swd_vt1_dev` names the wrong type | 1 |
| `/=0  dev=0,t2  dsk=0,t2  s2=14` | `/dev/dsk` resolved *as a directory* (`swd_vt1_dsk` = 2) and was then refused as one during the leaf walk.  The classic mixed/stale page: two reads of the same object disagree | 1 |
| `... s2=2` (`ENOENT`, not `ENOTDIR`) | the leaf name is genuinely absent from a directory that reads as a directory.  **This is the historical 040 signature, not ours** — a different bug at the same site, and it would mean attempt 3's `error 20` did not reproduce | the `gen_strategy` / ISSUE-10 class |
| `s1=0` while `s2` fails | the two nodes are neighbours in the same directory data; one resolving and the other not localises the damage **below block granularity** — i.e. to a cache line, not to a page or a disk block | 1, sharpened |
| `s1` and `s2` fail identically | the failure is at the parent; neither leaf name was ever reached | 1 or 2, undiscriminated by this row |
| any `swd_vt1_swap` other than `3` on a successful `s2` | the leaf's own mode field is wrong (a block special reading as something else).  A corruption at the leaf rather than at a directory | 1 |

**Table B — pass 2, the decisive row.**  This is the reason the instrument exists in this shape.

| pass 1 | pass 2, after `cpusha dc` | verdict |
|---|---|---|
| some lookup fails | the **same lookup returns 0** | **candidate 1 proven by this artifact alone.**  Nothing happened between the two reads except a push+invalidate of the data cache: no disk I/O was repeated, because the page-cache page for that directory is already valid and `lookuppn` re-reads it from RAM.  So the bytes in RAM were right and the CPU's cached copy was stale.  Arm B then has a *mechanism*, not a hypothesis |
| some lookup fails | the same lookup fails with the same code | the wrong bytes are in **RAM**, not merely in the cache.  The stale-line form of candidate 1 is refuted; what survives is DMA landing somewhere it should not, candidate 2, or a genuine namei defect.  **Read `swd_cacr` bit 28 (DPI) FIRST** |
| everything succeeds | everything succeeds | non-reproduction; Table A row 1 |

**The DPI caveat, registered so a null result cannot be over-read.**  On the 68060, `CPUSHA`'s
*invalidate* half is suppressed when `CACR` bit 28 (DPI) is **set**.  This port's `CACR` is
`0x80008000` (`src/pstart040.s`, and `src/dma_cache040.s` says so in as many words), so DPI is
expected **clear** and the push does invalidate — but that is a reading, not an assumption.
`swd_cacr` carries the value.  **If bit 28 reads set, the pass-2 row is VOID, not negative.**

**The flap signature.**  If `swd_called = 1` (the retry succeeded, so the override tail-jumped to
the real `swapconf`) and the screen *then* shows the stock `PANIC: swapconf lookupname ... error N`,
three reads of the same path produced two good answers and one bad one.  That is a stronger
coherency signature than any single reading in Table A.

### 3.2 What the instrument buys besides the name

`swapconf_dbg` **carries the boot past swap** — normally, by running the real `swapconf`, and
otherwise by skipping it.  Either way the boot proceeds into userland, which is what unlocks
`/dev/kmem`, §4.6's live A/B and §4.7's dhrystone row.  Two honest caveats:

* **`anon_resv` with no swap.**  If swap is skipped, `anoninfo.ani_max` stays 0 and every anonymous
  reservation may be refused.  This is not speculation: an `anon_resv` stub existed in the dbg
  relink *precisely because* `swapconf` was being skipped, and was dropped on 2026-06-23 when
  `swapconf` started working (`relink-040-dbg.sh:55`, `src/forkdbg.s:33-35`).  Expected symptom is
  `init` or the first `fork` failing with ENOMEM, **not** a panic.  Registered here so that if it
  happens it is recognised, not re-discovered.  It applies only on the skip path
  (`swd_skipped = 1`); on the `swd_called = 1` path swap is configured normally and this risk is
  absent.
* **`nlist` against `/stand/unix` is a trap.**  The 2026-08-25 bench round recorded it: the kernel
  under test is installed into the **boot slice**, so `/stand/unix` inside the root filesystem is
  still the box's older kernel and an on-box `nlist` names the wrong addresses.  Every address for
  the live A/B must come from `tools/status-facts.sh` at the observed load base, or from §4 below
  — never from `nlist`, unless `/stand/unix` is separately replaced with the same image.

## 4. The arm-B mechanism — how a COMMON became pokeable

`amix-z3660scsi/src/z3660.c:320` declares `long z3660_cache;` — a C tentative definition, so the
object carries it as a **COMMON** symbol, the loader allocates it in bss and zeroes it, and there
is no byte in the linked kernel to poke.  That is why attempt 3 recorded arm B as unreachable
except through `/dev/kmem` on a multiuser system, i.e. exactly the state the failure prevents.

`src/z3660_cache_arm.s` gives it a `.data` home.  A defined symbol beats a common, so the link
absorbs the driver's common into this definition and every driver reference relocates here.
**The driver's repository is not touched.**  `src/patch_z3660_cache.py` then stamps the value and
refuses four silent failures: the symbol still being `SHN_COMMON` (the definition did not absorb
it), the symbol not being in `.data`, the magic word in front of it not reading `ZCA!`, and the
piscsi driver not being present in the image at all.  The witness word behind it is stamped too
and required to agree.

```
kpeek 08111454 3     zc_magic 5a434121 'ZCA!' | z3660_cache | zc_armed
                     08111454              08111458        0811145C
```

**`z3660eth_cache` is deliberately left COMMON and zero.**  The ethernet arm is a separate question
with its own *predicted PASS*, and arming both would make the SCSI answer a two-variable one.  The
build prints its status on every run so the choice is on the record rather than assumed.

**Measured, not argued:** the arm-B image and its own control differ by **exactly three bytes** —
the two stamped value words and one build-id digit.

### 5.3 Reading the driver's own counters without a multiuser system

`z3660_push_n` and every other §4.6 gate is a COMMON, so its address is chosen by the loader and
cannot be computed from the file.  It **can** be read the way the 2026-08-25 bench round read it:
each reference is an `R_68K_32` relocation, so the loader wrote the resolved address into the
instruction stream.  Read the longword at `load_base + offset` below and it *is* the counter's
address.  The offsets are identical in both artifacts (the driver text did not move):

```

z3660_inv_n      .text 0x0f55d0      z3660_sptalloc_unsafe .text 0x0f54ac
z3660_inv_bytes  .text 0x0f55d6      z3660_bounce_wr_n     .text 0x0f592c
z3660_range_ovf  .text 0x0f5536      z3660_bounce_rd_n     .text 0x0f5994

z3660_ci_ok      .text 0x0f5406, 0x0f54ca, 0x0f54d8
```

## 6. Pre-registered expectations

### 6.1 The DBG artifact

* the banner, then `no fpu detected`, then `68060-260825-06` — the F1 rows must reproduce
  (`fpi_n = 1`, `fpi_trap_n = 1`, `fpi_nofpu_n = 1`, `fpi_ok = 0`, `fpc_*_nofpu_n = 0`) at the
  **shifted** addresses of §5.2.  Nothing in this arm touches the FPU probe;
* `initialize+0x5C` is not executed and `0x00DD0002` is not written — unchanged from attempt 3;
* **`PANIC: swapconf lookupname ... error 20` cannot occur**, because the function that prints it
  has been replaced.  Its absence is not evidence of anything;
* the seven `DBG` lines print, and `swd_magic` reads `SWD!` with `swd_n = 1`;
* the boot proceeds past swap, by one of the two routes, and `swd_called + swd_skipped = 1`;
* Table A and Table B are read **as written**, first matching row wins.  No row is re-scoped after
  the reading.

**How to tell from a backtrace which kernel is on the screen.**  `main` has exactly one
relocation naming `swapconf`, and in this artifact it resolves to `0x000f7530` instead of the
stock `0x000b401e`.  So the frame attempt 3 printed as `8059900->80B401E` prints here as
**`8059900->80F7530`**, and the probe's own tail jump lands back on `80B401E`.  One frame
identifies the artifact without reading a counter.

**Registered as a success, not a failure, of this change:** a *new* stop further along the boot.
This artifact's claim is "the ENOTDIR is named and swap no longer ends the boot", and that claim is
settled by the `swd_*` block regardless of what happens next.  The same rule attempt 3's §6.4 used.

### 6.2 Arm B

* if candidate 1 is the mechanism, `swapconf` succeeds and **no swap panic appears at all** — the
  boot proceeds, and multiuser, `/dev/kmem`, §4.6's counter gates and §4.7's dhrystone row all
  become reachable in that one boot;
* if the panic reappears **unchanged, with the same `error 20`**, cache maintenance at
  `z3660_cache = 60` does not close this stop;
* every counter block sits at attempt 3's addresses (§5.2); `zc_magic` reads `ZCA!` and
  `z3660_cache` reads `0000003c`.  **If `z3660_cache` reads 0 the run is void** — the image booted
  was not the one intended;
* §4.6's gates apply to any coherency claim from this boot and are not optional:
  preconditions `z3660_direct_map == 1`, `z3660_ci_ok == 1`, `z3660_dtt0`/`_dtt1`/`_cacr` captured,
  CACR bit 28 recorded; gates `z3660_push_n > 0`, `z3660_nest_hits == 0`, `z3660_cq_overflow == 0`,
  `z3660_sptalloc_unsafe == 0`, `z3660_bounce_wr_n == 0`.  **A green boot with `z3660_push_n = 0`
  is a failed run**, because it proves the maintenance was never exercised.

### 6.3 What arm B does NOT prove — registered so it cannot be claimed afterwards

* **Not the F3-M3 canary.**  §4.6's arm-B claim is *15/15 cycles clean and 8/8 canary binaries
  byte-identical* — a load protocol.  One boot to multiuser is at best one cycle and no canary.
  **The canary is still owed** and no amount of a clean boot substitutes for it.
* **Not a decision on the ISSUE-10 cure gate.**  Candidate 2 is a separate latent question
  (`060-F4-M2-PREREG-260824.md` §7 declines it in either direction, and so does this round).  Arm B
  succeeding shows candidate 2 was not the cause of *this stop*; it says nothing about whether the
  cure should be ungated on 060.
* **A failure of arm B does not refute the coherency class.**  It refutes only "z3660scsi's own
  maintenance, as implemented, at `z3660_cache = 60`, closes this".  DMA landing in the wrong
  physical page is in the same family and no cache push fixes it.
* **Nothing about `z3660eth`.**  Its arm is deliberately at 0.
* **Arm B alone cannot separate "the maintenance fixed it" from "the extra cache ops changed the
  timing."**  Only the DBG artifact's Table B row can, which is why the two artifacts corroborate
  each other and why either alone is the weaker reading.
* Everything in `060-F4-M2-PREREG-260824.md` §7 that this round does not touch still stands: no FP
  result, no full-68060 result, no durability result, no 100 MHz result.

## 7. The boot order, and why it is this way

1. **`unix-060-f4dbg-CARD1-ced0s1` first — to NAME.**
2. **`unix-060-f4cache60-CARD1-ced0s1` second — to TEST.**
3. `unix-060-f4cache0-CARD1-ced0s1` — the control, **only** if (2) behaves differently from attempt
   3 *and* the session wants the delta attributed to the value rather than to the relink.  Its
   registered behaviour is attempt 3's, line for line.

DBG-first strictly dominates.  The probe artifact can never reproduce the panic (it replaces the
function that prints it), so booting it second would risk ending the session with the arm answered
and the mechanism unnamed.  Conversely arm B's verdict is one line on the screen and needs no
instrument, and the DBG boot may itself reach multiuser under arm A — which is the cheapest route
there is to `/dev/kmem`, the §4.6 gates and the dhrystone row, and it gets them **with the shipping
default in force**, which is the more interesting posture to measure from.

If the DBG boot reaches multiuser, the live `/dev/kmem` poke of §4.6 becomes available *within that
boot* — subject to §3.2's `nlist` trap: take the addresses from §5.3 and `tools/status-facts.sh`,
never from `/stand/unix`.
