# The battery on a 68040, and the row that was passing without measuring

`68040-260830-06`, A3640/68040, 2026-08-30.

```
image      build/unix-040-quiet
sha256     e1fb866eb72af3b8381868846e85e6176afbe6455c2b96a1f43f3437bddcc361
uname -m   Amiga (Unlimited) 68040-260830-06
load base  0x07000000        <- from the loader: kernel: entry=07000000 tvaddr=07000000
text       1009096 (0xf65c8)
driver     test-tools/batteryrun-260830-06.sh, GENERATED by tools/gen-battery.sh
```

The 12-row battery had reached 12/12 on the 68060 on 2026-08-27 and had never been run on a 68040
with anything close to this kernel: over a hundred commits had touched `src/` since the last 040
session on 2026-08-13 (`git log --since=2026-08-13 -- src/` counts 101 as this was written). The A3640 was already installed, so the run cost nothing but time.

## Result

**Battery 12/12, all 38 magic words read back, every must-stay-zero counter zero.** One of the
twelve was measuring nothing, which is the finding this document is really about, and it is fixed
and re-run below.

Three further things were established on the same boot, without a reboot between them:
`fp060probe` 7/7 bit-exact through the 040 FPSP with the 68060 package provably not entered; the
`kvp` probe's cost measured at **7.4% of system time per system call**, together with the
histogram that says which paths it is on; and Dhrystone demonstrated to be incapable of resolving
that cost, which is what the standing plan had proposed to use.

```
=== MAGIC CHECK (38 blocks, 38 checks) ===
all 38 magics OK
...
BATTERY-RESULT PASS
MUST-STAY-ZERO-OK
```

## The driver is generated now, and that is the point of it

Every previous battery driver was made by copying the last one and editing 30-odd addresses
against a fresh `tools/status-facts.sh` run — a third pass by hand over numbers that were already
correct twice. `tools/gen-battery.sh` does it instead: it parses `status-facts.sh`, emits the
driver, and then converts every address it emitted back to a `.data` file offset and requires the
four bytes there to equal the magic constant on the same line. Nothing is printed unless all of
them agree.

```
checked 38 magic addresses against build/unix-040-quiet -- all agree
```

Two things the generator gets right that the hand-written drivers did not:

* **the read length is the block's byte extent, not its member count.** A member may be a byte
  field, a 16-byte frame or an array; `smu` has 37 named members spanning 44 longwords. The old
  drivers used the extent and were right, but nothing said why, and a block is split into two
  `kpeek` calls only where the gap exceeds 64 bytes — which is what separates `dma_on`, 20 KiB
  from the rest of its block, from `smu_bitpop`, an eight-longword array in the middle of one;
* **no name is used for two things.** `batteryrun-260827-13.sh` used `A3D_N` first as a block
  length and then as a counter address, and worked only because the second assignment happened
  after the last read of the first. Generated names carry a `Z_` prefix for the counter
  addresses and cannot collide by accident.

It is also a superset of what it replaces, which was checked rather than assumed. Against
`batteryrun-260827-13.sh`, the last hand-written driver, the generated one adds `A3P`, `DMA` and
`Lkx` and **drops nothing**:

```sh
comm -23 <new blocks> <old blocks>   ->  A3P  DMA  LKX
comm -13 <new blocks> <old blocks>   ->  (empty)
```

The load base is passed, not assumed. `status-facts.sh` has taken it as an argument since the
A3640 first appeared; `0x07000000` reproduces the address the previous session confirmed on this
card by hand (`a3p_magic` at `0710F6E4`), and all 38 magics then read back on the first attempt.

## ISSUE-57: `devmaptest` passed without running

Both of `devmaptest`'s cases mmap physical `0x08000000` — written into the source as *"the kernel
load base on this machine"*. On this card that address is not memory. Both `mmap()`s returned
`ENXIO`, both cases took a `SKIP` return that does not increment `fails`, and the program printed
`DEVMAPTEST-RESULT PASS`:

```
  T1 SKIP: mmap /dev/mem failed errno=6
  T2 SKIP: mmap failed errno=6
DEVMAPTEST fails=0
DEVMAPTEST-RESULT PASS
```

The battery greps for that string and scored the row `ok`. **12/12 was 11 measured and one
vacuous.**

Nothing in the battery said so. The serial log did — four lines the battery never prints, denied
by this port's own fault instrument:

```
WARNING: DBG krnxflt FAILEXIT w=2 va=8000000 rw=1 depth=1
WARNING: DBG krnxflt FAILEXIT w=2 va=8000000 rw=1 depth=1
WARNING: DBG krnxflt FAILEXIT w=2 va=8000800 rw=1 depth=1
WARNING: DBG krnxflt FAILEXIT w=2 va=8000000 rw=1 depth=1
```

Three at the base and one at base+2048: `a`, `b` and `c` of T1, in order. The full entry, the fix
and the other tests that name a physical address are in `KNOWN-ISSUES.md` ISSUE-57.

### Re-run with the base probed

```
devmaptest: PAGESIZE assumed 4096
    probe: 0x8000000 does not map, errno=6
    probe: 0x7000000 maps, 3315/4096 bytes non-zero
devmaptest: physical base 0x7000000 (probed)
    kernel-base window non-zero bytes: 3315/4096
  T1 PASS: /dev/mem same-offset identical=1, base+2048 aliases correctly=1
  T2 PASS: mincore over a 4-page device mapping wrote 4 entries, canary bytes clobbered = 0
DEVMAPTEST fails=0 skips=0
DEVMAPTEST-RESULT PASS
```

So the row now says what it was always supposed to: on 68040 silicon a 2048-aligned device mmap
offset aliases to the same 4 KiB page, and `mincore` over a four-page device mapping writes four
entries and not eight. **That is ISSUE-33's page geometry and ISSUE-49's fault path measured on a
68040 for the first time.** The battery is 12/12 with all twelve measured, the twelfth taken
outside the driver.

## `fp060probe` on the 040: the control, and the invariant that makes it one

The four instructions a 68060 does not retire in hardware — `fsin`, `fetox`, `flogn`, `fmovecr` —
should simply work on a 68040, because the 040's own FPSP emulates them. That is the cleanest
available demonstration that F3 restores on the 060 what the 040 already had.

```
fadd       OK  3FF0000000000000  (0 ulp)
fsqrt      OK  3FE6A09E667F3BCD  (0 ulp)
fintrz     OK  0000000000000000  (0 ulp)
fsin       OK  3FDEAEE8744B05F0  (0 ulp)
fetox      OK  3FFA61298E1E069C  (0 ulp)
flogn      OK  BFE62E42FEFA39EF  (0 ulp)
fmovecr    OK  400921FB54442D18  (0 ulp)
FP060PROBE bad=0
```

Seven of seven, bit-exact, 0 ulp. The pass is the weaker half of the result. The `f60` block —
all 32 longwords — was read immediately before and immediately after the run and is **byte for
byte identical**:

```
diff /tmp/f60-before.txt /tmp/f60-after.txt   ->  no difference
```

`fpc_*` likewise stayed at zero across it. So the seven instructions were retired by the 68040
path with the 68060 package never entered once, which is an invariant rather than a passing test:
if the cputype gating were wrong, the counters would say so whether or not the arithmetic came
out right. `relink-040.sh` records the same pairing from an earlier kernel; this repeats it on a
kernel over a hundred commits newer.

`fp060probe` has to be cross-built — it uses `__asm__ volatile`, which the guest's 1991 `cc` will
not accept. `test-tools/mk060.sh` is the recipe and `build/fp060probe` was current.

## The `kvp_on` cost, measured — and the instrument the plan asked for cannot see it

The standing question is whether the `kvp` vector probe should ship enabled. The standing plan
was a Dhrystone A/B across `kvp_on` 1 → 0 → 1 in one boot. Two things had to be settled before
running it.

### Where the probe actually is

`src/kvecprobe040.s` wraps `nullvect` and describes it as *"the catch-all that turns an unhandled
exception into SIGSYS"*. Its own per-vector histogram says something else. After the battery,
exactly two of the 64 buckets were non-empty and every other one read zero:

```
kvp_vec[2]  =  62 432      vector 2  = access fault  (page fault)
kvp_vec[32] = 124 400      vector 32 = TRAP #0       (system call)
```

So the probe runs on the system-call path and the page-fault path — which is what the session
plan asserted and what the source comment does not. The attribution was then measured rather than
inferred: a loop of `n` = 200 000 `lseek()` calls moved `kvp_vec[32]` by 203 264 / 201 550 /
201 550 in the first arm. Every call trapped, and the excess is the rest of the machine.

### Why not Dhrystone

Dhrystone is a userland compute loop. It makes almost no system calls and takes almost no page
faults, so it exercises the probe a handful of times per run. `test-tools/kvpcost.c` times a tight
loop of one cheap system call instead, with `times(2)`, and reads `kvp_vec[32]` and `kvp_vec[2]`
around every pass so that the loop cannot quietly stop trapping without saying so.

### Three arms, one boot

Arm A2 is not decoration: without it, anything that drifted between the halves is
indistinguishable from the probe.

| arm | `kvp_on` | `sys` ticks, 200 000 calls (HZ = 60) | mean | `vec32` delta |
|---|---|---|---|---|
| A1 | 1 | 1254, 1252, 1275 | 1260.33 | 203 264 / 201 550 / 201 550 |
| B | 0 | 1166, 1163, 1170 | 1166.33 | **0 / 0 / 0** |
| A2 | 1 | 1257, 1271, 1246 | 1258.00 | 202 108 / 201 552 / 200 193 |

* **The gate is complete.** With `kvp_on` = 0 neither `kvp_vec[32]` nor `kvp_vec[2]` moved at
  all — not "hardly", zero. The probe is entirely out of the path.
* **A2 returns to A1** within 2.33 ticks, 0.19%. The difference measured in B is the probe's.
* **The arms do not overlap.** The slowest A run (1246) is 76 ticks above the fastest B (1170).

```
probe on   104.9 us of system time per system call
probe off   97.2 us
cost         7.74 us per system call  =  7.37 % of system time
```

### And Dhrystone, as asked

| arm | Dhrystones/s | mean |
|---|---|---|
| A1 | 21201.4, 21261.5, 21261.5 | 21241.5 |
| B | 21231.4, 21216.4, 21201.4 | 21216.4 |
| A2 | 21201.4, 21141.6, 21216.4 | 21186.5 |

**B − A = +2.4 Dhrystones/s, +0.011 %** — and the arm with the probe *on* is nominally the
faster of the two. The within-A spread is 119.9 (0.57 %), and the A1 → A2 drift alone is −55,
twenty-three times the size of the A/B difference. Dhrystone cannot resolve this cost, and a
two-arm Dhrystone A/B would have reported "no measurable cost" with a straight face. That is
worth recording as a result about the instrument, not about the probe.

### What follows

7.4 % of system time on every system call and every page fault is material for what is a
debugging aid — the plan's own rule was *"if the cost is material the default flips to 0"*. That
flip is a one-word change to `src/kvecprobe040.s` and a new image, and it was **not** made in this
session; the flag can be taken out of the path live with `kpoke <kvp_on> 1 0` in the meantime,
which is exactly what this measurement did.

One number is not explained here and should not be quietly rounded away: 7.74 µs is about 193
cycles at 25 MHz, for a wrapper of roughly twenty instructions. The instruction count alone
predicts well under a microsecond. The five separate `.data` longwords it writes, on a copyback
data cache, are the obvious suspect — but that is a hypothesis, not a measurement, and nothing
here tests it.

## ISSUE-51: six burst rounds, in flight as this was written

`burstloop11.sh 6` was launched on the same boot: 6 rounds x 4 bursts x (6 concurrent 4 MiB
copies + `hat_dup_cow 64`), 144 checksums. The arithmetic was written down before the run,
because the result is easy to over-read:

> ISSUE-51's observed rate is 2 wrong sums in 288. At p = 0.0069 per sum, the chance of seeing
> **zero** events in 144 sums is `(1-p)^144 = 0.37`. A clean run is the more likely outcome even
> if the defect is exactly as frequent as before, and is therefore **not evidence against it**.
> What 144 clean sums buys is a tighter rate — 2/432 rather than 2/288.

A burst takes roughly eight minutes on this machine, so six rounds is about three hours and did
not finish inside the session. The log is `/tmp/burstloop11.log` on the guest and the summary
prints at the end; partial counts are `grep -c '1570 8192'` (expect 24 per completed round) and
the ten anomaly patterns the driver checks one at a time, because AMIX `grep` has no `\|`.

**Read the serial log too, not only the summary.** That is what caught ISSUE-57 on this same
boot, and the burst is also the discriminator for the Mercury-instability hypothesis: the same
load produced three unexplained events on the Mercury on 2026-08-29/30 and none on this A3640.

## What this does not establish

* **ISSUE-53 is not closed.** `a3w_eint_only` is still 0 after 203 912 level-2 interrupts. The
  instrument is in place and correct; the event has to arrive by itself.
* **WB1 is still unexercised** on both platforms. `wbf_slot` = 3 here as everywhere else.
* **The FPE lane was not run.** `build/unix-040-fpe` is `68040-260828-02` and is a different
  image; nothing here says anything about it.
* **`fp060probe` says nothing about the 68060 package.** It passes here through the *040*
  FPSP, and the whole point of the reading is that the 060 code was not entered — so it is a
  control for F3, not a test of it.
* **The six remaining `test-tools` programs that name a physical address have not been read.**
  ISSUE-57 lists them. Assume they carry the same defect until somebody checks.
