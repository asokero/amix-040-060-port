## 5. The fault, decomposed

**This section is post-hoc static analysis of data attempt 6 recorded.  It is not a scored row of
the attempt-6 pre-registration, and it is labelled as analysis wherever it is one.**  What it does
score is **attempt 5's Table F**, which was pre-registered in
`docs/060-F4-M2-ATT5-PREREG-260825.md` §4 and reported "NOT REACHED — no register file exists to
decompose".  The register file now exists.

### 5.1 FSLW `05011000`, decoded

The 68060 replaces the 68040's 16-bit SSW with a 32-bit fault status longword at frame+76.  The
field layout below is the architecture's; two independent things in reach corroborate it, and
both are consulted rather than one: this port's own decode masks (`src/wb040.s:404,555,589` reads
MA as bit 27 and the RW field as bits 24–23; `src/userspace040.s:91-92` and `src/ufault_dbg.s`
read TM as bits 18–16), and the MMU model in the emulator this project benches on, whose table
assigns the same three fields to the same bits and names the rest.  The port's own two recorded
FSLW samples check the map end to end: `docs/XPAGE-FPROT-FINDING-260806.md`'s `08810200` decodes
as MA set / RW = 01 write / TM = 001 user data / page fault, and
`docs/060-COUNTERS-UNIT-SPEC-260805.md`'s `01810200` as MA clear / RW = 11 locked RMW / TM = 001 /
page fault — which is exactly what both documents say they are.

`0x05011000` has four bits set: 26, 24, 16, 12.

| field | bits | value | reading |
|---|---|---|---|
| MA — misaligned | 27 | **0** | the transfer does not span two pages.  No XPAGE round-up applies |
| LK — locked | 25 | **0** | not a locked read-modify-write.  Not a `TAS`/`CAS` |
| RW | 24–23 | **10** | a **pure read**.  `TST` never writes memory, and the FSLW agrees |
| SIZE | 22–21 | **00** | **long** — a 4-byte access, which is what `tstl` issues |
| TT | 20–19 | **00** | a normal access, not `MOVE16` |
| TM | 18–16 | **001** | **user data.**  Not an instruction fetch, so no I-cache reading is admissible for this fault — attempt 5 §2.3's refutation of candidate (a) stands, now measured rather than argued |
| bit 26 | 26 | **1** | set, and **not consumed anywhere in this port**.  Reported as an undecoded bit rather than named; §5.6 registers the check that would settle it |
| PTA | 12 | **1** | **the root-level table descriptor for this address is invalid** |
| PF | 9 | **0** | **not** an ordinary page fault |

**PTA without PF is the sharp part, and it is quantitative.**  The 68060 table search fetches the
root descriptor indexed by address bits 31–23; an invalid one aborts the walk immediately and sets
PTA, while an invalid *leaf* descriptor sets PF instead.  `0x4AFC0008 >> 23 = 0x95`, so the root
entry that failed covers `[0x4A800000, 0x4B000000)`.  **Nothing in that 8 MiB window is mapped at
all in PID 1's address space** — this is not a resident-page miss inside a real mapping, and no
reading in which `0x4AFC0000` is a slightly-wrong pointer into live memory survives it.

`uft_f_brkbase 8000A15C` / `uft_f_brksize 00001000` put the break a gigabyte away, so the ISSUE-10
cure (`src/hgfault040.s`, a user *write* just past the break) is not this bug — the FSLW's RW = 10
alone settles that, and the break pair settles it again without argument.

### 5.2 The register file is named one longword low

`src/ufault_dbg.s` copies sixteen longwords from `u.u_ar0 + 0` into slots named `uft_f_d0..d7`,
`uft_f_a0..a7`.  Its model of the frame is `u_ar0+0 .. +63 = d0-d7 then a0-a7`.  **That model is
wrong by one longword**, and the same pre-registration that caught it in `src/srgtrap.s` (§2.3)
contains the proof.

`nullvect_orig` is entered by the CPU with the raw frame on `(sp)` and pushes `moveml %d0-%fp,%sp@-`
= d0–d7 then a0–a6 = 15 registers = **60 bytes**; its own `btst #5,%sp@(60)` counts them.  Then
`utraps` pushes the USP and the `jsr` pushes the return address.  Measured from the pushed-USP
slot: USP at +0, the 60 saved registers at +4..+63, SR at +64, PC at +66, format/vector at +70,
fault address at +72, FSLW at +76.

`u.u_ar0` is that USP slot, and the instrument's **own self-check proves it**, because the two
candidate bases disagree at the offsets it checks:

* `uft_f_fpc` reads `u_ar0+66` and must equal `uft_f_pc`, which comes from `cmn_err`'s argument at
  `%sp@(32)` — a completely independent source.  Both read `C1027EAA`.  Had `u_ar0` pointed at the
  d0 slot instead, a long read at +66 would have returned the format/vector word joined to the
  fault address (`0x40084AFC`), and the check would have failed.
* `uft_f_ffa` reads `u_ar0+72` and equals `uft_f_fa` from `%sp@(28)`.  Both read `4AFC0008`.

So the sixteen-longword copy stores the USP, then d0–d7, then a0–a6:

| slot as named | actually holds | attempt-6 value |
|---|---|---|
| `uft_f_d0` | **USP (user A7)** | `C07FFD64` |
| `uft_f_d1 .. uft_f_a0` | **d0 .. d7** | `00000001 FFFFFFFF 80000001 C07FFDF8 C07FFE46 00000000 00000001 0000000A` |
| `uft_f_a1 .. uft_f_a7` | **a0 .. a6** | `4AFC0000 C07FFE04 800013C8 800096F8 00000000 800096FB C07FFD74` |

Three independent confirmations, all from the same capture:

1. **`uft_f_d0` equals `uft_f_usp` to the digit.**  `uft_f_usp` is read from `%usp` by its own
   instruction, from a different source entirely.  Under the names as written, a data register
   holding the user stack pointer exactly is an unexplained coincidence; under the correction it
   is the identity it has to be.
2. **The faulting effective address composes exactly** — §5.3.
3. **a6 becomes a frame pointer.**  True a6 = `C07FFD74` = USP + 0x10.  Under the old names, a6
   would be `800096FB`, an *odd* address in another segment, and a7 would be `C07FFD74` ≠ the USP.
   The "`uft_f_a7 != uft_f_usp`" mismatch previously written off as a known-bad bench check **is
   this off-by-one, and it was the instrument saying so.**

`src/ufault_dbg.s`'s header now carries the correction.  **The code is deliberately not changed
and the slots are deliberately not renamed**: the values are right and only the names are wrong,
so every register file attempts 4, 5 and 6 recorded stays usable once re-labelled, whereas a
rename would silently re-interpret all of them.  The code-level fix is a round-7 decision, not a
change to slip into the commit that re-bases the lineage.

### 5.3 Attempt 5's Table F, scored

Attempt 5 §2.1 derived the faulting instruction from a copy of `libc.so.1` outside the metal work
root.  **It has now been read out of the work root that actually booted**
(`Amix/tmp/2026-08-25-blizzard-f4m2-att6/f4m2a6-work-root.hdf`), which is a stronger derivation
and is what the rest of this section rests on:

* the byte sequence `2054 4ab0 2e00` occurs **exactly once in the whole 100 MB image**;
* both of the image's symbol-table entries covering the fault offset resolve, through their own
  string tables, to the name **`hsearch`**, with `st_value = 0x27E26` and `st_size = 0x108`.
  `0xC1027EAA − 0xC1000000 = 0x27EAA` is **`hsearch+0x84`**, inside `[0x27E26, 0x27F2E)`;
* decoded, the three instructions ending at the fault are

```text
   moveal %a5@(0x0000068c),%a4     ; a4 = &table, fetched through the GOT at a5
   moveal %a4@,%a0                 ; a0 = table
   tstl   %a0@(0,%d2:l:8)          ; <== PC C1027EAA.  EA = a0 + d2*8, a 4-byte READ
```

`4ab0` is `TST.L` with an indexed effective address on `%a0`; extension `2e00` selects `%d2`, long
index, scale 8, zero displacement.  A `table[i]` probe with 8-byte entries — which is what an
`ENTRY { char *key; void *data; }` hash slot is.

Now Table F, whose rows were fixed before any register file existed:

| Table F row, as registered | as written (slot names) | as meant (architectural registers) |
|---|---|---|
| `uft_f_a0` = `4AFC0000` **and** `uft_f_d2` = `1` → **G1**, "the EA decomposes exactly as §2.1 predicts: libc's `table` pointer held the fabricated value and the probe index was 1.  Correct code, corrupt datum" | MISS — `uft_f_a0` = `0000000A`, `uft_f_d2` = `FFFFFFFF` | **HIT.**  a0 = `4AFC0000`; d2 = `80000001`, and `0x80000001 × 8 mod 2^32 = 8` |
| `uft_f_a0` = `4AFC0008` and `uft_f_d2` = `0` | MISS | MISS |
| any other register also reads `4AFC00nn` → "the value is being propagated rather than held in one place" | HIT on `uft_f_a1` | does not apply — `uft_f_a1` **is** a0 |

```text
  as written:   0x0000000A + 0xFFFFFFFF*8  =  0x00000002          — 0x4AFC0006 away from the fault address
  as meant:     0x4AFC0000 + 0x80000001*8  =  0x4AFC0008          — the fault address, exactly
```

**G1 fires**, with one refinement the row could not anticipate: `%d2` is not literally 1, it is
`0x80000001`, whose scale-8 product wraps to exactly 8.  The index has bit 31 set, so **`%d2` is
out of range for any hash table** and is a second implausible datum in the same register file.
Recorded; not explained.  The "propagated rather than held in one place" row does **not** fire —
`0x4AFC0000` appears in exactly one register, and that register is the `table` pointer.

### 5.4 Where the value was read from: user virtual address 0

The remaining register is the one that closes the chain.  **True a4 = `00000000`** — and two
instructions before the fault, `%a4` is dereferenced.

`docs/ISSUE10-SETUPSH-WALL-260819.md` §14.1 established, on the 040 lane and by reading four
images, that the byte string `33 fc 4a fc` — `MOVE.W #$4AFC,($00000000).L`, *store the `ILLEGAL`
opcode word at absolute address 0* — is **stock kernel code**.  Re-verified here against the
artifact this session actually booted, and against two others, each carrying it exactly once:

```text
  build/unix-060-f6vsm-CARD1-ced0s1   file offset 0x0073CC   33fc 4afc 0000 0000
  build/unix-040-f1-z3660             file offset 0x0073CC   33fc 4afc 0000 0000
  build/unix-030-i10d                 file offset 0x0073CC   33fc 4afc 0000 0000
```

So address 0 holds the word `0x4AFC`, and **a longword read at address 0 returns `0x4AFC0000`** —
the sentinel word followed by the zeros after it.  The chain is then complete and every measured
register is accounted for:

```text
  a4 = 0                                   the pointer that should have been &table is NULL
  moveal %a4@,%a0    reads address 0       LEGALLY, no fault -- and a0 becomes 0x4AFC0000
  tstl %a0@(0,%d2:l:8)  EA = 0x4AFC0008    root descriptor invalid -> PTA -> FLTBOUNDS -> the wall
```

**This is a fourth independent confirmation of §5.2's correction**, and the sharpest one: under
the slot names as written, a4 reads `800096F8`, the chain does not close, and `a4 = 0` — the one
value that explains where `0x4AFC0000` came from — is not in the register file at all.

Two things follow, and they matter more than the fault itself:

* **Nobody wrote `0x4AFC0000`.**  It was not stored, not copied and not fabricated; it was *read*,
  from address 0, and it is the kernel's own sentinel.  The genesis question as attempt 6 posed it
  — "which memory location held the fabricated value" — has the answer **user virtual address
  `0x00000000`**, and the ISSUE-10 §14.1 mechanism reproduces on the 68060 for the first time,
  from the register file rather than from an emulator watch.
* **The real defect is one hop upstream and it is a NULL, not a poison.**  The question round 7
  must ask is *what left `%a4` at zero* — and, standing behind it, why a stock kernel leaves user
  virtual address 0 readable with a value shaped like a pointer, which is what converts a clean
  NULL dereference into a wild pointer eight bytes into unmapped space.

That user VA 0 *was* readable in PID 1 on this rig is a deduction from the measurement rather than
an assumption: had it been unmapped, the `moveal` would have faulted at PC `0x27EA8` with fault
address `00000000`, and the recorded PC is `0x27EAA`.

### 5.5 The register set is wrong in more than one place, and that is the lead

Re-labelled, the frozen register file reads:

```text
  a7/USP C07FFD64   a6 C07FFD74 (= USP+0x10, a frame pointer)   a5 800096FB   a4 00000000
  a3 800096F8   a2 800013C8   a1 C07FFE04   a0 4AFC0000
  d0 00000001  d1 FFFFFFFF  d2 80000001  d3 C07FFDF8  d4 C07FFE46  d5 00000000
  d6 00000001  d7 0000000A
```

`%a5` is the GOT base — established here rather than assumed, because the instruction two before
the fault addresses `%a5@(0x68c)` with a full-format extension word whose index is suppressed, so
`%a5` is a plain base pointer into libc's own data.  A GOT base of `800096FB` is **odd-valued and
in `/sbin/init`'s data segment**, not in libc's.  So at the moment of the fault at least three
registers are implausible at once — `%a5` (odd, wrong segment), `%a4` (NULL), `%d2` (index with
bit 31 set) — while `%a6`, `%a7`, `%a1`, `%d3` and `%d4` are perfectly ordinary user-stack values.

**A multi-register corruption is a different animal from a single corrupt pointer**, and it points
at a path that writes many registers at once.  This kernel has exactly one such path in the signal
loop: `restorecontext`, which reloads the register file from a `ucontext` — the same object this
campaign has watched fail its checksum on every boot.  The checksum is a 201-longword XOR fold and
therefore **blind to any corruption that flips the same bit position in an even number of
longwords**, so "the guard would have caught it" is not an argument.  Registered as the leading
round-7 hypothesis with a discriminator that can refute it, in `…ATT7-PREREG…` §4 — **not claimed
here.**

### 5.6 What §5 does not establish

* **Not a cause.**  §5 says what the fault *was* and where the value came *from*.  It does not say
  what left `%a4` at zero, and nothing here names a mechanism for it.
* **Not a link to the `ucontext` failures.**  §5.5 is a hypothesis with a registered refutation
  test, and the only thing supporting it today is that several registers are wrong at once.
* **Sequential execution is assumed at one step.**  The chain in §5.4 assumes the `moveal` at
  `0x27EA8` ran immediately before the fault.  The bytes support it and nothing contradicts it,
  but `0x27EAA` could in principle be a branch target, in which case `%a0` was loaded elsewhere.
  Registered as a round-7 discriminator.
* **FSLW bit 26 is not decoded.**  It is set, this port consumes it nowhere, and it is reported as
  an undecoded bit.  Round 7 registers a check: if bit 26 is set on *every* fmt-4 frame this
  kernel ever records, it is not a property of this fault.
* **The instruction was identified, not disassembled in place.**  UFS block allocation means an
  image byte offset is not a file offset, so `hsearch`'s bytes were matched by content and by
  symbol table, not by walking the filesystem.  Uniqueness in 100 MB plus two symbol entries
  agreeing on name, value and size is what carries it.
* **`%d2 = 0x80000001` is recorded, not read.**  No claim is made about how a hash index acquired
  bit 31.

## 6. The swap slice is over-declared at its source, and the clamp cannot see it

**A proposal for other repositories, not a change made here.**

Measured: `va_size = 0x01E00000` (30 MiB) on three boots, against a `UNIX_Swap` slice of
18,874,368 bytes (18 MiB) in the work root's RDB, with `bo_offset = 0` and `bo_size = 0xF000`
static in the kernel image.  The clamp that exists to catch exactly this is

```text
  (bo_offset + bo_size) * 512 > va_size    ->  clamp nswap, print the WARNING
```

and `(0 + 0xF000) * 512 = 0x01E00000`, which is **equal to** `va_size`, not greater.  The test
compares the configured size against a device size that reports the same number, so **it can never
fire on this rig** — and did not, three times.

Two readings, and both are fixed by the same change:

1. the device-size report echoes the configuration, in which case the clamp compares a number with
   itself and is structurally blind; or
2. the slice really is declared as 30 MiB at its source — the RDB / `updbootpart` values the work
   root was built with — and coincidentally by exactly the configured amount.

The bench does not discriminate between them: its swap slice is 61,440 blocks, exactly equal to
the configured `bo_size`, so the strictly-greater test cannot fire there whatever `va_size` is.
**A rig whose slice size differs from the configured `bo_size` and whose root path is `a3091`
would discriminate, and costs no metal window.**

**Proposed, for the media-builder and build-harness repositories rather than for this one, because
it is a configuration question and not a kernel one:**

* derive the configured swap size from the partition table at install time instead of declaring it
  independently, so the two cannot disagree;
* keep the kernel-side clamp but add a boot-time cross-check that compares `bo_size` against the
  slice length the driver reports and **prints on disagreement in either direction**, since the
  present test is one-sided and silent when the numbers merely match.

**The hazard is real in configuration and was not exercised.**  61,440 configured blocks against a
36,864-block slice that is adjacent to `UNIX_Boot` with no gap, and `UNIX_Boot` is where the kernel
under test is installed.  Checked at close-out: boot 1's used disk was downloaded whole and its
boot-slice kernel re-hashed to `0d965ad5…8f45200`, **unchanged after a boot that ran the full
837-fault wall storm**, with 715 of the slice's 36,864 blocks non-zero — so swap was genuinely
used and got nowhere near block 36,864.  Recorded as a durability hazard that remains open, not as
one shown to be harmless.

## 7. Two base fixes absorbed — and THE DETERMINISM LINEAGE RE-BASES AT THIS COMMIT

Both were named in the attempt-6 pre-registration (§2.2, §2.3) and deliberately **not** fixed
there, for the reason that they are base changes and would move every artifact the 030 and 040
arms are compared against.  That reason has not gone away; it has been paid.

### 7.1 `src/kvecprobe040.s` — `kvp_super_n` was structurally dead

The S-bit test read `btst &5,%d1` — the **register** form, a long operand with the bit number
taken mod 32 — so it tested SR bit 5, which both CPUs define as zero.  The branch was never taken,
**every** entry landed in `kvp_user_n`, and attempt 5's and attempt 6's "all user" readings were
never measurements.  `nullvect_orig` itself gets this right with the memory form,
`btst #5,%sp@(60)`, where bit 5 addresses the S bit inside the SR's **high byte**.

Fixed to `btst &13,%d1`, which keeps the register form and corrects the bit number, so the
encoding stays four bytes and only the extension word moves.  Confirmed from the linked images —
one site, and only that site:

```text
  before   0801 0005 present at 0xda98e   0801 000d absent there
  after    0801 0005 GONE from 0xda98e    0801 000d present at 0xda98e
```

The other `0801 0005` sites in the image are stock code and are untouched.

**Every `kvp_super_n` reading in the campaign is void, not zero.**  Attempt 6's `kvp_super_n = 0`
was already reported as "not a measurement" and is not retroactively upgraded.

### 7.2 `src/srgtrap.s` — the ring's frame offsets, +60

The ring read the frame words sixty bytes low because it omitted `nullvect_orig`'s own 60-byte
register save.  Corrected to the layout the pre-registration re-derived, which is **not a
re-derivation on paper**: `src/kvecdisp040.s` hooks the same edge with the same layout and carries
three self-checks for it, and all three passed on the bench and on three metal boots.

```text
  srt_vec   %sp@(30) -> %sp@(90)     frame format/vector word
  srt_pc    %sp@(26) -> %sp@(86)     frame PC
  srt_usp   %sp@(20)  unchanged      the pushed USP was already right
  srt_d0    %sp@     -> %sp@(24)     user d0 -- nullvect_orig's LOWEST saved register.  %sp@ is
                                     OUR saved d0, which nullvect_orig had already overwritten
                                     with sup_cacr before this code ever ran
```

Confirmed in the linked image: `302f 005a`, `202f 0056`, `202f 0014`, `202f 0018`.  The unit grows
two bytes, and `.balign 4` rounds that to **four**.

**No result in this campaign rested on `srt_*`** — the ring was never reported in attempts 3, 4 or
5 — so nothing is retracted.  `srg_pushslot`, the one `srg` slot that *did* vary between boots
(§3.3), is computed arithmetically and is unaffected by this fix.

### 7.3 `tools/status-facts.sh` — COMMON counters, derived instead of remembered

`z3660_range_ovf` has **two** relocation sites; the bench sheet listed one, and metal read both and
required them to agree.  A hand-kept table that names one site where the file has two silently
turns off the agreement check that makes a COMMON reading trustworthy at all.

The tool now derives every COMMON symbol's `R_68K_32` sites from the ELF's own relocation
sections, so it structurally cannot list one site where there are two.  It reports 414 COMMON
symbols carrying 4,090 sites, 352 of them multi-site, and lists a selectable subset (default
`z3660 putbuf`, overridable with `AMIX_COMMON_SYMS`).  It reproduces every independently-known
value: `z3660_range_ovf` 2 sites at `0x0f5536` / `0x0f55a2`, `z3660_ci_ok` / `dtt0` / `dtt1` /
`direct_map` 3 each, `cacr` and `nest_hits` 2 each, and `putbuf` **6** — the count the session's
own message-buffer recovery derived independently (`05-DEVIATIONS.md` §1).

It also scans **`SHT_RELA`**, which is what this ELF carries.  A scanner that looks only for
`SHT_REL` reports "no relocation targets this symbol" and reads like an instrument defect — the
wrong intermediate analysis attempt 6 kept in its record (`05-DEVIATIONS.md` §4).

Recorded in `05-DEVIATIONS.md` and not paraphrased away:

1. **No HDMI capture all session.**  The KVM's streamer returned no frame; HID worked throughout

3. **Table L's baseline slot is read-time dependent** (§3.1).  Fixed by design in round 7.
4. **`dm2` prints 32 bytes per row** regardless of the requested length, so every "len 4" read in
   the dumps shows eight longwords.
5. **A serial capture was overwritten and recovered** from the live log at its recorded byte
   offset; nothing was lost, and the naming collision is recorded because it could have lost
   something.
6. **Operator error at close-out**: a `P` keypress sent while the SD file manager, a *line*
   reader, was the consumer, after `console_set_mode menu` was declared on stale evidence.  The
   guard allowed it because a single key is legal in the declared mode — **the guard was told a
   falsehood and acted on it correctly.**  Benign because `P` is benign and a line reader buffers
   rather than acts.  The lesson is that `console_set_mode` is only as good as its evidence
   string.

**The discarded run** is a first-of-a-kind and belongs to another lane: `[Core0] DataAbortHandler()`,
DFSR `0x00001c06` — an ARMv7 asynchronous/imprecise external abort on a write, taken inside an ARM
poll loop — and the board rebooted itself underneath the guest four seconds after the guest reset.
It fails one leg of attempt 5's three-proof discard test (it had one `Found no handler` line, not
zero) and that failure is recorded rather than waved through; it is discarded on the different and
stronger ground that the firmware terminated the guest.  Device CRC afterwards unchanged, so it
wrote nothing.  Explicitly **not** attributed to the kernel, the instruments or the 68060, and not
analysed here — it is Z3660-lane recon.  `Write Fault to 0x00000000` is **not** read as a
null-pointer store: for an asynchronous abort the DFAR is architecturally UNKNOWN.
