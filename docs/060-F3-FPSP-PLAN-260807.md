# F3 — a floating-point support package for the 68060: plan

**Written 2026-08-07.** Goal: make the 68060 execute the FP instructions it does not retire in
hardware, instead of killing the process with SIGSYS. Closes ISSUE-34b's FP half.

Baseline: `68060-260806-06`, hardware-accepted 2026-08-07 (`REALHW-260806-06-ACCEPTANCE.md`).

## 1. The measured basis

From `060-FPU-STATE-260807.md`, measured on real silicon one instruction per child:

```text
fadd fsqrt fintrz          survive      retired in hardware
fsin fetox flogn fmovecr   SIGSYS (12)  nothing handles them
```

Two facts set the scope:

* **`fmovecr` is the common case, not an exotic one.** It loads the FPU ROM constants (0.0, 1.0,
  π), gcc emits it for ordinary FP literals, and the campaign plan's userland scan counted **287
  occurrences** of it in installed binaries (`FScc`: 26). `x = 1.0;` is enough to die.
* **Transcendentals are also live.** `fsin`/`fetox`/`flogn` all trap, so a package that only fixes
  constant loading leaves libm-using programs dead.

Cause is not in doubt: `src/fpsp_glue040.s` gates every entry on `cmpl #40,cputype`, so on
an 060 the 68040 FPSP falls through to `nullvect` → SIGSYS.

## 2. What we already have

**Motorola's M68060 Software Package is on disk**, in the same NetBSD tarball the 040 FPSP came
from: `amix-playground/netbsd/syssrc.tgz`, path `usr/src/sys/arch/m68k/060sp/`. Contents that
matter:

| file | what it is | size |
|---|---|---|
| `dist/fpsp.sa` | full FP package: unimplemented instructions **and** data types **and** IEEE exceptions | **53 KiB** |
| `dist/pfpsp.sa` | partial: reduced module set, no transcendental emulation | 27 KiB |
| `dist/isp.sa` | integer package (F2 territory; we shipped a bespoke subset instead) | 6 KiB |
| `dist/fskeletn.s` | Motorola's example call-out section — the template for our glue | — |
| `dist/ftest.s` | **Motorola's own FP test suite** | — |
| `fnetbsd.S`, `netbsd060sp.S` | NetBSD's OS adaptation — a worked example, not our answer | — |
| `asm2gas`, `copyright.S` | the converter the 040 build already uses; licence notice that MUST be retained | — |

Kernel text today is `0xe4bb8` = 915 KiB, so the full package is **+5.8 %**.

And we have the precedent: `build-fpsp040.sh` + `src/fpsp_glue040.s` already solve this exact
problem for the 040, including the 12 OS callbacks and the `ld -r` packaging into a SysV kernel.

## 3. The one real architectural difference

**The 040 FPSP is symbol-based; the 060SP is address-based.** This is the main technical risk and
it changes packaging, not maths.

The 060SP is a binary image with three sections:

```text
   [ Call-Out section  ] 128 bytes, 32 x 4-byte fields, WE fill these in
   [ Entry-Point section] 8 bytes per entry, fixed offsets from the top
   [ Code section       ]
```

Callers do not link against symbols — they jump to a fixed offset:

```text
	bra	_060FPSP_TOP + 128 + 0x30	| F-line handler (vector 11)
```

Entry points (offsets from the start of the entry-point section):

| offset | entry | vector |
|---|---|---|
| 0x30 | `_060_fpsp_fline` | **11** — unimplemented FP instruction ← *what our measurement needs* |
| 0x38 | `_060_fpsp_unsupp` | 55 — unimplemented data type |
| 0x40 | `_060_fpsp_effadd` | 60 — unimplemented effective address |
| 0x00…0x28 | `snan, operr, ovfl, unfl, dz, inex` | 48–54 — IEEE exceptions |

Call-outs we must provide (32 slots, addresses **relative to the call-out section start**):
`_060_real_{bsun,snan,operr,ovfl,unfl,dz,inex,fline,fpu_disabled,trap,trace,access}`,
`_060_fpsp_done`, and the memory family `_060_{imem_read,dmem_read,dmem_write,imem_read_word,
imem_read_long,dmem_read_{byte,word,long},dmem_write_{byte,word,long}}`.

On AMIX these map onto machinery that already exists and is hardware-proven: the `real_*` slots go
to the stock `nullvect`/`u_trap` signal paths, `_060_fpsp_done` to `ureturn`, and the memory family
to `copyin`/`copyout`. `fpsp_glue040.s` already implements the equivalent twelve.

## 4. Vector map and gating

Current state (campaign plan §6): ISP owns 61; FPSP owns 11, 48–55, 60; our 040 hooks sit on 11,
48 and 51–55; 49, 50, 60, 61 are still `nullvect`.

F3 adds an 060 branch to the *existing* shims rather than a second vector table:

```text
fpsp_vec11:   cputype == 40 -> 040 FPSP        (unchanged, byte-identical)
              cputype == 60 -> _060_fpsp_fline (new)
              otherwise     -> nullvect        (unchanged)
```

Campaign rule 1 is binding: the 040 path must stay byte-identical, and both emulator CPU configs
must boot before any hardware boot.

## 5. Milestones

### M0 — the instrument, first

A `nullvect` probe: record the vector number, faulting PC and a count, in `.data`, before anything
else changes. Rationale, and it is not bureaucratic:

* We still **cannot attribute** any program's SIGSYS. `wolf3d`'s "bad system call" and the `xv` /
  X11R5 crashes are *consistent* with F3 and unproven, because SIGSYS also has a legitimate
  producer (a genuinely absent syscall). The probe settles those three symptoms directly.
* It is how every later milestone is judged: "the SIGSYS stopped" is only evidence if we know which
  vector was producing it.
* KNOWN-ISSUES already specifies this probe. It is small and CPU-independent.

*Acceptance:* on the 060, `fp060probe` moves the counter by exactly 4 and reports vector 11 for
`fsin/fetox/flogn/fmovecr`; running `wolf3d` and `xv` names their vector.

#### ✅ M0 DONE — `src/kvecprobe040.s`, kernel `68040/68060-260807-03`

Implemented by wrapping `nullvect` (`--weaken-symbol nullvect` + `nullvect_orig=.text:0x11b4`,
address asserted from both `build/unix-stage1` and vanilla `stand/unix`) rather than retargeting a
vector slot, so one override covers every vector. Not cputype-gated; gated on the `kvp_on` data
flag instead. Both emulator CPU configs boot clean.

**The acceptance number came out exactly as pre-registered.** Emulated 060, `kvp_vec[11]`:

```text
before fp060probe   0
after  fp060probe   4      fsin, fetox, flogn, fmovecr -- one each; fintrz survived and added none
```

That closes the inference chain: until now "`acomp` dies of vector 11" was deduced from the
`cputype` gate. It is now measured, per instruction.

**And M0 corrected a premise this plan was written on.** `nullvect` is **not** the
"unhandled vector" path its name suggests — it is the *shared exception entry*. Measured on the
emulated 040 at idle:

```text
vector 2   12 346    access fault
vector 32  26 552    TRAP #0 = system call
all others      0
```

Every syscall and every page fault passes through it. Consequences, both now baked into the
milestones below: "reached `nullvect`" is **not** a synonym for "will become SIGSYS", so F3's later
claims must be read off the per-vector bucket and never off `kvp_n`; and the probe sits on the
syscall path, which is why `kvp_on` exists. Cost not yet quantified — a Dhrystone A/B across
`kvp_on` would do it, and should be run before this ships on hardware.

⏳ Still owed from M0: run `wolf3d` and `xv` under the probe and read their vector. That is the
attribution the whole question started from, and it needs the RTG kernel rebuilt on this base.

### M1 — build the package body

`build-fpsp060.sh`, modelled on `build-fpsp040.sh`: convert with the same NetBSD `asm2gas`,
assemble with the GNU m68k toolchain, `ld -r` to one object, keep `copyright.S` linked in (licence
condition), and lay out `[128-byte call-out table][package image]` contiguously.

*Acceptance:* object builds; `m68k-cbm-sysv4-ld -r` accepts it; **the entry-point offsets are
verified by disassembling the entry table**, not assumed; measured text growth reported.

**Also decided here, by measurement rather than argument:** build `pfpsp.sa` as well and run
`fp060probe` against both. The probe already distinguishes them — whichever variant makes
`fmovecr` *and* `fsin/fetox/flogn` survive is the one we ship. Expectation: the full `fpsp.sa`,
since `pfpsp` drops the transcendental modules.

#### ✅ M1 DONE — `build-fpsp060.sh`

```text
build/fpsp060.o    .text 0xd490 = 54 416 bytes   full package
build/pfpsp060.o   .text 0x6c20 = 27 680 bytes   partial
```

Both assemble straight from the NetBSD tree with no `asm2gas` step: `fpsp.S`/`pfpsp.S` are already
the `.sa` hex image in GNU/MIT syntax. `copyright.S` is linked in (licence condition).

Assertions, all passing and all re-checked on every build rather than trusted once:

* **the nine entry points are decoded from the linked `.text`, not read from the document** —
  each slot must be a `bra.l` (`60ff`) whose target lands inside the image, with `0x51fc`
  (`trapf`) filler at `0x48`. This is the plan's risk 1, and it is now a build-time assertion.
* **image linked FIRST, `copyright.S` after.** Anything ahead of the image silently moves every
  entry point, and a wrong offset does not fail to link — it jumps into the middle of the package.
* **zero unresolved symbols**, and none defined. This is the structural difference from the 040
  package (which leaves exactly 12 for the linker): the 060 package finds its OS call-outs through
  the run-time table, so the linker has nothing to bind. It also means the object cannot be
  sanity-checked by symbol name — the offset decode above is the only check there is.
* `m68k-cbm-sysv4-ld -r` accepts both objects, so the kernel relink can consume them.

**Noted for D2:** the entry-point table is *byte-identical* between the two variants — same nine
targets. So `pfpsp` answers the same entries and differs only in what those handlers can do
internally. D2 therefore cannot be settled by inspecting the table; it needs `fp060probe` against
each, exactly as planned.

Offsets for M2, from the TOP of the call-out section: vector 11 → `TOP+128+0x30`,
vector 55 → `+0x38`, vector 60 → `+0x40`, vectors 48–54 → `+0x00…+0x28`.

### M2 — glue and the vector-11 hook

#### Architecture settled 2026-08-07, and one assumption killed

The plan above assumed the call-out table could be a separate object placed before the image.
Two bench checks changed the shape:

* **`.incbin` is not supported by the SysV4 assembler** (`Error: Unknown pseudo-op: .incbin`),
  so the image cannot be pulled into a hand-written glue file that way. Tested before designing
  around it.
* **Cross-object symbol arithmetic will not do either.** The table entries are *differences*
  (`stub - TOP`), and a difference between two symbols is only a link-time constant when both are
  in the same assembly unit.

So the package is built as **one GNU-assembled source, concatenated in this order**:

```text
  [ call-out table   ]  32 x .long  (stub - fpsp060_top)   <- src/fpsp060_head.s
  [ package image    ]  060sp/fpsp.S verbatim
  [ AMIX call-outs   ]  the stubs the table points at      <- src/fpsp060_glue.s
  [ vector-11 shim   ]  jmp fpsp060_top+128+0x30
```

assembled with `m68k-linux-gnu-gcc` exactly as the FPSP body already is, and consumed by the
kernel relink through `m68k-cbm-sysv4-ld -r` — the path `build-fpsp040.sh` already proves.
The stubs go *after* the image; only the 128-byte table may precede it.

Verified on the bench with a throwaway build of exactly this shape:

```text
fpsp060_top       0x00
fpsp060_image     0x80          <- table is exactly 128 bytes, image immediately after
table slot 0      0x0000d510    <- relative address of a stub past the image; arithmetic works
TOP+128+0x30      60ff -> image+0x1b8c   _060_fpsp_fline
TOP+128+0x38      60ff -> image+0x00668  _060_fpsp_unsupp
```

#### Call-out contract, from NetBSD's implementation

Documented nowhere in `fpsp.doc`; read out of `netbsd060sp.S`:

```text
_060_imem_read_long / _060_dmem_read_long
  INPUTS   a0 = user address;  a6@(0x4) bit5:  1 = supervisor, 0 = user
  OUTPUTS  d0 = data;  d1 = 0 success, non-zero failure
```

The user-mode side is a `moves` under a fault-handler landing pad — on AMIX that is the
`u_nofault` convention `Lwb_do` in `wb040.s` already uses, so this is a solved problem here.

The `_060_real_*` slots are exception **exit points**, not functions: they are reached with the
frame on the stack and end in `rte`. AMIX routes them to the stock `nullvect` path, counted, so
no new signal policy enters with this unit.

#### Staging

**M2a** — packaging and reachability only: the table, the image, a counted decline stub for every
call-out, and the `cputype == 60` branch in `fpsp_vec11`. Pre-registered: `kvp_vec[11]` stops
moving across `fp060probe` and an `f60_entry_n` counter moves by 4 instead. That proves the
offset wiring — M1's risk 1 — before a single accessor is written.

**M2b** — the real call-outs: the 11-strong memory family and the `real_*` exits.

#### ⚠ M2a BUILT AND RUN — wiring proven, and it panics. Kernel `68040/68060-260807-04`

Built: `src/fpsp060_head.s` + `060sp/fpsp.S` + `src/fpsp060_glue.s` concatenated by
`build-fpsp060.sh` into `build/fpsp060_pkg.o`, linked in the FPSP block, with `fpsp_vec11` gaining
a `cputype == 60` branch. textsize `0xe4c24` → `0xf2210` (+54 764 B). Assertions in the build:
`fpsp060_top` at 0, `fpsp060_image` at 0x80, all 32 call-out slots inside the object, the three
entry points decoding as `bra.l` into the image, only `nullvect` unresolved.

**What is proven:**

* **The gate holds.** The emulated 040 boots clean on this same image and reaches login. The
  failure is confined to the 060 path — which is the campaign's rule 1, demonstrated rather than
  asserted.
* **The wiring is reached.** On the emulated 060, `fp060probe` produces a kernel panic whose PC is
  *inside the package*, so vector 11 does now enter it instead of falling through to `nullvect`.

**The failure, in full:**

```text
PANIC: KERNEL FAULT psw=0x2004, pc=0x80E6C6E, fmt=0x2, vector=0x6 (CHK, CHK2)
proc = 4022EC00 (pid 213, fp060probe)
PC = fpsp060_image + 0x1fb6
```

Disassembling the package at that offset shows **data, not code** — `chkl %fp@+,%d5` followed by
`.short 0x4b4c`, `.short 0x4f4c` and nonsense addressing modes. So control flow left the rails and
ran into a constant table; the CHK is what executing data happened to hit, not a real bounds check.

**Leading hypothesis, and it is a defect in my stubs rather than in Motorola's package:**
`Lco_access` and the eleven `_060_real_*` stubs end in `jmp nullvect`. `nullvect` is entered by the
CPU with a **raw exception frame at (sp)** — it immediately saves 60 bytes and reads the frame at
`sp@(60)`. By the time a call-out runs, the stack holds the *package's* frame, not a fresh
exception frame, so `nullvect` dispatches on garbage. M2a's memory stubs deliberately fail closed
(`d1 != 0`), which is precisely the path that drives the package into `_060_real_access` — so the
stub design guarantees this on the first trapping instruction.

Untested alternatives, recorded rather than pursued: the 040 path sets CACR from `sup_cacr` before
entering its package and the 060 branch does not; and the call-out contract's `a6@(0x4)` implies an
`a6` frame the package builds itself, which nothing verifies yet.

**Consequence for M2b:** the `real_*` exits cannot simply be forwarded to `nullvect`. They need
either a synthesized exception frame or a different return path — and that is a contract question
worth answering from `fskeletn.s` and NetBSD's `fnetbsd.S` before more code is written.

> ⚠ **The leading hypothesis above was WRONG, and it is left standing on purpose.** Codex's static
> reading (2026-08-08) showed the terminal call-outs are tail transfers that leave a *valid raw
> exception frame* at `(sp)`, so `jmp nullvect` was structurally right all along. The panic was
> earlier: the first `_imem_read_long` in `_fpsp_unimp` is never `d1`-tested, so the fail-closed
> stub fed the package a zero opword and it executed its own dispatch table. Recording the refuted
> hypothesis is the rule (`feedback-attribution-and-instruments`) — and the cost of guessing here
> was one whole milestone aimed at the wrong half of the problem.

**Escape hatch, already in place:** `FPSP060=0 sh relink-040.sh` leaves the 060 on the old SIGSYS
path, so a working 060 kernel is one environment variable away.

`src/fpsp_glue060.s`: the 32 call-out slots plus the `cputype == 60` branch in `fpsp_vec11`.
Counters in the F2 style: entry count, per-entry-point counts, and a **counted, state-preserving
fallback** to `nullvect` for anything the package declines — never a partial decode, never a silent
approximation.

#### ✅ M2b DONE -- the real call-outs.  Kernel `68040/68060-260807-09`

Written from Codex's static contract (`amix-kernel-analysis` vm-map/F3-FPSP060-CALLOUT-CONTRACT.md,
1868bdf), which corrected the M2a post-mortem above on the one point that mattered:

> the panic was **not** in the `real_*` exits. `_fpsp_unimp` fetches the faulting opword with
> `bsr _imem_read_long` and **does not test `d1`**. M2a's decline stub returned `d0=0,d1=1`, the
> package decoded the zero opword and `jsr`ed into `tbl_trans` as code. Measured PC
> `fpsp060_image+0x1fb6` = `tbl_trans+0x24`, to the byte.

So "fail every memory call-out" was never a supported package mode, and M2b's shape follows:

* **memory family, for real** -- `copyin`/`copyout` for user origin (the primitive `isp61_060.s`
  already fetches user instruction words with, and which owns function codes, address validation
  and the nofault pad, so this file cannot repeat ISSUE-22), direct access for supervisor.
* **terminal exits, per class rather than uniformly.** The six arithmetic exits and BSUN get
  Motorola/NetBSD's FP pending-state prelude before the signal path, or the OS inherits an
  unhandled pending condition and the `rte` at the end re-traps forever. F-line/trap/trace/access
  tail into `nullvect` with the package's own raw frame -- AMIX must not build a second one.
* **`_060_fpsp_done` returns through `ureturn`**, never a bare `rte`: the `fpsp_glue040.s` /
  `isp61_060.s` shape, so qrun, signals, stack-frame adjustment and the user CACR all run.
* **`sup_cacr` installed at the vector entry**, which M2a omitted -- the 060 branch bypasses
  `nullvect`, so without it the package and every `copyin` it makes ran under the *user* cache mode.
* **no register clobber on an exit.** M2a's `moveq #slot,%d0` overwrote the restored *user* d0;
  the slot id is now an immediate written straight to memory.

**Full emulator acceptance, both CPUs, one image:
`test-tools/f3-m2b-emu-verify-260808.txt`.** Headlines:

```text
emu-060  fp060probe 7/7 bit-exact (0 ulp) incl. fmovecr = pi
         f60 entry 4 / mem 4 / done 4 / real 0 / access 0 / memfail 0;  kvp_vec[11] 0
         fputest060 fork runs to completion -- it used to die before its first printf
         battery 11/11
emu-040  fp060probe 7/7 bit-exact via the 040 package -- the two packages agree to the bit
         battery 11/11, and EVERY f60_* counter still 0
```

The probe was extended for this: it now returns the result through a pipe and compares the
IEEE-754 bit pattern, and the parent never touches a double. Survival is not correctness.

**D2 is settled, by measurement.** `FPSP060_VARIANT=pfpsp` (new switch) on the emulated 060:
`fsin/fetox/flogn/fmovecr` all SIGSYS again, with `f60_entry_n 4 / f60_mem_n 0 / f60_fline_n 4` --
the partial package *is* entered and declines through `_060_real_fline` without ever fetching the
instruction. Byte-exactly Codex's static prediction. **Ship the full `fpsp.sa`.**

**Motorola's `ftest` is built and runs** (`build-ftest060.sh`, which also does the `.sa` -> GNU
conversion NetBSD never did for this file), and its "1 failed" is **not** ours:
`test-tools/ftunimp0.c` replicates sub-test 1 exactly and every field the suite compares is
correct -- fp0 to all 96 bits, FPSR `0x08000208`, FPIAR, CCR, all 15 integer registers. What
fails is upstream: `fmovm.x DEF_FPREGS,&0xff` loads the extended NaN `7FFF0000 FFFFFFFF FFFFFFFF`
into all eight FP registers and reads back `3FFF0000 00000000 00000000` **before any trap**. The
emulated FPU cannot hold it, every sub-test starts with that load, so ftest cannot pass under
Amiberry whatever the FPSP does. Its verdict is owed from silicon.

Also unmeasured, and recorded rather than glossed: the six **enabled** FP exception exits.
`f60_arith_n` stayed 0 through ftest's enabled suite -- the emulated FPU never raised one, so
those exits have never executed.

**`FPSP060` now defaults to 1.** The rebuilt default image differs from the accepted one in
exactly two bytes, both build-id digits. `FPSP060=0` remains the one-variable escape hatch.
**M5 (hardware) is still owed.**

*Acceptance, pre-registered:*
* `fp060probe`: all seven survive, and `fmovecr` returns the correct constant (the probe must be
  extended to check the *value*, not just survival — survival is not correctness, the lesson from
  `protfault`);
* `fputest060 fork` (Test C) **runs to completion** — it currently dies before its first `printf`,

* the 040 path byte-identical: emu-040 battery unchanged and every 060 counter still 0.

Full run list, as for `-06`: identity, `fp060probe`, `ftest`, battery, burst, and the power-cut

## 6. Decisions, with recommendations

**D1 — Motorola's package, or a bespoke emulator like F2?** → **Motorola's.**
F2 wrote its own vector-61 handler, and that was right *there*: the arithmetic already existed and
was validated (`lmul060.s`, 202 500 cases), and exactly one instruction form covered the whole
installed compiler. Neither holds here. The maths is transcendental-function emulation, which is
the part not to hand-roll, and Motorola ships a test suite for it. Keep bespoke as the fallback if
M1 shows the package cannot be linked or does not fit.

**D2 — full `fpsp.sa` (53 KiB) or `pfpsp.sa` (27 KiB)?** → decide in M1 **by running `fp060probe`
against both**, not by reading module lists. Expectation is the full package, because the measured
failures include transcendentals.

**D3 — where do the `real_*` call-outs land?** → the existing stock signal paths, exactly as
`fpsp_glue040.s` does. No new signal policy in this unit.

## 7. Risks

1. **Address-based interface.** A wrong offset jumps into the middle of the package. Mitigation:
   M1 verifies every entry offset by disassembly, and M2's counters must show each entry point
   being reached before any behavioural claim.
2. **Size.** +5.8 % kernel text. Mitigation: measured in M1; `pfpsp` is the fallback if it matters,
   at the cost of transcendentals.
3. **No 68040 in the machine.** Any regression of the 040 path can only be checked in the emulator.
   Mitigation: the 040 path is not touched — the gate is additive — and this is asserted by
   counters, not by inspection.
4. **`ftest.s` may need the same treatment as `fputest`**: it is Motorola assembly for their
   syntax, and the guest's own compilers are the thing under test. Cross-assemble it.

## 8. Not in scope

* ISSUE-42 (`wb040_replay` fault propagation) — separate, and 040-only.
* The 060SP **integer** package: F2's bespoke unit covers the measured userland. Replacing it with
  `isp.sa` is a later cleanup, not this unit.
* `FScc` (26 occurrences): note it, measure it in M0/M1, act only if it traps.
