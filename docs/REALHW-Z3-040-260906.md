# Zorro III on a 68040, first run — 2026-09-06, `68040-260906-06`

The Zorro III graphics track was developed and accepted on a 68060 on 2026-08-19
(`docs/REALHW-Z3-VA2000-ACCEPTANCE-260819.md`). This is its first run on a 68040, and the reason
it needed a new kernel first is ISSUE-64: the combined RTG build script had never carried the
Zorro III define, so every kernel built by it since 2026-08-19 shipped the pre-Zorro-III driver.
That defect and its acceptance are in `KNOWN-ISSUES.md`; this document holds the measurements.

## Configuration, from the loader's own census rather than from a tool

```
board[0] mfg=0202 prod=70 addr=00e90000 size=00010000    A2065        Zorro II
board[1] mfg=4231 prod=01 addr=00ea0000 size=00010000    Prelude      Zorro II
board[2] mfg=6d6e prod=01 addr=40000000 size=02000000    VA2000       ZORRO III, 32 MB
mem[0] lower=08000020 upper=0a000000     32 MB  accelerator's own RAM
mem[1] lower=07000020 upper=08000000     16 MB  motherboard
kernel: entry=08000000 tvaddr=08000000 tsize=000ff9d8 dvaddr=080ff9d8
```

**No Piccolo**, which is why the VA2000 has the first Zorro III slot and sits at `0x40000000`
rather than the `0x42000000` of the 2026-08-19 configuration. Load base `0x08000000`, read from
the loader and not assumed. Identity confirmed by reading four magic words back at addresses
computed from the artifact, then by the battery's full 38.

`/lszorro` on the guest reported **eighteen** boards on this machine, several with kernel `.data`
addresses as their base. It is wrong. The loader census above is the instrument.

## `Lcm_fb` on a 68040 — measured in isolation, before X ran

The 68040's data cache is in copyback here, and change D's framebuffer classification had never
run on this CPU. `cmfcensus` reads the live leaf PTE, one page at a time, with X stopped:

```
CMF registered intervals: [40010,42000) [00000,00000)
CMF +00010000  FB   events +1  pte 40010069  pfn 40010  NC  noncacheable, not serialised
CMF +01fff000  FB   events +1  pte 41fff069  pfn 41fff  NC  noncacheable, not serialised
CMF +00000000  DEV  events +1  pte 40000049  pfn 40000  NCS noncacheable SERIALISED
CMF-DONE ok=3 bad=0
```

Predicted before the run, in `[pfn 0x40010, 0x42000)` from a 32 MB aperture at `0x40000000`, and
all three lines came out as predicted. **The register page lands in a different class from the two
framebuffer pages**, which is what proves the interval is consulted rather than that a constant
happens to be right. The last page of the aperture resolves to pfn `0x41fff`, so the whole 32 MB
window is addressable.

## The bandwidth, and the first Zorro III figures for this CPU

`busbench`, 1 MB default size, framebuffer offset `0x10000`, local-RAM reference taken in the same
session because absolute numbers do not compare across sessions. `/tmp/BENCH-LOCK` held.

| | write32 | write16 | read32 |
|---|---|---|---|
| local RAM (this session's reference) | 21.52 MB/s | 14.33 | 24.75 |
| **VA2000, Zorro III, on the 68040** | **7.14 MB/s** | **3.90** | **6.75** |
| aperture vs local | 3.01× below | 3.67× | 3.67× |

**Width discriminator: `7314 / 4002 = 1.83×`.** A long moves nearly twice the bytes of a word, so
this is a 32-bit datapath being used and not merely a faster one — the same test the 68060 run
passed at 1.86×.

### Against the 68060, and the interesting part is which number moved

| | 68060, 2026-08-19 | 68040, today |
|---|---|---|
| local RAM write32 | 25.91 MB/s | 21.52 MB/s (83 % of it) |
| Zorro III write32 | 7.66 MB/s | **7.14 MB/s (93 % of it)** |
| aperture vs local | 3.38× below | 3.01× below |
| width discriminator | 1.86× | 1.83× |

The 68040 reaches 83 % of the 68060's local-RAM figure but **93 % of its aperture figure**, and
ends up proportionally closer to its own local RAM. That is what a **bus-limited** path looks like:
the aperture is not waiting for this CPU. It is the first direct evidence on that question, because
until today every Zorro III number came from one processor.

⚠ Same qualification as the 2026-08-19 record, and added there on the same day as this run: the
Zorro II baseline of 3.12 MB/s was taken **before** change D, at `CM=0x40` serialised, and every
Zorro III figure including this one is at `CM=0x60` not serialised. The `busbench` note that
asserted comparability was written sixteen minutes before change D landed and has now been
corrected in the tool. The width discriminator is a within-run ratio and is unaffected; the
Zorro-II-to-Zorro-III *gain* carries two variables and cannot be attributed to the bus alone.

## ISSUE-58: the all-ones `ISTR` read does not happen here

First measurement of ISSUE-58's counters in a bootable kernel, and it is a negative with the
coverage to mean something. `a3w_ran` reads `A3WR`, so the wrapper ran:

| counter | value |
|---|---|
| `a3w_calls` (every level-2 interrupt) | 54 662 |
| `a3w_own` (INT_P set at entry) | 10 484 |
| `a3w_ints_only` | 10 484 |
| `a3w_or_istr` (OR of every snapshot) | `0xfed3` |
| **`a3w_allones` / `_re` / `_reff` / `_pr`** | **0 / 0 / 0 / 0** |

On the 68060 the all-ones read occurred once in every 726 interrupts. At that rate 54 662
interrupts would have produced about 75 of them. **Zero occurred.** `a3w_or_istr = 0xfed3` shows
bits 15–9 floating as the record says they do on hardware, so the register is being read and the
high bits are live — they simply never all came back set. That makes the all-ones read look like a
property of the 68060 side rather than of the A3091 or of the demux code, which is one more
anomaly that sorts with the open hardware question rather than against it.

**ISSUE-53 is unchanged and still open**: `a3w_eint_only = 0` and `a3w_eint_acked = 0` over those
54 662 interrupts. ISSUE-54's Stage D counters are all zero because no CD access was made — an
untested path, reported as untested.

## Dhrystone: the 68040 baseline reproduced to 0.03 %

`echo 1000000 | /root/amix-bench/dhry` → **30 045.1 /s**.

The recorded 68040 copyback cluster is 29 813.7 / 30 000.0 / 30 037 / 30 037.5
(`docs/REALHW-COPYBACK-ACCEPTANCE-260730.md`), against a write-through baseline of 18 292.7. Today's
figure sits at the top of that cluster, 0.03 % above its highest member and inside its 0.75 %
spread — six weeks and a great deal of change later. As a machine-health reading that is worth as
much as it is as a performance reading.

⚠ **Do not divide this by 916.1.** That ruler converts Dhrystones to MHz and was calibrated on
**68060s** (55.5 against a true 56, 51.1 against a true 52), at one clock, 66 MHz. The same
document that records it also records that the 68060 is only 7.1 % faster per clock than the 68040
on this benchmark — which is exactly why the constant cannot be carried across CPUs without
recalibration. `30045.1 / 916.1 = 32.8` is not this machine's clock; it is a category error.

## What still fails, and it is not ISSUE-64

`/usr/bin/X11/Xrtg :0` on this kernel still dies in a `kstack` cascade. That is **ISSUE-65**, and
it was diagnosed the same evening by booting the escalation kernel `68040-260906-07` and letting
KSTKCHAIN capture the recursion: the 68040's byte-wise write-back replay (`Lwb_loop`, our own
`src/wb040.s`) takes a bus error on the VA2000's **register** page, `hardbus` returns 0 = retry,
and the retry never terminates. The full reading is in `KNOWN-ISSUES.md` under ISSUE-65.

It matters for *this* document that the failure is not in the Zorro III path measured above.
`wb040.s` is gated by the format-7 access-error frame and therefore runs only on a 68040, so the
2026-08-19 acceptance could not have met it; and the page it dies on is pfn `0x40000`, the register
window, which is outside the registered framebuffer interval and is classified `CM=0x40` NCS
exactly as `cmfcensus` said it should be. The framebuffer path, the classification and the
bandwidth are unaffected by it.

So the honest summary of the day: the Zorro III path itself is proven on a 68040 — the board is
reachable, the classification is right, the aperture is fully addressable, and the bandwidth is
bus-limited rather than CPU-limited. **The X server on top of it is not.**

## Postscript, the same evening: ISSUE-65 is now survivable

ISSUE-47's guard was written, built and hardware-accepted after this document's measurements, on
`68040-260906-12`. Starting Xrtg on that kernel still fails — ISSUE-65 is not fixed — but it now
kills the server and leaves the machine running, instead of recursing through the u-area kernel
stack into a panic. `hbu_n = 1`, `wbf_signal_n = 1`, `wbf_alien_n = 0`, battery 12/12, 39/39 magics.
The full reading is in `KNOWN-ISSUES.md` under ISSUE-47.

That changes the economics of everything above: a Zorro III experiment on this machine no longer
costs a boot when it goes wrong.

## 2026-09-07: Xrtg runs

ISSUE-65 was fixed the next day and hardware-accepted on `68040-260907-04`: the write-back replay
now reissues a normal write-back with one `MOVES` of its recorded size instead of decomposing it
into bytes, so the aligned 16-bit register write that killed the server reaches the board as a
16-bit write. `va2000InitHW: done OK`, `InitOutput: done`, `InitInput: done`, and the server reports
**32704 KB on bus Zorro III**.

That closes the gap this document opened. Everything measured above — the classification, the
bandwidth, the full 32 MB aperture — was the Zorro III path working while the X server on top of it
did not. Both now do, on a 68040, for the first time.

The bandwidth figures are unchanged by the fix and were not re-measured; nothing in the replay path
is on `busbench`'s access path.
