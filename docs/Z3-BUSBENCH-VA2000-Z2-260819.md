# The VA2000's own Zorro II baseline — the number Zorro III has to beat

**Machine:** Amiga 3000, Mercury 68060 @ 66 MHz, MNT VA2000, Zorro II firmware 1.9.0
**Image:** `68060-260819-02` (`unix-040-va2000-dbg`, carrying changes A/B/C)
**Date:** 2026-08-19
**Why:** `docs/Z3-BUSBENCH-Z2-MEASUREMENT-260810.md` measured the **Piccolo**, and said so. A
Zorro III comparison has to be the same card through the same tool on the same machine, so the
VA2000 needed its own Zorro II number before the firmware moves.

## Measured

`busbench -r` first, because the tool refuses to be read without it.

| | write32 | write16 | read32 |
|---|---|---|---|
| local RAM reference | 26.66 MB/s | 17.37 | 26.33 |
| **VA2000 aperture, Zorro II** | **3.12 MB/s** | **2.78** | **3.71** |
| ratio | 8.5× | 6.2× | 7.1× |

Mapped at `c1033000` — outside DTT0, so the cache class came from the leaf PTE: `CM=0x40` NCS,
the same class the Piccolo run got. The two Zorro II measurements are therefore comparable to
each other.

## Reading it with the tool's own pre-stated discriminator

`busbench.c` states, before any number exists, that on a 16-bit Zorro II port a 32-bit access
costs two bus cycles but is one CPU access — so if per-access overhead dominated, `long` would
move about 2× the bytes of `word`, and only if bus cycles dominate do they come out equal.

Measured: **write32 3200 KB/s vs write16 2853 KB/s = 1.12×**, not 2×.

Same verdict as the Piccolo: **the bus is saturated**, not the access rate. The VA2000's Zorro II
aperture has nothing left to give, and **3.12 MB/s write32 is the number the Zorro III run must
beat.**

## Against the Piccolo, 2026-08-10

| | write32 | write16 | read32 |
|---|---|---|---|
| Piccolo, Z2 | 3.09 | 2.95 | 3.08 |
| VA2000, Z2 | 3.12 | 2.78 | **3.71** |

Writes are the same card-to-card, which is what a saturated shared bus predicts. Reads are 20 %
faster on the VA2000. Not chased further: it does not change the conclusion, and a second Z2 data
point agreeing on the writes is what this run was for.

## A discrepancy that must not be swept up: the reference itself moved

The local-RAM reference is **7–20 % below** the 2026-08-10 figures (28.66 / 21.59 / 31.33) on the
same machine and the same CPU. It is **not noise**: an immediate repeat reproduced it to within
0.2 % (26.66 / 17.33 / 26.33).

Not attributed. The plausible causes, in order, are that this image is built on the **debug** base
(`unix-040-dbg`) while `68060-260809-03` was not, that a cache-configuration global differs, or
something about machine state. Deciding it needs a non-debug VA2000 build and another boot, and
it was not worth spending hardware time on today.

Two consequences, and they are the reason this is written down rather than left as a footnote:

1. **Absolute busbench numbers do not compare across sessions or images.** The ratio to a
   same-session `-r` is the comparable quantity. This is exactly why the tool demands `-r` first.
2. **The Zorro III run must carry its own `-r`,** and should ideally be on the same image family as
   this one. Comparing a Zorro III number against the 3.12 MB/s above without a fresh reference
   would be the same mistake in the other direction.

## A correction made to the instrument itself

`busbench.c`'s header said the VA2000 at a Zorro II address takes `CM=0x60` NC through DTT0, and
its footer printed that claim on **every run**. It is wrong for this program: `busbench` uses
`mmap`, the mapping lands at `c1xxxxxx`, far outside DTT0's `0x00000000-0x3FFFFFFF`, and the class
comes from the leaf PTE — `Lcm_sel` gives every `pp == NULL` mapping `0x40` NCS. The 2026-08-10
document had already corrected this for the Piccolo; the tool had not been updated, so it kept
telling every future reader the opposite.

Both are now fixed, and the corrected note says the useful thing instead: Zorro II and Zorro III
apertures are both measured serialised here, so they are comparable **to each other** — what is
not comparable is either of them against a kernel-side `cd_BoardAddr` access, which on Zorro II
does get the friendlier `0x60`.

## Context: this image is the one carrying changes A/B/C

X11, wolf3d and Quake were all started on the VA2000 on this image and worked. Together with
`docs/REALHW-Z3-CHANGE-A-260819.md` that closes the Zorro II half of the plan: the driver is
address-agnostic, its registers are reached through a kernel mapping with an explicit cache class,
and nothing about the Zorro II behaviour regressed.
