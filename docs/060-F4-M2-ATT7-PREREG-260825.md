2026-08-25.  Follows `docs/060-F4-M2-ATT6-RESULTS-260825.md` and scores nothing that document
already scored.

**The honest sequence, since it is the only thing that makes a pre-registration worth anything.**

the artifact attempt 6 actually booted — and on the work-root image attempt 6 actually ran from.
**No instrument code exists for this round yet, and this document is committed before any is

## 2. FSLW `05011000`, and the two bits round 7 checks

The full decode is `…ATT6-RESULTS…` §5.1 and is not repeated.  The load-bearing readings:
**RW = 10, a pure read**; **SIZE = 00, long**; **TM = 001, user data**; **MA = 0**, so no page
crossing; **LK = 0**, so not a locked RMW; **PTA set with PF clear**, so the fault aborted at the
**root** level of the table search — `0x4AFC0008 >> 23 = 0x95`, and nothing in that 8 MiB window
is mapped at all in PID 1.

Two things about that decode are not yet measurements, and both are cheap:

* **bit 26 is set and this port consumes it nowhere.**  Registered check: `f60`/`uft` already
  record an FSLW on every fmt-4 frame they see.  If bit 26 is set on **every** fmt-4 FSLW this
  kernel records, it is a property of the CPU's frame and not of this fault, and it stops being
  interesting.  If it is set on this fault and clear on others, it is a finding and gets its own
  question.  **Either way it is reported before anything is built on the rest of the decode.**
* **PTA-without-PF is asserted from the architecture, not yet from this rig.**  Registered
  control: any *ordinary* user page fault on this machine must show **PF set and PTA clear**.  A
  rig on which every fault shows PTA would mean the bit means something else here, and every
  conclusion drawn from it is withdrawn.

## 3. The derived fault-source location, and what it makes the real defect

Established in `…ATT6-RESULTS…` §5.2–§5.4 and restated here as the premise §4's instrument is
built on, because an instrument built on a wrong premise measures nothing:

```text
   moveal %a5@(0x0000068c),%a4     ; a4 = &table, through the GOT at a5
   moveal %a4@,%a0                 ; a0 = table      <-- a4 = 0, so this reads ADDRESS 0
   tstl   %a0@(0,%d2:l:8)          ; PC C1027EAA, EA = a0 + d2*8 = 0x4AFC0008 -> the wall
```

* **The location the value was read from is user virtual address `0x00000000`.**  Stock kernel
  code at file offset `0x0073CC` — `MOVE.W #$4AFC,($00000000).L` — puts the `ILLEGAL` opcode word
  there, so a longword read at 0 returns `0x4AFC0000`.  Verified in three artifacts of this tree,
  once each.
* **The register file is corrupt in at least three places at once**, once re-labelled through the
  one-longword correction: `%a4 = 0`, `%a5 = 800096FB` (odd, and in `/sbin/init`'s data rather
  than libc's, though `%a5` is libc's GOT base by construction), `%d2 = 80000001` (bit 31 set in
  what must be a hash-table index).  `%a6`, `%a7`, `%a1`, `%d3`, `%d4` are ordinary user-stack
  values.
* **A multi-register corruption is a different animal from a single corrupt pointer.**  The one
  kernel path in the signal loop that writes a whole register file at once is `restorecontext`,
  reloading from a `ucontext` — the object this campaign has watched fail its checksum on every
  boot.  Its guard is a 201-longword XOR fold, therefore **blind to any corruption flipping the
  same bit position in an even number of longwords**, so "the guard would have caught it" is not
  an argument.

**Registered as a hypothesis with a killer, not as a finding.**  §4.3 row G3 refutes it outright.

## 4. The instrument: `ucp`, the paired `ucontext` bracket

### 4.1 The three candidates, judged

| candidate (from the brief) | judgement |
|---|---|
| **a kernel-side watch on the derived location** — who writes it, when | **Rejected.**  The derived location is user VA 0 and **nothing writes it**; the value is the kernel's own boot-time sentinel.  There is no writer to catch.  Worse, the only way to watch it is to write-protect page 0, which changes the behaviour of the very instruction under test — and on the 040 lane exactly that write-protection produced the artifact §11 of `ISSUE10-SETUPSH-WALL-260819.md` had to retract |
| **a `copyout`/DMA-path latch bracketing the location** | **Adopted, re-aimed.**  The location that matters is not VA 0 but the **register file**, and the only kernel path that carries a whole register file across `copyout` and back is the `ucontext` round trip.  Bracketing it *is* a copyout/copyin latch, on the exact object §3 implicates, and it needs no page protection and no behaviour change |
| **an `hsearch`-side canary in the miniroot's `init`** | **Rejected for round 7, kept as the fallback.**  It requires modifying a user binary in the install media — a change outside this repository — and it changes the code under test.  §5 of the results document already identifies the instruction, the function and every operand without it.  Reconsider only if §4.3 reads G3 — the wall's registers did not come out of a `ucontext` — because then the corruption is *not* in that path and a user-side canary becomes the cheapest next probe |

**The killer for §3's whole reframing, registered before the instrument:** `ucp_sent0` reads the
longword at **logical address 0** through the kernel's own DTT0 identity window — a kernel read,
not a user dereference.  **If it does not read `0x4AFC0000`, `…ATT6-RESULTS…` §5.4 is dead**, the
"read through a NULL" chain collapses, and every row below that depends on it is withdrawn rather
than reinterpreted.

### 4.2 Design

One new unit, two hook points, read-only, **nothing dereferences a user address** — the standing
rule `src/ufault_dbg.s` was built under.  Both `ucontext` buffers are kernel-stack addresses
(`…ATT6-PREREG…` §2.4: `setcontext` and `sendsig` both pass `%fp-1024`).

* **at `savecontext` return** — after the stamp exists, which is why this hook wraps rather than
  prologue-hooks — copy the **whole 804-byte checksummed region** into a ring of **four** shadow
  slots, together with its stamp (`ucp+0x3F8`), its `ucp`, and the call sequence number.
* **at `restorecontext` entry** — fold the 201 longwords; if the fold is not `0xFFFFFFFF`, look the
  incoming stamp up in the ring, and on a hit **compare longword by longword** and latch the first
  **twelve** differences as `(index, save-time value, restore-time value)`.

**Why a shadow and not more folds.**  Round 6's honest caution was that a `0xA000` delta in a
201-longword XOR fold is not a `0xA000` delta in one longword — `0xA000` can be one longword
changing by `A000` or two changing by `8000` and `2000`.  **A per-longword compare against the
same object's own save-time bytes removes that ambiguity completely**, and it is the only thing
that can.  Folds cannot be inverted; bytes can be subtracted.

**Why the pairing fixes Table L.**  Round 6's `mcs_g_*` was the *last good* `restorecontext`,
rewritten every call, so on boot 3 the baseline was a different exception from the failure and
**no row could fire** even though the precondition was met — and on boot 1 the same block scored
L4 at one read time and nothing at another.  The shadow is keyed by the **stamp of the object
being restored**, so the baseline is that object's own earlier self.  There is no moving baseline,
no read-time dependence, and no possibility of comparing unlike frames.

**Why a ring of four is enough, and how it says so itself.**  `mcs_s_n == mcs_r_n` exactly on
boot 2 (193,128 each), so saves and restores are 1:1; a depth of four covers three levels of
nesting.  `ucp_miss_n` counts restores whose stamp matched no shadow, so the ring's adequacy is
**measured rather than assumed** — a large `ucp_miss_n` invalidates the depth, not the finding.

**The arithmetic self-check that makes a null result mean something.**  If the stamp matches a
shadow and our restore-fold is not `0xFFFFFFFF` while **no** longword differs, that is an
arithmetic contradiction and the block is **void, not negative** — the same rule §3.1 of the
attempt-5 and attempt-6 pre-registrations used.

### 4.3 The registered rows

Read in order.  First matching row wins.  Precondition: `ucp_sent0` read (§4.1's killer) and
`ucp_bad_n > 0`.

| reading | mechanism it names | verdict |
|---|---|---|
| `ucp_sent0 != 0x4AFC0000` | address 0 does not hold what §3 says it holds | **stop.**  §3's chain is dead and every row below is withdrawn.  Report before anything else |
| `ucp_self_void != 0` | fold says corrupt, byte compare says identical | **VOID**, not negative.  The instrument is wrong and no row is scored |
| stamp hit, and one or more differences land in the **register area** of `mc_state`, with at least one save-time value non-zero becoming zero | the `ucontext` round trip lost a register.  If the zeroed slot is the one `%a4` is restored from, this is §3's hypothesis caught in the act | **G1 — the round trip zeroes a register.**  Report every latched triple; do not guess which register until §4.4's layout row has fired |
| stamp hit, differences land in `mc_state[0..3]` (the format-4 exception frame: SR, PC, format/vector, fault address, FSLW) | the saved **frame** changed across the round trip | **G2**, and it is a different and equally serious finding |
| §4.4's third row fires — the wall's sixteen `u_ar0` longwords correspond to **no** window of the last restored `ucontext`'s `mc_state` | the wall's register file did not come out of a `ucontext` at all, whatever else the round trip did | **G3 — §3's hypothesis is REFUTED**, and refuted from the one direction that does not depend on the pairing engaging.  The `hsearch`-side canary (§4.1) becomes the next probe |
| `ucp_bad_n = 0` across the whole boot while the console still prints `Bad ucontext checksum` | our entry-fold and stock's deciding fold disagree about the same 804 bytes — round 6's unscored observation, now with the pairing unable to engage because we never see a bad object | **G0 — scope, not a candidate.**  Report `ucp_save_n`, `ucp_r_n` and `ucp_miss_n`, say the bracket did not engage, and score no G row |
| stamp hit, differences land **only** in `mc_state[77..199]` | the region no code writes (`…ATT5-PREREG…` §2.5) — uninitialised kernel stack the checksum nevertheless covers | **G4**, a stock defect rather than a port one, and it explains round 6's L4 without implicating the register file |
| `ucp_miss_n` ≥ `ucp_bad_n` | no failing restore's stamp was ever in the ring | **scope, not a candidate.**  Report the ring depth and say the pairing did not engage.  No G row is scored |
| differences appear whose save and restore values differ **only** in bits 12, 13 and/or 15 | round 6's fold-delta bit union `{12, 13, 15}`, now measured **per longword** instead of through a fold | report alongside whichever G row fired.  This is the measurement §3.2 of the results document says is owed, and it is the one that can finally separate "a format nibble", "an SR system byte" and "two data-bus lines" — **but only if the affected longwords' *content* is also reported**, so it is registered as a report, not a verdict |

### 4.4 The layout row, which must fire before G1 is interpreted

`mc_state` begins at `ucp+0xD8`, and round 6 decoded `mc_state[0..3]` as the format-4 exception
frame — for the wall frame, `0004C102 7EAA4008 4AFC0008 05011000` = SR `0x0004`, PC `0xC1027EAA`,
format/vector `0x4008`, fault address `4AFC0008`, FSLW `05011000`, every field equal to the `uft`
census read through a different hook.  **Where the register file sits inside `mc_state` has never
been measured**, and G1 cannot name a register without it.

So `ucp` latches `mc_state[4..19]` — sixteen longwords — at the last `savecontext` before the
first wall fault, and the row is:

| reading | verdict |
|---|---|
| those sixteen longwords equal the sixteen at `u_ar0+0` for the wall fault, in order | **the register file is at `mc_state[4..19]`**, and G1 may name a register.  It also links the wall's register set directly to a restored `ucontext`, which is §3's hypothesis confirmed from a second direction |
| they equal them after a shift of one longword | the same off-by-one as `src/ufault_dbg.s` (`…ATT6-RESULTS…` §5.2), now in a second place.  Report it and apply it before naming any register |
| they do not correspond at all | the register file is elsewhere in `mc_state`, or the wall's registers did not come from a `ucontext`.  **G1 is reported as "a longword changed at index N" and no register is named** |

### 4.5 Registered risk, and it is not small

`mcs` already folds 201 longwords on every `savecontext` and every `restorecontext`; `ucp` adds an
804-byte copy per save.  Attempt 5 boot 3b delivered 14,093 signals and attempt 6 counted ~190,000
`savecontext` calls per boot, so this arm changes the timing of the signal path measurably.
**A boot in which the `ucontext` refusal does not occur therefore cannot be read as "the defect
went away"** — it is one draw from a distribution this round has perturbed.  `ucp_on` exists as a
`.data` gate so a control can be stamped one word apart if that question needs answering.

**And `ucp` supersedes `mcs`'s Table L rows rather than joining them.**  Running both would fold
the same region five times per signal for no added information; `mcs`'s counters are kept for
continuity and its L-rows are retired.

## 5. Everything is hex, and the sheet is recomputed

**Every runtime address comes from `tools/status-facts.sh` against the artifact that will actually
be booted, at the load base actually observed — never from an on-box `nlist`**, because the kernel
under test is installed into the boot slice and `/stand/unix` is a different kernel.  A slot
reading `ffffffff` means *not applicable*, not zero.  Read every block's magic before believing
any number in it.

**Attempt 6's counter sheet is not reusable, and neither is attempt 5's.**  The base fixes move
every block by exactly +4 (§7.2 of this document, and `…ATT6-RESULTS…` §8.2), and `ucp` will move
them again when it is linked.

**Nor is attempt 6's driver anchor list**, which is the easier trap to fall into because §6.2 of
that pre-registration was entitled to say the driver's `.text` did not move and this round is not.
Stock-text `R_68K_32` sites are unchanged; **every appended-object site shifts by +4**, and the
drivers are appended objects — `z3660_range_ovf` `0x0f5536`/`0x0f55a2` → `0x0f553a`/`0x0f55a6`,
and so for all sixteen §4.6 gates (`…ATT6-RESULTS…` §8.3).  A stale anchor offset does not fail;
it reads a longword out of a neighbouring instruction and returns a plausible address.  **Re-derive
the list with `tools/status-facts.sh` against the artifact that will be booted, and require every
multi-site symbol to agree before believing any single-site value.**

## 6. The session: N boots, stratified cold and warm

### 6.1 Which of §5.3's five, and why

| §5.3 option | decision |
|---|---|
| **1. N-boot outcome distribution** | **ADOPTED.**  §5.3 calls it "the prerequisite for every other experiment on this list", and it is: every other item is a comparison of two distributions and there is not yet one.  Round 6 produced three outcomes in three boots and could conclude nothing about proportions |
| **4. cold versus warm** | **ADOPTED, folded in at zero cost.**  §5.3 calls it "the cheapest of the four — it needs no code and no card change".  Making it the *stratification* of the N-boot protocol rather than a separate session answers both questions in one window.  Every boot in attempts 3–6 followed an `Escape`/reset rather than a power cycle, so carried DRAM and card state has never been controlled for |
| 2. clock sweep | deferred — it is a comparison of two distributions and needs this one first |
| 3. `default_timings` A/B | **excluded: an explicit user gate**, not an agent decision.  Fetched read-only as a restore witness, as in round 6 |
| 5. resident memory canary | **excluded this round.**  It wants a periodic driver — a clock-tick hook, which is a base change — and this round already re-bases the lineage.  Two structural changes in one round is exactly what makes a determinism proof measure two things at once |

**Stratified, not blocked.**  The two arms are interleaved (W, C, W, C, …) rather than run as four
warm then four cold, so that thermal drift, card-state drift and operator drift cannot align with
the arm.

### 6.2 The plan

1. **Eight scored boots minimum** of the instrumented primary, each from a **fresh gated copy** of
   the work root, alternating **warm reset** and **cold power cycle**, starting warm.
2. **Fast tier on every boot**, and nothing more, so a boot costs minutes rather than a window:
   `swa` first (one `kpeek`, the only block guaranteed to have fired), then `ucp`, then the `uft`
   head (`uft_n`, `uft_have`, `uft_f_fa`, `uft_f_pc`, `uft_f_fslw`), then
   `kvd_n` / `kvfar_n` / `kvd_split_n`, then the outcome class, then one thermal and rail sample.
3. **Full census on boot 1, and on any boot that fires a row no earlier boot fired.**  A new row is
   worth a window; a repeat is worth a line.
4. **Every boot is scored.  No boot is re-run to green.**  A mechanical non-boot is discarded only
   under attempt 5's rule and with the same three independent proofs; a firmware-side abort of the
   class round 6 saw is discarded on its own separate and stronger ground, and is recorded either
   way.
5. **The fallback artifact is not booted** unless the primary produces two mechanical non-boots.

**Registered as deliberately not in the plan:** no `--cache 0` control (the A/B is settled and a
control stops at `swapconf`'s lookup); no `--dbg` combination (it shifts every counter address
again and adds a second variable); no `nullvect` chain (the one hook whose failure costs the whole
window); no card-side change of any kind.

### 6.3 What the distribution can and cannot say

* **It can** say whether the outcome classes are a small stable set with reproducible proportions,
  and whether cold and warm draw from the same set.  A cold arm that never produces the wall, or
  produces it at a visibly different rate, is the first evidence in this campaign that **carried
  state** is involved at all.
* **It cannot** make the software-versus-electrical cut.  Eight boots is a distribution, not a
  mechanism, and `…ATT6-PREREG…` §5.2 is not repealed by a larger *n*.
* **It cannot** be pooled with attempts 3–6.  Those boots ran a different kernel — this commit
  re-bases the lineage (§7.2) — so they are a different population and are not counted in.

## 9. What attempt 7 will NOT prove — registered so it cannot be claimed afterwards

* **No software-versus-electrical verdict.**  `…ATT6-PREREG…` §5.2 stands and a larger *n* does
  not repeal it.
* **No cause for `%a4 = 0`** unless G1 fires *and* §4.4's layout row fires.  G1 alone says a
  longword changed, not which register and not why.
* **No claim that the `ucontext` path is the only way a register file can be corrupted.**  G3
  refutes the hypothesis; it does not enumerate the alternatives.
* **Nothing about `hsearch`'s own logic.**  `%d2 = 0x80000001` is recorded and not explained, and
