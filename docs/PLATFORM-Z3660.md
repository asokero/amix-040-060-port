# The Z3660 platform — an emulated 68040 on a real bus, and what it does not model

`docs/ACCEPTANCE.md` §1 says a new platform class must arrive with its own list of what it does
not model, because only whoever built it knows, and without the list its results will be read as
stronger than they are. This is that list.

**Proposed class name: `Z3660`**, beside `EMU` and `HW`. It is neither. It is a real Amiga, on a
real Zorro bus, with real DRAM and real timing — running a **software 68040**.

> The short form, for anyone citing a result from here: **this platform is strong evidence about
> memory, bus and DRAM behaviour, and weak evidence about the CPU.** Where a claim depends on
> what a 68040 does, `Z3660` and `HW` are not interchangeable, and the table in §2 is why.

## 1. What the platform is

A Z3660 accelerator card: a Zynq (Z-Turn) module in the CPU slot, whose ARM cores run the Amiga.
One core services the real bus; the other runs a CPU interpreter. The interpreter is a
**UAE-lineage 68040 with the real 68040 MMU enabled** — the card's `UAE_040_MMU` mode.

| | |
|---|---|
| CPU core | Amiberry 5.6.0's UAE core; the 68040 MMU opcode table generated by WinUAE 4.4.0 `gencpu` (its id 31) |
| CPU / FPU / MMU model | `cpu_model` 68040, `fpu_model` 68040, `mmu_model` 68040 |
| JIT | **off** — the MMU modes require fault restart, so the translation cache is 0 |
| `cpu_compatible` | **false** — no prefetch-pipeline path |
| `cpu_cycle_exact`, `cpu_memory_cycle_exact` | **false** |
| FPU arithmetic | the native host-floating-point implementation (`fpp_native.cpp`), not an extended-precision softfloat |
| Unimplemented FP opcodes | **trapped to the guest** under the AMIX contract, so AMIX's linked FPSP actually executes |
| Guest RAM | the card's own DDR, presented to AMIX as Fast RAM |
| Chip RAM, Zorro space, interrupts, DMA | the **real machine** |

The two halves matter separately. Everything outside the CPU box is silicon and behaves like it.
Everything inside it is a program.

## 2. The 68040 path had never been executed before AMIX ran on it

This is the single most important fact about the platform's history, and it is the reason §3's
list should be read as open rather than closed.

The UAE 68040-MMU table had been generated and linked, but no operating system had ever driven
it here. Getting an AMIX kernel from reset to a login prompt required **ten** guest-visible
defects to be found and fixed, and the recurring shape of them is the same: *a 68040 register or
instruction whose side-effect function exists in the core but has no caller.* Every one of them
was found by **AMIX failing on the card** — not by the emulator's own tests, which passed
throughout.

| # | date | defect | how it presented | guard added |
|---|---|---|---|---|
| 1 | 08-20 | core0's emulated-mode predicate omitted `UAE_040_MMU` | core1 never started; nothing was emulated at all | `bootmode_test.cpp` pins the mode indices across all four replicas |
| 2 | 08-20 | a core1 breadcrumb called the print routine before shared state was initialised | core1 wedged on **every** mode | NULL-safe print path |
| 3 | 08-20 | the 040 table's `STOP` handler never advanced the pc | AmigaOS wedged on its first `STOP` | `test_stop_advances_pc_all_tables` |
| 4 | 08-20 | `MOVEC` to `TC` never enabled the MMU | the kernel panicked at VM init | `test_mmu040_movec_tc_enables_mmu` |
| 5 | 08-20 | `PFLUSH` was a no-op and `PTEST` fabricated its MMUSR | one VM-init stage further, then died | `test_mmu040_pflush_ptest` |
| 6 | 08-21 | a guest reset cleared the registers but not the MMU state | a warm reboot inherited a stale translation regime | `test_mmu040_reset_clears_mmu_state` |
| 7 | 08-21 | bitfield instructions on the 040 MMU path used the **68030** accessors | `BFINS` to translated memory did not write — the store vanished | `test_mmu040_bitfield_translates` |
| 8 | 08-21 | the 040 accessors split only on page crossing, not on bus misalignment | a misaligned frame-PC read dropped bit 23: `0x80800000` delivered as `0x80000000` | `test_mmu040_misaligned_split` (routing invariant) |
| 9 | 08-21 | the format-`$7` frame stacked the write-back status words without clearing them | the guest replays on `WB3S` bit 7 alone, so a **stale** write-back was replayed against the **current** fault's address — a stray store of an old datum into the page being demand-paged in | `test_mmu040_writeback_slot_consumed`, `test_mmu040_user_icode_stream` |
| 10 | 08-21 | `mmufixup[1]` was never cleared at reset, and a zero slot reads as "A0 armed, restore 0" | the first bus fault of the session set `A0 = 0`; `copyout` resumed reading from guest address 0 | `test_mmu040_copyout_fault_keeps_source_reg` |

Two observations belong with that table rather than in a footnote.

**Defects 1 and 2 are firmware bring-up, not CPU modelling.** They are listed because they were
in the path, not because they say anything about 68040 fidelity.

**Defect 9 produced the exact signature this port had been chasing under its own issue number.**
A stray write, of a stale datum, into a page being faulted in, is indistinguishable from a kernel
bug until you can prove where the store came from. The lesson generalises: on this platform, a
memory corruption whose store has no source in the kernel's own code is a **platform hypothesis
before it is a kernel hypothesis**, and the two are separable only by instrumenting both sides.

Guards are **regression guards, not coverage**. They pin the ten cases that were wrong. They do
not establish that the eleventh is right.

### The harness

Three host suites, run on the build machine, not on the card: the CPU/MMU harness (**256** checks),
a SCSI CDB suite (**34**), and the boot-mode enum invariant (**26**). The MMU harness drives the
real table walk and the real run loop — descriptor and physical accesses bottom out in a flat
buffer, so it exercises the genuine engine rather than stubs.

Its structural limit is worth stating, because it has misled this project once already: **the
harness's flat buffer will service accesses the card's memory layer cannot.** Defect 8 could not
be value-reproduced on the host for exactly that reason — the host answers a misaligned read
correctly, the board drops a bit — so the guard pins the routing decision instead of the value.
A green harness is not evidence that the board agrees.

## 3. What it does not model

`AGENTS.md` lists four things Amiberry is not evidence for. Taking them in order, for this
platform:

* **Enabled IEEE floating-point exceptions** — *no evidence either way.* No enabled-exception
  battery has been run here. The FPU is the native host-FP implementation, not an extended-
  precision model, so bit-exactness results of the kind the 68060 work produced on silicon must
  **not** be transferred to this platform. What *is* modelled, and deliberately: unimplemented
  68040 FP opcodes raise the genuine trap instead of being computed by the emulator, so AMIX's
  FPSP executes rather than being bypassed.
* **The first 68040 write-back slot** — *modelled, and this is where the platform differs most
  from Amiberry.* The access-error frame is a real format `$7` filled from the fault record —
  SSW, FA, EA and the WB2/WB3 slots — so `wb040.s`'s replay path genuinely runs here. That is a
  capability, not a guarantee: it is established that the slots are populated and consumed, and
  **not** established that the set of write-backs a real 68040 would post matches this one.
* **The 68040 copyback data cache** — *not modelled at all.* There is **no data cache and no
  instruction cache model**; the descriptor and TTR cache-mode bits are decoded and then have
  nowhere to act. `CINV`, `CPUSH` and `MOVE16` therefore do not do what the silicon does, and
  cache-inhibited-DMA coherency is not emulated. **A cache-class or DMA-coherency change that
  passes here has not been tested**, exactly as for `EMU`.
* **Which instructions the CPU traps as unimplemented** — *partial, and asymmetric.* On the 040
  path the unimplemented-**integer** trap is unreachable by construction (64-bit multiply and
  divide always succeed for `cpu_model >= 68040`), which is right for a 68040 and means this
  platform is **not** evidence for the 68060's behaviour. FSLW.MA is not evidence here either.

Beyond that list:

* **No bus, cache or instruction timing.** Cycle-exact and memory-cycle-exact are both off and
  the speed setting is unthrottled. **Do not quote a throughput or latency number measured here
  as a silicon figure.** Structural results (which path was taken, which counter moved) survive;
  timings do not.
* **No prefetch pipeline** (`cpu_compatible` false). This is not cosmetic: under this
  configuration several fault paths throw straight to the run loop's handler instead of passing
  through the normal exception build, and that asymmetry is what hid defect 9 for six rounds of
  investigation.
* **Instruction fetch is not separately modelled.** It goes through the same translating
  accessors as data — measured, not assumed: an I-versus-D probe on the card read the same
  physical longword both ways and both returned the same (wrong) value, which is what refuted a
  fetch-path hypothesis and moved the search to page content.
* **68040 MMU semantics still without a vector**: indirect page descriptors (one level is
  handled, double indirection is flagged illegal, neither is exercised); ATC replacement and the
  global bit's flush exemption (a hit is checked, eviction is not); the individual `PFLUSH`
  variants and the full `PTEST` MMUSR encoding beyond what the one guard asserts; and the case
  where a page-crossing access faults on its *second* page.
* **68060 is out of scope.** The 68060 table is not built. Nothing here is evidence about it.

### One thing it models that the emulator does not: dirty DRAM

The guest's memory is the card's DDR after a cold ARM boot. It is **not zero-filled**, and
because it is not, it is deterministic — the same garbage in the same places on every boot.

That is not a gap; it is the platform's most valuable property so far. It is what exposed
**ISSUE-102** in this repository's ledger: stock AMIX maps the page-frame database into existing
DRAM and zeroes nothing, so `page_free` panics on the first structure whose fields arrive
non-zero. Zero-filled emulator RAM hides that defect completely. The bug is generic SVR4 VM code
and has nothing to do with the 68040 — it simply cannot be found on a platform that hands the
kernel clean memory.

The general form is worth keeping: **a `Z3660` pass and an `EMU` pass are not the same pass**,
and where they disagree the interesting question is which of them is blind.

## 4. What has actually been measured here

Stated so the class is not read as more proven than it is.

* The 68040 kernel **boots, banners, and runs PID 1** on the card, reaches the interactive
  installer prompt, and an AMIX install has completed on it. A login prompt has been reached
  **once, and not yet on every boot** — reaching it reliably is the open work, not a result.
* The kernel an **installed disk** boots is a different artifact from the miniroot kernel that
  installs it, and the current one **has not been run on the card at all**. Any claim about the
  installed system, as opposed to the installer, is unmeasured on this platform.
* The kernels that ran here were built on the **minimal-delta line** — the shipped miniroot
  lineage plus the fixes and nothing else — deliberately *not* on the instrumented line, whose
  audit hooks sit on the fault tails and execute during boot. When citing a `Z3660` result, name
  which of the two produced the image; they are not the same kernel.
* **The common battery of `ACCEPTANCE.md` §5 has not been run on this platform.** Not one of the
  historical eleven. Bring-up is not acceptance, and nothing here should be read as a battery
  result.
* **No acceptance record in the §10 form exists for this platform yet.** The first `Z3660` run
  that claims anything beyond bring-up should produce one.

## 5. How to cite a result from here

Per §2 of the acceptance procedure, identity before numbers — with one addition this class needs:

1. the class, `Z3660`, never collapsed into "the emulator" or "the hardware";
2. the **firmware build**, by size and CRC (the card's own SD menu prints the CRC), because the
   ten defects above were fixed across a dozen builds and a result from any earlier one carries
   whichever of them was still live. The build these findings were measured on is
   `BOOT.BIN` 12,762,380 bytes, zlib crc32 `D5CBFAF4`;
3. the kernel's build id and framed `sum -r`, and which build line it came from;
4. every counter block's magic word, as on any other platform.

## 6. What this document does not establish

It does not establish that the emulated 68040 is correct. It establishes that ten specific ways
in which it was incorrect are now guarded, that a kernel can be brought from reset to a login
prompt on it, and that the failures found so far all have the same shape — an unexercised path,
not a wrong algorithm.

It does not establish anything about caches, about floating-point exception delivery, or about
timing, because none of those are modelled or measured here.

And it does not close the list. Two of the ten defects were found after the kernel had already
booted successfully, by a process that only failed later and elsewhere. The honest expectation is
that more of them exist, and that the next one will also be found by AMIX rather than by a test.
