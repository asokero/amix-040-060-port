## 2. Why `ucp` is its own stage, and what the primary carries

**Its own stage, because a determinism proof taken over a stage that carries two changes measures
two things at once.**  Round 6's script builds its three arms; adding a fourth option to it would
have made "the round-7 base reproduces" and "the instrument is additive" the same measurement.
They are separate here, and §6 reports them separately.

**The primary carries `kvd`, `swa` and `ucp`.**  §7.3 of the pre-registration says to build the
instrument "as a post-pass over `build/unix-040-f7uft`", which taken literally would ship an
artifact carrying neither `kvd` nor `swa`.  §8 of the same document decides it the other way and
does so unambiguously: bench row 1's inertness set is

> `ucp_self_void = 0`, `ucp_bad_n = 0`, `ucp_miss_n = 0`, **`swa_n = 1` with `swa_ret = 0`**, the
> three `swa` constants equal to their file values, **`kvd_split_n = 0`**, **`kvd_a_chg_n = 0`**,
> **`kvd_a_nvcnt = 237`**, `uft_n = 0`

— four `swa` and `kvd` readings on the *same image* as the three `ucp` ones — and §6.2's fast tier
reads `swa` first, then `ucp`, then the `uft` head, then `kvd_n` / `kvfar_n` / `kvd_split_n`.  So
the chain is

```text
  f7uft  --(relink-040-f6.sh --kvd --swa)-->  f7vs  --(relink-040-f7.sh --ucp)-->  f7vsu
```

and the one change this round's determinism proof measures is the last arrow.  `relink-040-f7.sh`
also accepts the literal reading — `--ucp` straight over `f7uft` — and that path was built once as
a test and then discarded; it is not an artifact of this round.

**`mcs` is not in it, and the script refuses rather than discovers that.**  §4.5: `ucp` supersedes
`mcs`'s Table L rows rather than joining them, because running both would fold the same region
five times per signal for no added information.  It is also structurally impossible — both units
define `savecontext` and `restorecontext` — so `relink-040-f7.sh` rejects any input carrying
`mcs_magic`, with the reason, before it assembles anything.  Verified by running it against
`build/unix-040-f7vsm`: exit 1, no output file.  `mcs`'s counters are kept for continuity **by
name**: `ucp_save_n` / `ucp_r_n` / `ucp_bad_n` / `ucp_s_bad_n` are `mcs_s_n` / `mcs_r_n` /
`mcs_r_bad_n` / `mcs_s_bad_n` under this round's prefix.

## 4. Deviations from §4.2's design, stated rather than absorbed

Four, and each is recorded in `src/ucp_dbg.s`'s own header as well.

1. **A fourth metadata longword per slot: our fold of the object at save time.**  §4.2 lists
   three (stamp, `ucp`, call sequence number).  §4.2's VOID rule is "our restore-fold is not
   `0xFFFFFFFF` while no longword differs is an arithmetic contradiction" — and it is a
   contradiction only if the *shadow's* fold was `0xFFFFFFFF`.  Without the fourth field that is
   an assumption; with it, it is `ucp_b_s_fold`, read back with the rest.  `ucp_s_bad_n` counts
   the saves where it was not, i.e. where the stamp was wrong **at birth**.
2. **`ucp_hit_n`, `ucp_dup_n` and `ucp_diffev_n` are additions.**  §4.2 registers `ucp_miss_n`
   precisely so the ring depth is measured rather than assumed; these measure the other three
   things that decide whether a pairing engaged at all.  `ucp_dup_n` matters most: a stamp is a
   32-bit fold and is **not** a guaranteed-unique key, so an event where two slots carry the same
   stamp is an ambiguity of this instrument, and it is counted instead of being resolved
   silently.  The newest matching slot wins, and `ucp_b_s_ucp` is latched beside `ucp_b_ucp` so a
   pairing across two different objects is visible in the readout.
3. **`ucp_slots` / `ucp_slot` / `ucp_doff` are the ring geometry stamped into `.data`.**
   `tools/status-facts.sh` reads them out of the artifact, so a re-sized ring re-prints correctly
   and no tool carries a second copy of the number.
4. **The twelve-triple latch is claimed only by an event that HAS a difference.**  §4.2 does not
   say which event owns the one-shot.  A VOID event — bad fold, zero differences — would consume
   it under the obvious implementation and leave the block full of sentinels on a boot that later
   had a real difference to show.  So the compare runs in two passes on a hit: pass 1 counts and
   folds the bit union and stores nothing; pass 2 runs only for the first event with `n > 0` and
   writes the header and the triples.  The counters (`ucp_self_void`, `ucp_diffev_n`,
   `ucp_hit_n`, `ucp_miss_n`, `ucp_dup_n`) are boot-wide and are **not** one-shots, so both the
   VOID row and the G rows stay readable on the same boot.

Three further readings of the pre-registration were needed and are recorded here as readings, not
deviations:

* **§4.4's "the last `savecontext` before the first wall fault" is keyed on `uft_have`.**  The
  instrument cannot know about the wall except through the census that latches it.  The freeze
  test runs **before** the rewrite, so the block holds the last save taken while `uft_have` was
  still zero — without that ordering the `sendsig` the wall itself provokes would overwrite the
  very frame the row is about.
* **§7.1's table labels `f7vsm` "primary" and `f7swa` "fallback"**, which were that commit's names
  for the two re-based arms at a time when `ucp` did not exist.  §6.2 boots "the instrumented
  primary" and §8's rows read `ucp_*`, so the primary of the attempt-7 *session* is the `ucp`
  arm.  §7 below states the three roles explicitly.
* **A slot's sequence number is cleared before its fill and written after it**, so a slot is
  EMPTY for the duration rather than advertising its predecessor's stamp over this one's
  half-copied bytes.  §4.2 says nothing about the write order and the exposure is narrow —
  `savecontext` is reached from `setcontext` and `sendsig`, never from interrupt context — but a
  reader that landed in the window would pair against a torn frame and there would be no counter
  saying so.  With the ordering, such a reader skips the slot and lands in `ucp_miss_n`, which is
  a *measured* miss.  It costs one `clrl` and is why `ucp`'s `.text` is 636 bytes rather than the
  632 the first build produced.

## 10. Registered cost, unchanged and not small

`ucp` folds 201 longwords **and copies 804 bytes** on every `savecontext`, folds 201 longwords on
every `restorecontext`, and on a *bad* restore adds a four-slot scan plus one or two more passes
over the 201 longwords.  Attempt 6 counted ~190,000 `savecontext` calls per boot, so this arm
measurably changes signal-path timing — more than `mcs` did, because `mcs` folded and this copies
as well.

**A boot in which the `ucontext` refusal does not occur therefore cannot be read as "the defect
went away."**  It is one draw from a distribution this round has perturbed, and §9 of the
pre-registration already forbids the claim.
