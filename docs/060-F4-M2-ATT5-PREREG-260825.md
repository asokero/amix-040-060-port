# Attempt 5: the userland wall, and what would tell its causes apart

2026-08-25.  Follows `docs/060-F4-M2-ATT4-RESULTS-260825.md` and scores nothing that document
already scored.

**The honest sequence, since it is the only thing that makes a pre-registration worth anything.**
§2's refutations and §4's signature tables were derived from **static** work — two audits of this
tree and of the on-disk binaries that were actually running — and every one of them was fixed
before the round-5 artifact existed.  §5's identities and gate results are facts recorded after the
build, as attempt 4's own §5 was.  **No artifact of this round has been booted anywhere, on any
platform.**  **No fix has been written this round** — the only new code is a read-only census.
Nothing below is adjusted after a reading.

## 1. The measured situation, in five sentences

Attempt 4 named the swapconf mechanism and closed it: the piscsi driver's cache maintenance, armed
at link time, turns `PANIC: swapconf lookupname /dev/dsk/ced0s2 failed - error 20` into a boot that
enters userland, and a three-byte control makes the delta attributable to the value.  The boot then
forked, exec'd, and stopped one giant step further along: `/sbin/init` (PID 1) looped **182,741**
times on

```text
NOTICE: User BUS ERROR at 4AFC0008, PC:C1027EAA FAULT:6 PID:1 CMD:/sbin/init
```

and ended at the stock guard `Bad ucontext checksum (0xFFFFCFFF)in process: init`, after which the
machine went quiescent with **no kernel panic at all** (`bt_walks = 0`).  `FAULT:6` is `FLTBOUNDS`
(`build/sysroot-modelb/usr/include/sys/fault.h`), i.e. an invalid virtual address.  This document
splits that one screen into **two independent questions** — where `0x4AFC0008` came from, and why
it repeated 182,741 times instead of killing the process once — because they have different
candidate mechanisms and attempt 4's reading conflated them.

## 2. What is already settled, before this round starts

Four things were established without a boot.  They are listed first because a pre-registration that
re-asks a settled question wastes the only expensive resource this campaign has, which is a
15-minute real-CPU window.

### 2.1 The faulting instruction is known, and it is a DATA READ

`PC 0xC1027EAA` is **not in `/sbin/init`**.  `init` is `ET_EXEC` based at `0x80000034` and is
dynamically linked against `/usr/lib/libc.so.1`, which this port maps at **`UVSHM = 0xC1000000`** —
a base corroborated three independent ways inside this tree
(`docs/contracts/AVAILRMEM-ACCOUNTING-AUDIT.md`, whose worked example uses this very library's first
`PT_LOAD`; `src/sigkill_dbg.s:70,74`; and `src/usrxmemflt040-design.md:132`, whose
`C101116E _rtmalloc` resolves correctly against the copy on this root).  `0xC1027EAA − 0xC1000000 =
0x27EAA`, which lands inside libc's `hsearch`, and the instruction there is

```text
   27ea8:  2054           moveal %a4@,%a0            | a0 = libc's static `table`
   27eaa:  4ab0 2e00      tstl   %a0@(0,%d2:l:8)     | <== the faulting PC.  EA = %a0 + %d2*8
```

So `0x4AFC0008 = %a0 + %d2*8`, it is a **four-byte read**, and `TST` never writes memory.
`0x4AFC0008 = 0x4AFC0000 + 1*8` decomposes exactly if `%a0` held `0x4AFC0000` and `%d2` was 1.

### 2.2 `0x4AFC0000` is not a new number in this project

`docs/ISSUE10-SETUPSH-WALL-260819.md:119` records the **identical value** as a fabricated free-list
link in `/bin/sh`, faulting at `4AFC0003` with the same `FAULT:6`.  `0x4AFC` is the m68k `ILLEGAL`
opcode word, and `4AFC 00nn` is the exact byte pattern this compiler emits ahead of a switch
dispatch — an `ILLEGAL` guard word followed by a case count.  `/sbin/init` contains that idiom seven
times and `libc.so.1` contains the literal bytes `4A FC 00 08` twice, both switch-table headers with
eight cases.  **So the value is text bytes sitting where a pointer should be** — which is a
description of the corruption, not yet an explanation of it.

### 2.3 Candidate (a), the instruction cache, is refuted as the ACTIVE mechanism

Two independent static readings, either of which is sufficient:

* the fault is a **data** read (§2.1), not an instruction fetch, so no I-cache reading is admissible
  for *this* fault;
* there **is** an instruction-cache invalidate between a freshly DMA'd text page and its first
  execution — it is just not where anyone would look for it.  `hat_pteload`'s epilogue
  (`src/hat040.s:505`) uses `cpusha bc`, the **both-caches** form, and on the 68040 and 68060 alike
  that invalidates the whole I-cache; `resume` does a whole-IC `cinva ic` on every context switch
  (`src/runtime040.s:218`).  A demand-paged text fault must install a PTE, so it must pass through
  `hat_pteload`.

`z3660_cache` remains **binary**, and this is worth stating because the attempt-4 record can be read
otherwise: `amix-z3660scsi/src/z3660.c:320` documents 0 / 40 / 60 as CPU-*family* labels, every
consumer in that file tests the knob for zero versus non-zero, and **no site distinguishes 40 from
60**.  There is no bitmask in `0x3C` to decode.  The driver's only cache primitives are
`.word 0xf468` (`cpushl dc`) and `.word 0xf448` (`cinvl dc`) — **data cache only**, in both transfer
directions; there is no `ic` or `bc` form anywhere in that source.  The same is true of this port's
own `src/dma_cache040.s`.

**§4's Table E carries the one measurement that would overturn this**, and it costs nothing: the
FSLW's TM field says data versus code.  A pre-registration that refuses to carry its own refutation
test is an opinion.

### 2.4 Candidate (b), the `ucontext` skip, is refuted by ordering

The guard is stock **`restorecontext+0x5A`** (`.text 0x58D76`), reached only from `setcontext+0x9c`;
there is no `sigreturn` symbol in this kernel at all.  `stampsum` XOR-folds longwords: `savecontext`
folds 200 of them over `[ucp+0x0D8, ucp+0x3F8)` and stores `~sum` at `ucp+0x3F8`; `restorecontext`
folds 201 and requires `0xFFFFFFFF`.  On failure it calls `psignal(p, SIGKILL)`, which is exactly
why the machine ended **quiescent rather than panicking**.

* `fpu_setup_gated` is called at `sendsig+0x1f8`, **56 bytes after the last of three `copyout`s
  returned**.  It cannot have touched the user frame.  The reading "the no-FPU skip breaks the frame
  layout" is refuted by ordering, before this round starts.
* The FP region **is** inside the checksum's coverage and **is** left unwritten on an FPU-less part
  — but by stock's own `prhasfp` gate, not by ours, and the stamp is computed over that same garbage
  in the same breath, so it self-cancels.
* **Attempt 4 counted 182,741 deliveries before one refusal.**  A structural layout defect fails on
  delivery 1.  So the refusal is terminal or intermittent, and §4's Table H decides which.

Registered as a **lead and not a mechanism**: `0xFFFFCFFF` means an XOR delta of exactly
`0x00003000` — two bits, 12 and 13, of one covered longword.  `0x4008 ^ 0x7008 = 0x3000` exactly,
and those are the 68060 format-4 and 68040 format-7 exception-frame words, i.e. an arithmetic fit on
precisely this port's own 040/060 split, in a field `prsetstate` reads back out of the
**user-supplied** buffer to size a `bcopy`.  Two bits in 200 longwords have many fits.  It is
written down so it cannot be invented later, and it is not claimed.

### 2.5 Two findings recorded, and deliberately not acted on this round

* **`hat_pteload`'s I-cache invalidate is an unnamed side effect.**  Its own comment
  (`src/hat040.s:496-504`) is entirely about the hardware table walker seeing a stale descriptor, and
  neither `docs/060-D-CACHE-KNOBS-PLAN.md` nor `docs/contracts/CB-PAGE-LIFECYCLE-CLOSURE.md` lists it
  among the cache-operation sites.  `src/codepub040.s:24-27` already warns, about the *other*
  accidental barrier, that "a later range optimisation there would be correct on its own terms and
  would silently delete user-code publication" — and that sentence applies verbatim here, where such
  an optimisation would delete the only thing invalidating the I-cache on a same-process
  demand-paged text fault.  Relatedly, `src/cb_icode040.s:52-53` asserts that other user text
  "arrives via page-in DMA (whose prepare/complete hooks already maintain coherency)": that is
  **true for the data cache and false for the instruction cache**.
* **A 1024-byte kernel-stack leak to userland, and it is stock.**  Nothing zeroes the `ucontext`
  buffer; `mc_state[77..199]` — 492 bytes — is never written by any code, and the whole 1024 bytes
  are `copyout`'d on every signal.  Not this round's problem, and not silently unnoticed either.

## 3. The instrument — `src/ufault_dbg.s`

`u_trap` reports a fatal user fault with

```text
cmn_err(CE_NOTE, "User BUS ERROR at %x, PC:%x FAULT:%x PID:%d CMD:%s\n",
        fa, pc, fault, pid, u_comm)
```

from the call at `0x5a63e`, relocation at `0x5a640`.  `src/patch_usptrap.py` already points that
relocation at `unt_latch` (ISSUE-52); `src/patch_ufault.py` points it one step further at
`uft_latch`, which tail-jumps to `unt_latch`, which tail-jumps to `cmn_err`.  Both instruments run
and the NOTICE prints unchanged.  **The only path that reaches any of it is one already reporting a
fatal user fault**, so a healthy kernel executes none of it — which is the same argument that let
`usptrap.s` into a boot in the first place.

**Nothing in it dereferences a user address.**  Every read is kernel memory: the argument frame
`cmn_err` was about to consume, the u-area, `curproc`, the trap frame `u_trap` itself built, and
`rootdir`.  A probe that faulted while reporting a fault would turn a NOTICE into a panic and cost
the whole boot, so the user pages at `PC` and at the fault address were read **host-side, from the
on-disk binaries**, which is where §2.1 came from.

The frame layout is verified against this image rather than inherited: `u_trap+0x12` stores
`%fp+8` into `u+0x864`, so `u.u_ar0` **is** this fault's own frame, set 430 bytes before the NOTICE
is called; `setregs` writes the new SP at `u_ar0[60]` and the new PC at `u_ar0+66`, which pins
`d0-d7` then `a0-a7` at `+0..+63`, SR at `+64`, PC at `+66`, format/vector at `+70`.  On a **68060
format-4** frame only, the fault address is at `+72` and the FSLW at `+76` —
`src/getfault040.s:39` and `src/userspace040.s:91` read those same two offsets the same way, and
`src/patch_framesz060.py` sets `framesz[4] = 16` to match.  On a 68040 the frame is format 7 and
those two slots carry the sentinel `FFFFFFFF` instead.

`u_comm` is taken from **the pointer the NOTICE itself was handed**, not from a hardcoded u-area
offset — `src/usptrap.s` says `u+0x3b0` and `src/sigkill_dbg.s` says `u+0x1c0`, they cannot both be
right for one kernel, and the argument frame cannot be wrong.

**Everything is hex.**  `FAULT` 6 = `FLTBOUNDS`; `v_type` `VNON 0, VDIR 2`; a `uft_*` slot reading
`ffffffff` means *not applicable*, not zero.

### 3.1 Two self-checks that must pass before any value in the block is believed

* `uft_f_fpc` must equal `uft_f_pc`, and `uft_f_ffa` must equal `uft_f_fa`.  They come from two
  different places — the CPU's stacked frame and `u_trap`'s own locals — and if they disagree then
  `u.u_ar0` was not this fault's frame and **every register below it is noise**.  That is exactly the
  trap ISSUE-52 round 2 fell into: the right value read at the wrong moment.
* `uft_f_a7` must equal `uft_f_usp`.  Same argument, from the third direction.

If either fails, the register rows of §4 are **void, not negative**, in the same sense the DPI caveat
made attempt 4's pass-2 row void-or-valid.

#### 4.1 The static half of the cure-gate question, which needs no boot

`src/hgfault040.s` gates the ISSUE-10 cure on `cputype == 40`, and **the very next screen requires a
68040 format-7 access-error frame** (`moveb %a0@(70)` … `cmpiw &7`).  A 68060 stacks **format 4**.
So even with the `cputype` gate removed the 060 would fall straight through to `Lhg_pass` on every
fault.  **Ungating the cure on 060 is therefore not a one-line change**, and the F4-M4 cure-gate
question is not decided by deleting a `cmpil &40,cputype`.  Registered as a portability finding
about the cure, entirely independent of whether candidate (c) is the cause of this stop.

## 6. Pre-registered expectations

* the banner, then `no fpu detected`, then build id `68060-260825-11`; the F1 rows must reproduce at
  the **shifted** §5.2 addresses — `fpi_n = 1`, `fpi_trap_n = 1`, `fpi_nofpu_n = 1`, `fpi_ok = 0`,
  the whole `fpc` block 0, `fpi_ss_pass_n = 0`.  Nothing in this round touches the FPU probe;
* `zc_magic` reads `ZCA!` and `z3660_cache` reads `0000003c`.  **If `z3660_cache` reads 0 the run is
  void** — the image booted was not the one intended;
* `uft_magic` reads `UFT!` and `uft_magic2` reads `UFF!`.  **If `uft_magic2` still reads 0 while
  `uft_n > 0`, the first-fault body did not run and the whole FIRST block is void, not negative**;
* **`swapconf` succeeds and no swap panic appears** — attempt 4's arm-B result must reproduce.  It
  has been seen exactly once, so this is a claim under test, not a background assumption;
* the boot reaches userland, PID 1 runs, and the `User BUS ERROR` wall reproduces.  **A boot that
  gets FURTHER than attempt 4 is a success and this document's tables simply do not apply** — the
  same rule attempt 3's §6.4 and attempt 4's §6.1 used;
* §3.1's three self-checks pass before any register row is read;
* Tables E through I are read **as written**, in that order, first matching row wins.  No row is
  re-scoped after the reading;
* the four ISSUE-52 blocks — `unt`, `srg`, `ini`, `iur` — are read on **every** boot.  `unt_n` must
  agree with `uft_n`: the two latches sit on the same call, one behind the other, so a disagreement
  means the chain is broken and both are suspect.

## 7. What attempt 5 will NOT prove — registered so it cannot be claimed afterwards

* **Not the F3-M3 canary.**  Still owed, and still not substitutable by any number of clean boots.
* **No decision on the ISSUE-10 cure gate.**  §4.1 sharpens what that decision would cost; it does
  not make it.
* **Nothing about `z3660eth`.**  Its arm stays COMMON and zero.
* **Not a coherency acceptance.**  Attempt 4 showed the driver's maintenance closes one stop; the
  load protocol (15/15 cycles, 8/8 canary binaries byte-identical) has not run.
* **No root cause for `0x4AFC0000` itself.**  The census names *where the value was* at the fault.
  It does not say who wrote it.  If Table F lands on G1, the next round needs a write-watch on
  libc's data page (`0xC102E000`–`0xC1031000`), for which `src/asfault_probe.s` and
  `src/sigkill_dbg.s` already scaffold nearly the right address range — that is a specification, not
  a result, and it is deliberately not built into this artifact.
* **No verdict on the `0x3000` XOR delta.**  §2.4 registers it as a lead.  Settling it needs a latch
  on `mc_state[0..3]` at `savecontext`'s stamp and again at `restorecontext`'s verify — a second
  override on a stock function, which this round declines to carry alongside the census.
* **No decision on the open `swd_vt_root = VNON` finding**, beyond the one row §4 buys for free:
  `uft_f_rd_vt` read under arm B.  **VDIR** there means the VNON belonged to the unarmed driver and
  collapses into the write-back class; **VNON** there means a mounted-root defect that owes its own
  investigation and its own instrument.  Either way it is one reading, not a root cause.
* No FP result, no full-68060 result, no durability result, no 100 MHz result, and **no dhrystone
  row** unless a boot actually reaches multiuser — in which case the pre-registered band
  (27,000–46,000) applies unchanged and the four `PLATFORM-LC060-Z3660.md` §4 readbacks ride with it.

## 8. The boot plan, and why it is this order

1. **`unix-060-f5uft-CARD1-ced0s1` first, and it is the only artifact that has to boot.**  It is
   attempt 4's arm B plus a read-only census, so it reproduces the exact frontier, and every row of
   Tables E through I is decided by **one `kpeek 0811161C 50`**.  Read the census before anything
   else, because the box is on a 15-minute clock and this block is the entire point of the session.
2. **The same artifact, a second time, from cold.**  Determinism is a *claim*, and attempt 4's `n=1`
   is not a measurement of it.  Registered: `uft_f_fa`, `uft_f_pc` and the sixteen register slots
   must reproduce **to the digit**.  If they do not, the fault is state-dependent, which puts it back
   into the coherency family and changes the whole reading — so this boot can overturn Table F
   regardless of what Table F said on boot 1.
3. **The four ISSUE-52 blocks on both boots.**  They cost one `kpeek` each, they were carried by
   attempt 4's artifact and left unread, and `unt_n` is the cross-check on the chain.

**Registered as deliberately NOT in the plan, with reasons, so their absence is not read as an
oversight:**

* **no `--cache 0` control this round.**  The cache A/B is settled; a control would stop at
  `swapconf` and never reach `init`, so it would answer a question nobody is asking and spend a
  thermal window doing it;
* **no `--dbg` combination.**  The swapconf probe shifts every counter address again and adds a
  second variable to a boot whose whole job is one counter block;
* **no I-cache arm.**  §2.3 refutes candidate (a) statically and Table E carries the test that would
  overturn that.  Building an arm against a refuted candidate would spend the round's one degree of
  freedom on the least likely mechanism.

are green in §5.1.  The rigs and their root images live outside this repository, so the rows below
are a **specification, not a result**.

That last is the load-bearing claim: **the census is inert where nothing is wrong.**  A bench boot with `uft_n > 0` means either the bench has a fatal user fault of its own or the hook sits on a hotter path than intended — and until that is explained, the metal boot is not read at all |
