## 1. The headline, in four claims

1. **The mechanism is named, and it is the piscsi driver's cache maintenance.**  A three-byte A/B
   settled it on silicon: `z3660_cache = 60` (arm B) closes the swapconf stop; `z3660_cache = 0`
   (the control) reproduces attempt 3 line for line and frame for frame.  The two images differ by
   exactly three bytes — two stamped value words and one build-id digit — so the delta belongs to
   **the value**, not to the relink and not to timing.
2. **The stale-READ-LINE form is refuted; the WRITE-BACK form survives.**  The DBG artifact pushed
   and invalidated the whole data cache between two identical five-lookup passes, with `CACR`
   bit 28 (DPI) proven clear, and got the same five `ENOTDIR`s back.  The wrong bytes were in RAM.
   Combined with arm B's success — the driver pushes *before* the transfer — the surviving
   mechanism is a dirty CPU line written back over freshly DMA'd metadata.  A later `cpusha` can
   never repair that; a push before the DMA prevents it.
3. **A new deterministic frontier, one giant step further along.**  Under arm B `swapconf`
   configured swap, the boot entered userland and `/sbin/init` (PID 1) executed — then looped on
   `User BUS ERROR at 4AFC0008, PC:C1027EAA FAULT:6 PID:1 CMD:/sbin/init`, ~182,741 signal
   deliveries, and ended at the stock guard `Bad ucontext checksum (0xFFFFCFFF) in process: init`.
   **No kernel panic at all** (`bt_walks = 0`).  Per the pre-registration's own rule this counts as
   a success of the change, not a failure of it.
4. **Multiuser was not reached on any boot, and no dhrystone row was taken or invented.**  The
   first-ever 68060 dhrystone is still owed, for the fourth session running.

Firsts on real 68LC060 silicon this session: `swapconf` configured swap; a user process executed;
`fpi_ss_skip_n > 0` — the F1 sendsig row attempt 3 had to record as NOT REACHED.

### 3.2 The open finding: `swd_vt_root` = 0 = VNON

`swd_vt_root` is `rootdir->v_type`, read at struct offset +24.  It read **0 (VNON)**.  What makes
that load-bearing rather than a probably-wrong offset is the bench control: the **same binary** at
the **same offset** read `2` (VDIR) on bench rig A the same day.  So offset +24 *is* `v_type` in
this kernel, and the 0 is a wrong **value**.

The corollary from the same block is what makes it strange.  Inside **one** in-core vnode:

```text
+8   v_op      080FFD38   -- correct (the bench read 070FFD38, the same symbol at its own base)
+24  v_type    00000000   -- wrong
```

Sixteen bytes apart, one right and one wrong.  A corrupt directory block read off the disk explains
a wrong `v_type` for a *component*; it does not obviously explain the **root** vnode, which is an
in-core object.  Two readings survive and this document declines to pick between them:

* the same write-back class caught in the act on an in-core structure — a dirty line covering part
  of the vnode written back stale over a field another agent had updated; or
* a genuine mounted-root/vnode-state defect that has nothing to do with caches.

Registered as a discriminator for the next round rather than explained here (see
`docs/060-F4-M2-ATT5-PREREG-260825.md` §4, candidate D).

### 4.2 The new stop, characterized at mechanism level

Console, the last screenful — one line repeated to the top of the screen, then one final line:

```text
NOTICE: User BUS ERROR at 4AFC0008, PC:C1027EAA FAULT:6 PID:1 CMD:/sbin/init
… (identical, filling the screen) …
Bad ucontext checksum (0xFFFFCFFF)in process: init
```

* `User BUS ERROR at %x, PC:%x FAULT:%x PID:%d CMD:%s` is **this port's own instrumentation**
  (`src/usptrap.s`, `src/patch_usptrap.py`), not a stock message.  `FAULT:6` = `FLTBOUNDS` per
  `usptrap.s`'s own header.  The first `%x` is the **fault address**; the second is the PC.
* `Bad ucontext checksum (0x%x)in process: %s` **is** stock — the string is in the linked kernel and
  has no source anywhere in this tree, i.e. it is stock SVR4's `ucontext` validation refusing a frame.
* PID 1 is `/sbin/init`, so **the first fork and the first exec both succeeded** — strictly further
  than boot 1 (whose fork failed) and than attempt 3 (which never left the kernel).  `CMD` is
  **populated**, which is itself a discriminator: `usptrap.s` registered an empty `CMD` as evidence
  that `exec` wrote `u_comm` through a wrong pointer, and this reads `/sbin/init`.
* The faulting address `4AFC0008` is above `0x40000000`, i.e. kernel-arena-shaped, taken from user
  text at PC `C1027EAA` (`C1xxxxxx` is user space on this port).  Same **class** as ISSUE-106 — a
  kernel-shaped pointer used in userland — different value, different PC.  Not root-caused here.
* It is a **loop**, and its size is measured, not estimated: `fpi_ss_skip_n` = `0002C9D5` = **182,741**
  deliveries through the F1 `sendsig` skip path.  Attempt 3 had to record that row as
  "NOT REACHED — the panic precedes proc 1".
* **It is not a kernel panic**: `bt_walks = bt_frames = bt_stops = bt_badret = 0`, i.e. the backtrace
  printer never ran once.
* **Liveness, measured rather than assumed:** `push_n` advanced 189 → 209 while observed and then
  froze; `fpi_ss_skip_n` read 182,741 twice, 20 s apart, unchanged.  The storm ran and then
  **stopped** — the machine ends quiescent after the `ucontext` refusal, not spinning.

`fpi`/`fpc` on this boot: `1/1/1`, `fpi_ok = 0`, `fpi_badfmt_n = 0`, PCR pre = post = `04310402`,
`savedvec 080E7670` — the F1 set reproduces unchanged.  `fpi_ss_pass_n = 0`, which is correct: with
no FPU every signal takes the skip arm.

## 7. The corroboration statement — neither artifact says this alone

* **DBG (Table B row 2, DPI proven clear):** a full CPU-side push + invalidate of the data cache
  between two identical lookups changed nothing.  The failure was therefore **not** a stale
  read-side line over good RAM — the wrong bytes were **in RAM**.
* **Arm B (with its three-byte control):** turning on the driver's own maintenance, which pushes
  dirty lines *before* a transfer and invalidates after it, makes the same lookup succeed.
  `push_n = 189` proves it ran on the path that mattered.

Put together, the surviving mechanism is the **write-back form** of the DMA/cache coherency defect:
without the driver's push, a dirty CPU line covering the DMA target is written back over the freshly
DMA'd directory or inode data *after* the transfer.  That is exactly why a later CPU-side
`cpusha` + invalidate cannot repair it — there is nothing good left to re-read — and exactly why a
push before the transfer does.  The stale-read form is refuted; the coherency **class** is confirmed,
at the driver.

What each would have been alone: DBG alone leaves "DMA landing in the wrong page", candidate 2, and
"a genuine namei defect" open.  Arm B alone cannot exclude "the extra cache ops changed the timing"
— which is precisely what the three-byte control excludes.

## 9. Deviations, retries and policy overruns — reported, not smoothed

1. **The brief's premise about the work root was wrong**, and measurement corrected it.  Attempt 3
   used `att3-work-root.hdf` and deleted it at close-out; the card held 51 files and no work root of
   any name.  A fresh copy was derived from the pristine template, which is the brief's own fallback.
2. **The template's CRC is not a constant**, and the gate changed accordingly.  Attempt 3 recorded
   `B62D34F1` for `metal-040-target-INSTALL1.hdf`; this session read `434FBF5F`.  Cause, established
   from the as-found config: that file **is** the standing emulated system's own root, and attempt 3's
   closing neutrality boot mounted it read/write.  It is a live system disk, not an immutable master.
   The gate used instead: device-CRC == host-CRC after download, plus the structural census, plus the
   ufs-patch fingerprints.  Its CRC was `434FBF5F` at both ends of this session.
3. **Precondition 1 re-derived and reproduced byte-exact.**  `mkfs_ufs` `779c0b64…` → patched
   `3361ade5…`; `fsck_ufs` `9ed9cc56…` → patched `d7097f46…` — identical to attempt 3's and to
   F2-M1's verified originals, read back through the reader each time.
4. **No dedicated parked-060 thermal baseline boot** was taken (attempt 3's precondition 9).  The
   reference baseline in §10 is attempt 3's, from the same rig, same firmware, the same morning.
   Stated as a deviation, not presented as an equivalent.
5. **Boot 2 needed two `Escape`s.**  The first did assert the reset, but the Expansion Board
   Diagnostic requester **re-raised on the post-reset pass**, which it had not done on boot 1 or on
   either of attempt 3's runs.  A second `Escape` dismissed it and the kernel ran.  Mechanical; no run
   was discarded and nothing was re-run to green.  The A2 ladder on that requester reproduced attempt
   3's exactly — Board 1 Z2 vendor 15163 product 200 `$40000000` 4MB Bad; Board 2 Z2 5195 3
   `$00E90000` 64KB OK; Board 3 Z3 5195 1 `$10000000` 128MB OK — the ghost still reads 15163 while
   everything the card emits reads 5195.
6. **Boot 2's real-CPU window ran ~19 minutes, over the 15-minute cap.**  Reported as a policy
   overrun.  Justification offered, not claimed as compliance: the window was extended to complete the
   §4.6 gate readout and the liveness probes, and the measured temperature was flat at 52.4–52.8 °C
   throughout, 7 °C below WARN.  Per `PLATFORM-LC060-Z3660.md` §2.7, a truncated or overrun run is
   reported as such and no durability claim rides on it.
7. **No neutrality boot** of the restored standing posture.  Attempt 3 ran one because it had flashed
   firmware; nothing was flashed here.  The restore is proven instead by byte-exact readback of all
   four config files, and the boot menu was reached on the restored config before parking.  A
   deliberate second benefit: the standing system disk was never mounted read/write, so it ends
   byte-unchanged.
8. **`[!!!PISCSI] Found no handler for file system UNI/1 | res/118 | UNI/0`** appeared after every
   `Escape`-reset on every boot.  Scored **NOT NEW**: byte-identical to attempt 3's set.  Mechanism:
   the AmigaOS-side handler scan over RDB partitions whose types are UNIX ones with no AmigaOS handler.
9. **The four ISSUE-106 counter blocks carried by the booted artifact were not read** — §4.3.
