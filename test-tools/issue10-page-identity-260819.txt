REPRODUCING THE RIG -- the two things that are not in the kernel or the script
-----------------------------------------------------------------------------
1. THE KERNEL NEEDS A SWAP-DEVICE EDIT BEFORE IT WILL BOOT THIS MEDIUM.  A kernel
   built straight from the tree names /dev/dsk/c6d0s2 as its swap device, and on
   a rig whose install SOURCE is the id-0 disk that is the wrong controller: the
   boot dies with

       PANIC: swapconf lookupname /dev/dsk/c6d0s2 failed - error 2

   Two bytes fix it, at fixed offsets from the anchor string "/dev/dsk/c", which
   occurs exactly once in the image:
       anchor-0x24  dev_t  0x00480016 -> 0x00480010   (makedevice(18,22->16))
       anchor+0x0a  the id digit in the name          ('6' -> '0')
   The generic host-side rootdev patcher REFUSES this image (its contract wants an
   sd-major root; this miniroot kernel has rootdev major 0), so the edit is made
   by anchor and verified by re-reading both fields.  COST OF NOT KNOWING THIS: it
   presents as a size effect.  Adding 4 bytes of .data to the tree "reproduced" the
   panic, and so did 944/200 bytes of pure padding with no code change at all --
   because every one of those variants was rebuilt from source and therefore
   carried the unpatched c6d0s2, while the only kernel that booted was a
   previously staged one that already had the edit.  Six boots were spent on that
   before the two kernels were diffed against each other.

2. THE PAYLOAD SLICE MUST BE MOUNTED READ-ONLY.  On any image whose slice 4 was
   previously mounted read-write and never unmounted -- which is every image a
   crashed or killed bench run leaves behind -- a read-write mount returns

       mount: mount of /dev/dsk/c0d0s4 as /cdrom failed: No space left on device

   with a root filesystem that is very nearly empty (154 blocks used).  Mounting
   the same slice READ-ONLY on the same image succeeds immediately.  A run that
   cannot mount its source disk still produces a full log of zeroes, which is
   indistinguishable from a measurement that found nothing.

THE TWO EARLIER MASKS, kept because each one refutes a reading of the third
-------------------------------------------------------------------------
  vmask 0xFFFF0000 (a 64 KiB band, the first guess):
      hits=8 of 51 pages; latched uva=80006000 pte=0767b02d pfn=767b pp=400524f8
      p_vnode=400e1108 p_offset=00006000 p_mapping=07667018 (== its own ptea)
      mapn=2 min=1 hoff=92c hitv=4afc0055
      w0..w7 = [32 bytes of /bin/sh text -- verified host-side, not reproduced]
    VERIFIED HOST-SIDE against the miniroot's own /bin/sh: the frame's first eight
    longs are that file at offset 0x6000 byte for byte, and 0x4AFC0055 is that file
    at offset 0x692C.  So the band mask matches sh's OWN CODE -- 0x4AFC is the 68k
    ILLEGAL opcode and occurs at four places in that binary (0x692c, 0x8668,
    0xadee, 0xcdc4).  The page is not corrupt; the instrument was.
    It also proves the probe reads the right frame and reports it accurately.

  vmask 0xFFFFFFFF (the fault address exactly):
      hits=1 of 102 pages; latched uva=c07ff000 (the user stack) pfn=762f
      pp=40051328 p_vnode=40078704 p_offset=00034000 mapn=1 min=1
      hoff=9a0 hitv=4afc0003; w0..w7 ALL ZERO
    One word, and it is 0x4AFC0003 -- the fault ADDRESS, on the stack, i.e. the
    kernel's own residue by the second walk of a flood thousands deep.  Not the
    corruption.  Note the SAME vnode 0x40078704 as the heap page above at a
    different offset, which is what an anon/swap vnode looks like.

  The exact byte string 4A FC 00 00 occurs ZERO times in /bin/sh, so the link
  match in the main capture has no innocent explanation available to it.
