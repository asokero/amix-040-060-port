5b. ** ISSUE-29 ON REAL HARDWARE FOR THE FIRST TIME — sighting #5 **
-------------------------------------------------------------------
    DBG KMEMCORRUPT bin=80ED9F0 blk=40259300 next=8 prev=6 caller=8042334 size=1

  Exactly ONE occurrence in 152 374 bytes of log, at offset 21484 = 14% in, i.e. BEFORE
  the mid-session reboot.  So it happened during the FUNCTIONAL battery, NOT during
  pressure.sh or burst4 — both of those ran clean, which is worth stating because pressure
  is where one would expect it.

  Three things are new and they turn this from an emulator curiosity into a lead:
   1. It occurs on SILICON.  All four previous sightings (three on 2026-07-25, one on
      emu-060 on 2026-07-26) were emulator-only.
   2. The SHAPE MATCHES the 2026-07-25 emulator sightings: same caller=8042334, same
      next=8 prev=6.  (The 2026-07-26 emu-060 sighting had next==prev, a different shape.)
      Sizes differ across sightings: 0x8C on 07-25, 1 here.
   3. caller 0x8042334 resolves to **kmem_zalloc + 0x18** — the instruction right after
      `jsr kmem_alloc` inside kmem_zalloc.  So the corrupted blocks come from kmem_zalloc,
      not from kmem_alloc directly and not from the KMA pools.

  And the values themselves are informative: next=8 / prev=6 are SMALL INTEGERS sitting
  where free-list POINTERS belong.  That looks like an index being written over a pointer,
  not a wild address or a poison pattern.

  Still NOT attributed and not chased — the project's own rule after several ruled-out
  hypotheses is to record and redirect.  But five sightings with a consistent caller and a
  consistent corrupted-value shape is no longer noise.

5. ** NEW DEFECT FOUND: NFS WRITE LOSES 2048 BYTES — REPRODUCIBLE, SERVER-VERIFIED **
-------------------------------------------------------------------------------------
Found on the very first NFS write of the session.  This is NOT part of the delta the run
was validating; it is a pre-existing defect that had never been exercised.

  A file whose length is an EXACT MULTIPLE OF 8192 loses exactly its last 2048 bytes when
  written to NFS.

  size sweep, all written with dd from /payload.bin to nasu:Public over NFS:
      requested   stored     lost
        100         100        0
       2048        2048        0
       3000        3000        0
       4096        4096        0
       6144        6144        0
       8192        6144     2048     <- 2 x 8192
      10240       10240        0
      12288       12288        0     <- 3 x 4096 but NOT a multiple of 8192
      16384       14336     2048     <- 2 x 8192
      24576       22528     2048     <- 3 x 8192
      32768       30720     2048     <- 4 x 8192
    4194304     4192256     2048     <- 512 x 8192 (the historical /payload.bin)

  Controls that make this a kernel defect and not an artifact:
   * LOCAL control clean: the same `dd bs=1 count=8192` to local UFS gives 8192 three
     times out of three.  Only the NFS destination loses data.
   * Deterministic: 3/3 identical short writes at 8192.
   * NOT flush latency: sync + 5 s wait did not change the sizes.
   * SERVER-SIDE VERIFIED from a different client and a different protocol — read back
     over SMB from Linux: 4 192 256 bytes, and the file ends at page offset 2048 of 4096,
     i.e. the final 4 KiB page's UPPER 2 KiB half was never written.

  Mechanism, consistent with the numbers: 8192 = MAXBSIZE / the segmap slot, and 2048 is
  the stale page size.  nfs_putpage computes its write-out extent with 2 KiB arithmetic
  against a 4 KiB page population, and at an exact block boundary the final half page
  falls outside the computed range.  This is the ISSUE-27 class (4 KiB producer, 2 KiB
  consumer) and it is exactly the family Codex ranked #1 for implementation:
  vm-map/NFS-PROVIDER-RESIDUAL-CLOSURE.md, nfs_putpage, six unconverted sites.  Codex
  predicted a "server-verifiable data-loss test" for this group; it turns out not even to
  need mmap — a plain cp does it.

  ATTRIBUTION NOT PROVEN.  It is consistent with the Model-B asymmetry (on a 2 KiB kernel
  nfs_putpage's arithmetic would be correct, which would make this our regression), but
  the discriminator — booting the stock 030 kernel, or an 040 kernel with nfs_putpage
  converted — has not been run.  Do not record it as caused by our work until it has.

  Practical impact: every file whose size is an exact multiple of 8 KiB written to NFS
  from this machine is silently truncated by 2 KiB.  That includes tar archives.

  Evidence files left in place on the NAS at amix/hwtest-260727/ by request.
