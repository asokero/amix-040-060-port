WHAT THIS IS.  i10p_probe (part two) and the frame census (part three of the
document) had established that the poisoned longword 0x4AFC0000 at user
0x80014AA0 arrived by a STORE into a cleanly zero-filled page, not by a fill-tail
or a page-lifetime defect.  i10w_hook write-protects that page and reads the
68040 format-7 access-error frame of every store into it, so the store that
poisons the longword is caught AS IT LANDS -- PC, privilege, effective address,
value and register file.

THE INSTRUCTION.  Verified against /bin/sh in the source image at file offset
0x23F8 (VA 0x800023F8; sh's text VA base is 0x80000000), byte for byte:
  800023f8:  2091               move.l  (a1),(a0)    ; the STORE: (a0) := *(a1)
  800023fa:  2250               movea.l (a0),a1      ; a1 := (a0)
  800023fc:  0829 0000 0003     btst    #0,3(a1)     ; the flood read -> 4AFC0003
  80002402:  6700 fff4          beq.w   0x800023f8   ; loop
This is /bin/sh's own free-block coalescing loop (`p->word = q->word`).  The
format-7 frame's PC is 0x800023FA -- one instruction past the store -- because
the 68040 defers the store's write-back (WB3), which is the entire reason wb040.s
exists; WB3A/WB3D carry the store's true target and data.

VERDICT.
  * The write into user 0x80014AA0 is a USER store (SR S=0, PC in /bin/sh's own
    text), NOT a kernel copyout/bcopy/pagezero and NOT a mis-addressed store.
  * The store is CORRECTLY addressed: (a0) = 0x80014AA0 is exactly where sh's
    coalescing loop means to write the link.  There is no off-by-N, no wrong
    base -- "intended == actual" for the address.
  * The store is `move.l (a1),(a0)`, a memory-to-memory COPY.  Its value
    0x4AFC0000 is *(a1) -- read from another slot of sh's own arena that ALREADY
    held the poison.  So this store PROPAGATES a corrupt free-list link; it does
    not originate it.
  * Therefore the "mis-addressed single store into a clean page" reading (H2, and
    the kernel-store corner of it) is REFUTED for the 0x80014AA0 site.  The
    corruption is a free-list LINK that became 0x4AFC0000 upstream, and /bin/sh
    faithfully carries it forward until it dereferences it and walls.

NEXT.  The genesis -- what first wrote 0x4AFC0000 into a free-list link -- is the
remaining thread, and it is a DIFFERENT address (the source *(a1), on page
0x80013000 in this run, judging by the a0/a3/a4/a5 = 0x80013xxx free-list cursors
in the capture) that this watch, pinned to page 0x80014000, did not cover.  The
follow-up probe is a value-triggered watch: protect the arena and latch the FIRST
store whose WB3 data is 0x4AFC0000, wherever it lands.  That capture will say
whether the genesis is a kernel store (the still-open question) or sh's own
allocator computing a bad link -- and only then is the "kernel vs user" question
closed for the genesis rather than for this one propagation.
