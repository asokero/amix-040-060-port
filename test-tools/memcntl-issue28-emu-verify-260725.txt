================================================================================
WHY THIS IS A REAL DEFECT (and it is the SAME shape as ISSUE-27)
================================================================================

The mlock bitmap has a producer and a consumer, and only the producer was converted:

  as_ctl        0xaeafe   ALREADY 4 KiB   (patch_modelb.py:333-337)
  segvn_lockop  0xad2f0   ALREADY 4 KiB   (patch_modelb.py:302-307)
      ^ these FILL and index the bitmap in 4 KiB page units

  memcntl       0x4319a   was 2 KiB       <- SIZES the bitmap
  mem_unlock    0x434b6   was 2 KiB       <- WALKS the bitmap

Consequences on the pre-fix build:

  (a) `if (((int)addr & PAGEOFFSET) != 0) return EINVAL` used 2047, so a 2048-aligned
      but NOT 4096-aligned address passed the gate; as_ctl then masked it down to a
      4 KiB boundary and operated on a DIFFERENT range than the caller requested.
      *** This is what mlocktest T1 measures, and it is a clean discriminator. ***
  (b) mlock_size = BT_BITOUL(btoc(rlen)) with >>11 allocated twice the bits needed.
      Harmless over-allocation by itself, but the same divergence.
  (c) On the MC_LOCK / MC_LOCKAS FAILURE path, mem_unlock got 2 KiB-based bit indices
      (inlined btoc(seg->s_size)) for bits that were SET with 4 KiB indices, and its
      own ctob() halved both the byte offset and the byte length passed to
      as_ctl(MC_UNLOCK) -- so the rollback unlocked the WRONG address range: pages
      stay locked forever (pages_pp_locked/availrmem drift) while MC_UNLOCK is issued
      against ranges that were never locked.

Source contract: svr4-src-3b2/usr/src/uts/3b2/os/lock.c:266-415.

================================================================================
CLASSIFICATION -- 21 raw pattern matches, 17 real sites, 4 FALSE POSITIVES
================================================================================

A naive "#2047 / #2048 / #-2048 / moveq #11" scan over 0x42e7c..0x43544 returns 21
hits.  Four of them are NOT page geometry; each was read in context:

  0x42f58  textlock      moveq #11,%d0  = return EAGAIN (errno 11), then braw to exit
  0x42fde  datalock      moveq #11,%d0  = return EAGAIN
  0x43080  ublock        moveq #11,%d0  = return EAGAIN
  0x43212  memcntl       moveq #12,%d0  = return ENOMEM (errno 12), after
                                          valid_usr_range() fails
  (+ 0xad54e segvn_lockop moveq #11 = return EAGAIN, outside this range)

Converting any of those would silently change the errno a lock path returns.  The
patch script therefore asserts all five as CANARIES on every run.

Also deliberately NOT touched:
  ublock/ubunlock `subql #4` / `addql #4` on availrmem + pages_pp_locked = USIZE in
    PAGES.  It MATCHES segu_release @0xaa78e, which charges the same 4 pages.
    Changing one without the other would break u-area accounting.
  memcntl 0x4339a `addaw #31` + 0x433a0 `lsrl #5` = BT_BITOUL(), bits -> longs.
  segvn_lockop 0xad482 / 0xad536 `pea 0x800` = segvn_fault LENGTH args, deliberately
    withdrawn 2026-07-03 after the seg-family fault-len batch hung the boot
    (patch_modelb.py:576-582).  Not part of the bitmap contract (segvn_lockop's loop
    step and bit indices are already 4 KiB) -- they stay withdrawn.

The 17 converted sites: 0x431f4 (PAGEOFFSET gate); 0x4331c/0x43328/0x4332e
(MC_LOCKAS rlen); 0x43348/0x43352/0x43358 (MC_LOCK normalize); 0x4338e/0x43394
(btoc(rlen) for mlock_size); 0x43420/0x43428/0x4342e/0x43450/0x43456 (MC_LOCKAS
failure-path rollback); 0x43472/0x43478 (MC_LOCK failure-path btoc); 0x434ee
(mem_unlock ctob -- ONE moveq feeds BOTH lsll: byte offset AND byte length).

================================================================================
!! HONEST GAPS !!
================================================================================

1) THE FAILURE PATH (defect (c) above) IS NOT DIRECTLY EXERCISED.  mlocktest proves
   the alignment gate and the success-path round trip plus accounting stability over
   30 lock/unlock cycles.  It does NOT force an MC_LOCK/MC_LOCKAS failure, which is
   what makes mem_unlock walk the bitmap -- doing that deterministically needs
   lockable memory to be exhausted mid-operation, which I could not arrange safely.
   The failure-path conversion is therefore argued statically (it now matches the
   already-4 KiB as_ctl/segvn_lockop indices) and is NOT runtime-proven.

2) T2-T5 pass on BOTH kernels.  Only T1 discriminates.  That is expected -- the
   success path does not diverge -- but it means the runtime evidence for 16 of the
   17 sites is "no regression", not "proven correct".

3) NOT DONE: real hardware.  Amiberry emulation only.

4) memcntl(2)/plock(2) are not used by anything in the normal AMIX workload, so this
   fix removes a latent defect rather than a symptom anyone was seeing.
