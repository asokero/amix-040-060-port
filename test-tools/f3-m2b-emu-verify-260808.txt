5. D2 settled by measurement: FULL fpsp.sa, not pfpsp.sa
---------------------------------------------------------
The two packages have byte-identical entry-point tables (M1), so this could only be decided
by running.  Built with `FPSP060_VARIANT=pfpsp FPSP060=1 sh relink-040.sh` (new switch),
emulated 060, same probe:

  fadd/fsqrt/fintrz  OK
  fsin/fetox/flogn/fmovecr  DIED by signal 12 (SIGSYS)
  FP060PROBE bad=4

and the counters name the mechanism instead of leaving it to inference:

  f60_entry_n   4     the partial package IS entered -- the wiring is identical
  f60_mem_n     0     it never even fetches the instruction
  f60_real_n    4     it declines
  f60_fline_n   4     ...through _060_real_fline
  f60_last_co   7     = the fline slot
  f60_done_n    0

Byte-exactly what Codex predicted statically from pfpsp.s:3817-3854 ("does not emulate FP
unimplemented instructions").  Full package it is.

6. Motorola's own ftest -- and why its "failed" is NOT ours
------------------------------------------------------------
build-ftest060.sh converts dist/ftest.sa (NetBSD did not; only fpsp/pfpsp are converted in
that tree) and builds it as an AMIX user program: 128-byte call-out section -> printf, then
the image, then the runner.  The FPSP under test is the kernel's.

  ftest060 main     "Unimplemented <ea>..."  DIED by signal 9
  ftest060 unimp    "Unimplemented FP instructions...1 failed"
  ftest060 enabled  "Enabled SNAN/OPERR/overflow/underflow/DZ/inexact...1 failed" (all six)

Attribution, one item at a time:

* main -> SIGKILL is vector 60 (unimplemented effective address), which is F3 M3 and
  deliberately not hooked.  Expected.

* enabled -> f60_arith_n stayed 0 and f60_entry_n did not move for any of the six.  The
  emulated FPU never raised an enabled FP exception, so neither the package nor our
  _060_real_* exits ran at all.  These six exits are therefore UNMEASURED, not broken, and
  they stay that way until hardware.  Recorded rather than glossed.

* unimp "1 failed" -> chk_test prints the sub-test counter and nothing else, so
  test-tools/ftunimp0.c replicates sub-test 1 (unimp_0) exactly and prints every field
  Motorola compares.  Result:

      fp0    BFBF0000 80000000 00000000   OK   (all 96 bits)
      fpcr   00000000                     OK
      fpsr   08000208                     OK   (N + INEX2 + accrued INX)
      fpiar  = the fsin's own address     OK
      ccr    0000                         OK
      d0-d7/a0-a6 unchanged across the trap     OK

  The instruction is emulated correctly in every respect the suite specifies.  What fails is
  upstream of the FPSP:

      FPU CANNOT HOLD DEF_FPREGS: group 0..7 loaded 7FFF0000 FFFFFFFF FFFFFFFF,
                                  read back 3FFF0000 00000000 00000000 before any trap
      -> 8 of 8 FP registers mangled by the LOAD alone

  Every ftest sub-test begins with `fmovm.x DEF_FPREGS,&0xff` -- that extended NaN into all
  eight FP registers -- and ends by requiring fp1-fp7 to be unchanged.  The snapshot above is
  taken between the load and the fsin, so no kernel code has run; the emulated 68060 FPU
  simply cannot represent the value.  ftest cannot pass under Amiberry whatever the FPSP does.

  CONSEQUENCE: Motorola's suite is built, runs, and is correctly wired, but its verdict is
  owed from real silicon.  It is on the M5 run list.
