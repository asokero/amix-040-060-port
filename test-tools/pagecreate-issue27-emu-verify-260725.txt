================================================================================
!! THE DEFECT WAS NOT REPRODUCED -- THIS IS THE HEADLINE, NOT A FOOTNOTE !!
================================================================================

The spec's own acceptance test was implemented faithfully (test-tools/pgcreatetest.c)
and run on the PRE-FIX kernel.  It found NOTHING.

  probe (spec section "Acceptance test"):
    file with a fully written first 8 KiB UFS block
    write 100 B at 8192   -> start of a new UFS block, page-aligned -> pagecreate=1
    write  10 B at 11192  -> 8192+3000, not page-aligned -> no pagecreate
    read back and require the never-written bytes to be zero
    pre-fix zero-fill stops at roundup(8292,2048) = 10240, so [10240,...) should be
    the recycled physical page's old contents

  results, pre-fix kernel 68040-260725-06:
    64 iterations, page pool churned before each batch:   0 hits
    (an earlier 32-iteration run with a different churn method: 0 hits)

Two independent strengthenings were applied and neither changed the outcome:

  1. A wider observation window.  The spec's window [8292,11192) is only 952 bytes.
     Adding a third write of 1 byte at 12287 -- still inside the SAME 4 KiB page and
     not page-aligned, so it takes no pagecreate and no zero-fill -- makes the whole
     rest of the page file contents and widens the window to [10240,12288).
  2. Better-targeted page poisoning.  The first version dirtied anonymous memory in a
     forked child; that is both very slow under emulation and the wrong population.
     It was replaced by churning MARKER (0xC5) pages through a scratch file that is
     then unlinked -- file cache pages, which is exactly what the probe's page_get
     recycles.

It was separately confirmed from the binary that the mechanism is not defeated by
zeroing somewhere else: page_get (0xaffa4) and page_free (0xaf9ea) contain NO
pagezero/bzero/kzero call.  The only pagezero callers are the getapage providers
(spec/s5/ufs, for holes) and anon_zero.  So a page recycled into segmap_pagecreate
genuinely carries its previous contents.

WHAT THIS MEANS, STATED PLAINLY:

  * Per the spec itself ("A pre-fix hit is expected but not guaranteed; a no-hit
    pre-fix run is inconclusive"), this does NOT disprove the defect.
  * But it does mean the post-fix "CLEAN" result is NOT evidence that anything was
    fixed -- both kernels behave identically on this probe.
  * The claim "live silent data leak on the root filesystem" is therefore NOT
    supported by runtime evidence on this configuration.  It is supported only by
    static reading (mine and Codex's).  Until someone reproduces it, ISSUE-27 should
    be described as a proven-by-construction correctness defect of unknown live
    reachability -- not as an observed leak.
  * The most likely masking mechanism, and the open question for Codex, is the
    second write: with pagecreate=0 it goes to ufs_bmap with alloc_only=0, which can
    do a read-before-write (fbread) of the block and refill the page from disk.
    Codex already anticipated masking of this general kind ("it can be masked by UFS
    fragment growth and fbread") and gave the 8192/11192 probe as the stronger
    alternative -- and that stronger probe does not fire either.

FOLLOW-UP QUESTION FOR CODEX (concrete, not a guess):
  Why does the specified probe not fire on this image?  Specifically: for the second
  (non-page-aligned) write into a page created by an earlier pagecreate, does
  ufs_bmap(alloc_only=0) issue an fbread that refills the page from disk and thereby
  overwrite the un-zeroed tail?  If so, what probe WOULD expose the tail -- e.g. is
  the exposure only reachable via mmap, via a reader that faults the page before the
  second write, or via putpage writing the full page to disk?

The disk-truth gate matters most here: it is the check for RISK #1 below, because it
exercises heavy allocation plus writeback through the converted path and then reads
the bytes back from the platter after fsck.

================================================================================
RISK #1 -- ufs_bmap, deliberately left unconverted
================================================================================

rwip does not merely zero a tail: it passes `pagecreate` onward as ufs_bmap's
`alloc_only` argument, so this conversion changes UFS ALLOCATION and
read-before-write behaviour, not only zeroing.  And ufs_bmap (0x79d48) is itself
still 2 KiB in eight places:

  0x79d74  cmpil #2048      0x79d7e  movel #2048      0x79d96  cmpil #2047
  0x79da4  addil #2047      0x79daa  moveq #11        0x79ec0  moveq #11
  0x79ee2  moveq #11        0x7a030  moveq #11

The spec is explicit that these are a separate provider/allocation audit and must NOT
be converted by matching constants mechanically, while still requiring the pagecreate
decision itself to move to the 4 KiB contract.  That is a defensible call, but it
creates a new producer/consumer boundary -- the exact defect class that bit twice in
one day (ISSUE-27 itself and ISSUE-28).  The disk-truth + fsck gate is the mitigation,
and the ufs_bmap audit is the natural next Codex brief.
