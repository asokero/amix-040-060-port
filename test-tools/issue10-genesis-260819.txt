src/wb040.s resolved-tail hooks).  Guest driver test-tools/i10g.sh.

WHAT THIS IS.  i10w_hook (write-watch) had named the PROPAGATION -- sh's coalescing
loop at PC 0x800023F8 copying an already-corrupt free-list link into 0x80014AA0 --
and left the GENESIS open: what FIRST put 0x4AFC0000 into a link, and whether that is
a kernel store, a user store, or inherited frame content.  i10g_hook answers it.  It
write-protects a heap band and, on the store faults that forces, records for the FIRST
resolved fault whose landed value is the poison: the storing PC and privilege (PART W),
the frame the poison appears in with its fill census (PART I), and -- the decisive
field -- the value each of the store's address registers points at (so a genuine copy,
whose source memory holds the poison, is told from a store whose write-back value has
no source at all).

VERDICT.
  * WRITTEN, not inherited.  The page is cleanly zero-filled; PART I catches the poison's
    FIRST appearance as a store (iself=3), not as pre-existing content.  A companion run
    that write-protected page 0x80013 and scanned it after all 3320 of its forced store
    faults found the poison there ZERO times, so it does not transit that page either.
  * A USER store, not a kernel one.  SR S-bit clear, PC in /bin/sh's own text; and the
    kernel-store wrapper (krnxmemflt, ctx=2) never latched.  So no copyout/bcopy/mis-
    addressed kernel write put it there.
  * The value has NO SOURCE.  Not copied from memory (no operand points at it), not a
    register value, not an immediate.  For a move that lands 0x4AFC0000 while its source
    holds a valid token, the value is generated by the 68040 store / deferred-write-back
    mechanism itself -- the "write-back fidelity" family.  This is consistent with the
    two facts the record already held: the constant is 0x4AFC = the m68k ILLEGAL opcode,
    and the fault does NOT reproduce on the 68060 (whose write-back path differs).

  STATED CONFOUND.  The capture forces the store to fault (write-protect), which routes
  its completion through the 68040 write-back replay (src/wb040.s).  So this capture, by
  itself, cannot separate "the emulator's 040 core fabricates the value on the ordinary
  store" from "the fault-driven replay fabricates it"; both are the same 68040-write-back
  surface.  The poison is independently real -- i10cen.sh detected 0x4AFC0000 at 0x80014AA0
  read-side, with no write-protection at all -- so the corruption is not an artifact of the
  watch; what the watch adds is that the landed value has no data source.

  NEVER RUN ON 68040 SILICON.  All of this is emulated, on two different emulators, and
  the 68060 does not reproduce it.  A store-mechanism defect that is 040-specific and
  emulator-reproduced may be a 68040 EMULATION defect rather than a port defect -- in
  which case the setup.sh wall would not occur on real 040 hardware.  A non-write-protect,
  single-step capture of the ordinary (non-faulting) store is the follow-up that separates
  the emulator core from wb040_replay and, ultimately, from real silicon.
