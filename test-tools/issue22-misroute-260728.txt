ISSUE-22 NAMED ON REAL HARDWARE -- the fault is MISROUTED, not nested
=====================================================================
2026-07-28 evening, A3000 + Mercury 040, kernel 68040-260728-36 (copyback + the FAILEXIT probe).
amix-040-060-port HEAD 733d118.  Serial capture /tmp/amix-issue22-hunt.log, offset at run start 218343.

THE DECISIVE LINE
-----------------
    WARNING: DBG krnxflt FAILEXIT w=2 va=800C96B0 rw=2 depth=1

    w=2     no kas segment owns the fault address   (as_fault is NEVER called on this exit --
                                                     which is why the as_fault FAIL logger, cap 64
                                                     and unused, stayed silent through every hit)
    depth=1 no nesting whatsoever
    va, rw  VALID on this exit (only w=1 has them uninitialised)

WHAT IT REFUTES
---------------
Codex's static analysis (amix-kernel-analysis vm-map/ISSUE22-EFAULT-SOURCE.md, f757544) predicted
    DBG krnxflt FAILEXIT w=1 ... depth=5
from the global Lkx_depth counter aggregating concurrent sleeping resolvers.  The counter IS global
and IS held across as_fault (verified in src/krnxmemflt040.s:52/272 -- that part of the
analysis is correct), but it is not what fires:

  * depth=1 at the failure.
  * Lkx_depth read live through /dev/mem: 0 at rest before the run, 0 at rest after the failure.
    No leak, no elevated resting value, on this boot or on the previous -32 boot.

The depth cap remains a latent design defect worth fixing on its own terms (a machine-wide counter
compared against a per-context limit), but it is NOT ISSUE-22.

WHAT IT NAMES
-------------
va=0x800C96B0 is inside b2verify's own freshly malloc'd 4 MiB heap buffer (srcbuf, 760 KB in), and
rw=2 is a WRITE: this is copyout filling a user buffer during read(2).  The fault on that user page
was handed to the KERNEL resolver, which looked the address up in the kernel address space:

    read(2) -> rwip -> uiomove -> copyout -> lcopyout (DFC = user data, movesl)
      page fault on the user destination
        k_trap 0x5a19e   tstl u+0x374        nofault pad armed?  yes -> classify
        k_trap 0x5a1ca   jsr userspace       <== THE ROUTING DECISION, one call site in the kernel
                         returned 0 = "kernel"
        k_trap 0x5a1fe   jsr krnxmemflt
          krnxmemflt040  as_segat(&kas, 0x800C96B0) = NULL   (stock contract, verbatim at 0x5b19e
                                                              in the vanilla body)
          -> unresolved, no as_fault call            -> w=2
        k_trap 0x5a212   saved PC := u_nofault pad
        sf_fault 0x5f2   -> copyout returns -1 -> uiomove 0x43b54 -> EFAULT
    cp/b2verify: "read: Bad address"

The classifier is right almost always: the same run resolved on the order of 90000 copyout page
faults and misrouted ONE.  So userspace() normally reads function code 1 (user data) out of the
040 SSW at frame+76 and occasionally reads something else.  WHAT else is the open question; the
next probe answers it by printing the raw SSW.

This also corrects a written assumption in KNOWN-ISSUES' own ISSUE-22 section ("a guarded MOVES
fault has transfer mode = user, so k_trap dispatches it to usrxmemflt").  Usually true; measurably
not always.

ROOT CAUSE, FOUND BY READING AND THEN MEASURED: wb040.s EATS THE DFC REGISTER
=============================================================================
Verified byte-exactly in the stock binary:

    000005a0 <lcopyout>:
         5a0:  moveq #1,%d0
         5a2:  movec %d0,%dfc           <-- DFC = user data, set ONCE
         5c0 <lcolloop>: movel %a0@+,%d1 ; movesl %d1,%a1@+ ; subql #4,%d0 ; bgel
         5d6 <lcol2>:    moveb %a0@+,%d1 ; movesb %d1,%a1@+ ; subql #1,%d0 ; bnel
         5e4 <lcodone>:  clear the pad, return 0
         5f2 <sf_fault>: clear the pad, return -1        <-- what uiomove turns into EFAULT

The loop never reloads DFC.  Note also that its source read is a PLAIN movel from the kernel
segmap -- that is the supervisor-data fault our probe counts by the thousand.

src/wb040.s's Lwb_do sets DFC = WBxS&7 to re-issue a pending write-back with the faulted
access's function code, and never restores it.  DFC is not saved by the exception mechanism, so
the value survives the rte back into the interrupted copy loop.  From there:

    next movesl uses DFC=5 -> a USER address is looked up in the SUPERVISOR tree -> access error
    with TM=5 -> userspace() reads the frame CORRECTLY and says "kernel" -> krnxmemflt ->
    as_segat(&kas, userVA) = NULL -> unresolved, no as_fault -> sf_fault -> EFAULT

MEASURED on 68040-260728-45, which counts the mechanism instead of waiting for its symptom:

    one boot, nothing else running
        wb_replay_n     4747     write-back replays performed
        wb_replay_odd    218     ...of those, replays that set DFC to something != user data
        wb_dfc_changed   218     faults that returned with a DFC the caller did not set
        wb_dfc_lastold     1     what the interrupted code had   (user data)
        wb_dfc_lastnew     5     what the replay left behind     (supervisor data)

    The two 218s are the same events counted at two different places: every odd-FC replay
    corrupts, none of them is repaired by anything else.  1 -> 5 is the exact pair the theory
    predicted before the counter existed.

    30 s of cofault (six processes doing nothing but read into fresh malloc'd buffers)
        wb_replay_n    +6472
        wb_replay_odd     +0     <-- and this is why cofault never reproduces ISSUE-22
        wb_dfc_changed    +0

That last line is the useful negative result.  A pure read workload generates thousands of
replays and not one of them carries a non-user function code, because the only pending stores
are the copy's own.  The hazard needs a pending SUPERVISOR store at the moment of a copy fault,
which is what boot activity and b2repro's concurrent disk copies produce and cofault does not.
It also explains the rarity: DFC has to be corrupted WHILE a copy is still mid-loop, since the
next copyin/copyout call sets it again.

CAUSAL CHAIN CLOSED BY INJECTION, 2026-07-29, kernel 68040-260729-03
====================================================================
The natural event is too rare to A/B (a 12-burst control run gave 25 corruptions and zero EFAULTs),
so the corruption was injected instead: `wb_dfc_force` leaves a chosen function code in DFC for the
next N faults, at exactly the point in the wrapper epilogue where a leaking replay would have left
it -- BEFORE the restore, which is what makes the same test an A/B of the FIX and not only of the
mechanism.  `dfcinject` arms it from inside the test process, microseconds before the read it is
meant to hit.  Both halves ran in the same boot, one .data long apart, in two seconds:

    A  wb_dfc_on = 0     DFCINJ RESULT read_total=0        errno=14  injections=3
                         VERDICT EFAULT -- the leaked DFC broke the copy
    B  wb_dfc_on = 1     DFCINJ RESULT read_total=1048576  errno=0   injections=40
                         VERDICT CLEAN -- the copy completed under injection

Serial during A, and this is the point of the whole exercise -- the injected leak reproduces the
ISSUE-22 signature exactly, including the `w=2 ... rw=2 depth=1` that was captured by chance a day
earlier at a completely different address:

    WARNING: DBG userspace ODD fmt=7 fc=5 fa=80003228 ssw=85
    WARNING: DBG krnxflt FAILEXIT w=2 va=80003228 rw=2 depth=1

    ssw 0x85 = TM 101 (supervisor data, the injected DFC) + RW 0 (write) at a USER address.

Counters, all read from /dev/mem with `xpage_on == 1` anchoring the range:

| | baseline | after A (fix off) | after B (fix on) |
|---|---:|---:|---:|
| `us_odd_user` misroutes | 0 | **1** | 1 |
| `Lkx_fn` FAILEXIT prints | 0 | **1** | 1 |
| `wb_dfc_forced` injections performed | 0 | 3 | 43 |
| `wb_dfc_changed` corruptions seen | 213 | 214 | **254** |
| `wb_replay_odd` natural odd replays | 213 | 213 | 213 |

Read the last two rows together: with the fix on, the wrapper detected and repaired **40**
corruptions during a single 1 MiB read and the copy completed byte-complete, while with the fix off
**3** were enough to abort it at zero bytes read.  `wb_replay_odd` unchanged confirms the injection
was not conflated with natural replays.

WHAT THIS DOES AND DOES NOT PROVE
* Proven: a leaked DFC produces the ISSUE-22 signature deterministically, and the fix neutralises it.
* Not proven: that every historical ISSUE-22 event was a DFC leak. The support for that is the
  identical signature, 218 natural leaks per boot with the exact `1 -> 5` pair, and Codex's census
  (`vm-map/ISSUE22-DFC-ARCH-STATE-AUDIT.md`, 7c314b2) finding no other architectural state leaking
  out of the fault path. A natural-rate A/B remains the last confirmation, and it is now
  confirmation rather than primary evidence.

THE FIX
-------
Treat DFC as what it is -- a register belonging to the interrupted code.  Save it on entry to
the fault wrapper, restore it before returning.  In the WRAPPER, not in Lwb_do:
  * nesting-safe: each invocation has its own frame, so a nested fault inside a replay restores
    the OUTER replay's DFC, which is the value that loop still needs;
  * Lwb_do cannot use the stack at all -- k_trap lands an unresolvable nested fault on Lwb_fail
    with the trap-time SP, and its rts expects the stack exactly as bsr left it.
wb_dfc_on = 0 restores the old behaviour in one .data long, so the A/B runs inside one boot.
