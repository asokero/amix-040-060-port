================================================================================
ISSUE-17/18 -- THE HEADLINE RESULT
================================================================================

ISSUE-17 was recorded as "can hold/release/abort the wrong page_t".  It is worse than
that: on the pre-fix kernel any /proc process-memory access is a HARD KERNEL PANIC.

Proven with a discriminating test (test-tools/proctest.c, K&R C, native AMIX cc).
It forks a child, then reads and writes the child's memory through /proc/<pid> in three
regions chosen to hit three different kernel paths:

  R1 priv   child fills it AFTER fork -> private, resident, writable
            => prfastmapin fast path, read AND write
            DISCRIMINATING: the parent's own copy of that page is ZEROS, so if the walk
            resolved the wrong address space T1 would read zeros, not the child's pattern
  R2 cow    parent fills it BEFORE fork, child never touches it -> COW, write-protected
            => read succeeds on the fast path (W set, writing==0);
               write must DECLINE on the W bit -> as_fault COW -> prmapin -> vtop user branch
  R3 absent never touched by either -> not resident
            => prfastmapin declines (PDT==0) -> as_fault faults it in; must read as zeros
  T7        deliberately PAGE-CROSSING unaligned window -> exercises prusrio's own page
            loop (0x64580/0x64586), the two sites whose half-conversion hung the kernel
            on 2026-07-03

Regions are 3 pages of .bss and the window is the page-ALIGNED middle page, so "absent"
really is a page nobody touched (an unaligned window would share a page with a filled
neighbour and make the zero check lie).

  pc 0x8063504 = kernel base 0x08000000 + text 0x63504, which is INSIDE stock
  prfastmapin (0x63484..0x63590), at the `btst #0,%a2@(3)` PTE dereference that
  follows the dead 030 SDE walk.  psw=0x2400 is exactly prfastmapin's own splhi
  (0x63492 `movew #0x2400,%sr`).  The guest did not recover.

So the pre-fix behaviour is: /proc silently returns the WRONG memory contents, and then
panics the kernel.  Root cause as predicted statically: hat_alloc (hat040.s:1211) stores
the 040 ROOT TABLE VA at as@(20), and stock prfastmapin reads that table as an array of
8-byte 030 SDEs (0x634ba `moveal %a0@(4,%d0:l:8),%a0`), producing a wild pointer.

This closes ISSUE-17 and the reachable half of ISSUE-18 (18a: vtop_orig's stock 2 KiB
per-process walker is now bypassed for user VAs).

--- ISSUE-18b hardening, measured ---------------------------------------------
vtop040's dispatch was deliberately made proc-LAST so that EVERY proc==0 path keeps its
previous behaviour byte-for-byte.  Reason found during design: mmmmap (0x2067e) calls
vtop(addr, 0) for /dev/mem, and on an Amiga that address legitimately reaches
0x80000000+ (Zorro III).  Classifying >=0x80000000 as "user VA" on address alone would
have broken /dev/mem for high physical space, because stock svirtophys returns any
non-SCN1 address unchanged (0xb7744).  Also verified from the binary: startio (0xc100)
DOES pass bp->b_proc, and dma_pageio (0x20c90) COPIES b_proc into its bounce buffer
(amiga_dma_pageio 0xdbee clears it instead) -- so a proc-FIRST dispatch would have
broken disk DMA.
The capped diagnostic for "kernel VA arrived with proc != 0" (Lvt_viol, cap 8) NEVER
FIRED in any run -- boot, login, churn, proctest, on either CPU.  The forced proc=0 is
therefore a pure no-op safety net today, and the stale-b_proc shape does not occur in
practice on this configuration.

ISSUE-15 -- KMA pool clicks + kmem_avail
================================================================================

Source contract: svr4-src-3b2/usr/src/uts/3b2/os/kma.c:67-70
  SMALLCLICKS = btoc(SMALLBYTES=4096)   030: 2   Model B: 1
  BIGCLICKS   = btoc(BIGBYTES=16384)    030: 8   Model B: 4
26 sites: kmem_allocspool(8) + kmem_allocbpool(9) + kmem_freepool(8) + kmem_avail(1).

Deliberately NOT changed (buffer/hash constants, not page sizes): SMALLBYTES 4096,
BIGBYTES 16384, MAXASMALL 256, MAXABIG 4096, bitmap sizes, HASH shift 14, and the
kmeminfo BYTE bookkeeping.  Verified from source that both bitmaps are exactly sized
(BIGBYTES/MAXBIG = 16384/16384 = 1 long = 4 bytes = the 4 bytes allocated inside the
72-byte kmem_alloc; SMALLBYTES/MAXSMALL = 16 longs = 64 bytes = the 64-byte bitmap), and
that with the halved counts each managed region ends EXACTLY at the end of its mapping
(small 1x4096, big 4x4096) -- so halving removes double-mapping without shrinking usable
KMA memory by a single byte.
kmem_alloc/kmem_free oversize paths were already converted (patch_modelb.py:606-610,
moveq #12 at 0x42002/0x420b6/0x4246a) and were not touched.  No address overlaps any
existing patch script.

kmem_avail (0x42d68) was NOT in Codex's KMA table (STREAMS-MBLK-LIFETIME-AUDIT.md lists
only allocspool/allocbpool/alloc/free/freepool).  It computes
ptob(availrmem - tune.t_minarmem) with <<11, i.e. it reported HALF the true available
bytes to STREAMS bufcall back-pressure.  Found by this session's own binary diff.
