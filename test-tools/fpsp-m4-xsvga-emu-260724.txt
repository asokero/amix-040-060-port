M4 -- FP ARITHMETIC EXCEPTION VECTORS 48-55
-------------------------------------------
src/fpsp_glue040.s gained the FPSP_VEC() macro and six dispatch entries
fpsp_vec48/51/52/53/54/55, each: cputype==40 gate (a 68060 boot of this dual-CPU
binary must never enter the 040 package) -> kernel supervisor CACR from sup_cacr
-> jmp <package entry> with the raw 68040 exception frame untouched on (sp):
    vec 48 -> fpsp_bsun     (branch/set on unordered)
    vec 51 -> fpsp_unfl     (underflow)
    vec 52 -> fpsp_operr    (operand error)
    vec 53 -> fpsp_ovfl     (overflow)
    vec 54 -> fpsp_snan     (signaling NaN)
    vec 55 -> fpsp_unsupp   (unimplemented DATA TYPE)
Vectors 49 (inexact) and 50 (divide-by-zero) are deliberately NOT retargeted:
the 68040 completes both in hardware and the Motorola package exports no entry,
so they stay on the stock nullvect -> u_trap -> SIGFPE path (asserted).
Installed by src/patch_fpsp_vectors.py (relocation-retarget in .rela.text,
offsets derived from the M68Kvec symbol; idempotent; fails closed).  Wired into
BOTH relink-040-fpsp.sh and relink-040-fpsp-xsvga.sh.  Reloc validation 0.

THE (MIS-CONTEXTUALISED) CRASH: single client disconnect under remote start
---------------------------------------------------------------------------
Xsvga :0 starts, prints "Xsvga Version 1.4", and is STABLE with no client
(alive >20 s, 0:02 CPU, load 0.00 -- it is NOT in a trap loop).  It speaks full
X11R5 (xdpyinfo: MIT R5, depth 8, SHAPE/MIT-SHM/Multi-Buffering; "number of
screens: 1") and serves a complete client transaction.  BUT:
  1. xdpyinfo reports  dimensions: 0x0 pixels  -- the server's root window is
     0x0 even though the driver is in 1152x900.  So the server<->driver geometry
     handshake at ScreenInit yields 0, while a later GetScreenData returns
     1152x900.  (Under Amiberry's Piccolo RTG the init-time geometry read
     returns 0.)
  2. The server dies the instant the client disconnects.  truss:
        poll/read/writev loop (serving xdpyinfo) ... all succeed
        read(...) Err#130                 <- ECONNABORTED, client closed
        close(...)                        <- server tears the client down
        Incurred fault #1, FLTILL %pc = 0x800C7030
        siginfo: SIGILL ILL_ILLOPC addr=0x800C7030
        *** process killed ***
     adb on /core: pc=0x800C7030 decodes as "or.b %a4,%d0" (illegal: An as OR
     source), a0=0x800C702C = pc-4, and 0x800C7010.. is NOT in the static .text
     -- the disconnect-cleanup path jumped through a corrupt/uninitialised
     function pointer into non-code.  Deterministic: identical
     uret=800912F8 kcaller=804858C (sigaddq) every run; the vec-48..55 retarget
     did NOT change it (so it is NOT the FP arithmetic gap).
WHY MY REMOTE TEST CRASHED (and normal use does not)
----------------------------------------------------
I started Xsvga REMOTELY over the emu.py telnet session and fed it ONE-SHOT
clients (xdpyinfo, xlogo) with NO window manager.  Each client connected and
disconnected immediately, and that lone-client teardown-without-a-WM is the path
that hit the bad pointer.  `xinit` (used by the manual test) starts the server +
twm + persistent xterms as one live session -- the clients stay connected, the
teardown path is not exercised that way, and the desktop runs fine.  So the
SIGILL is a real edge in the disconnect-cleanup path, but it is NOT on the
normal-use path and did NOT block the graphical goal.  (The xdpyinfo
"dimensions 0x0" was likewise harmless -- the root window is plainly 1152x900 in
the working desktop.)
