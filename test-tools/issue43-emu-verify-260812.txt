WHAT THIS RUN CAN AND CANNOT DECIDE
------------------------------------
It CANNOT decide ISSUE-43.  The emulator raises no enabled IEEE FP exceptions, so the six
classes fpenab060 exists to measure are UNEXERCISED there -- which looks exactly like failing.
Registered before the run, and confirmed by two independent readings below.

It CAN decide three things that hardware should not be spent on:
  1. does the new 060 code run at all, and on which paths;
  2. is the 040 path untouched;
  3. does anything regress in ordinary FP or in the boot/context-switch path.

Consistency: null+idle+excp = 10084 vs save_n 10080, and rest_live+rest_null = 9390 vs
rest_n 9386.  The four-count drift is the counters being read one kpeek at a time on a live
system, not a discrepancy.

THE NUMBER WORTH KEEPING: 9229 of 10080 saves -- 92 % -- are genuinely null frames.  This is the
honest remeasurement of the "7100 null saves per boot" figure that ROUND 3 collected through the
wrong byte-zero predicate and that KNOWN-ISSUES then retracted.  The conclusion it was used for
survives: on the 060 the null case is the common case, so "always save" would be a permanent
per-context-switch cost.  The 8 % idle-frame remainder is the traffic this fix preserves and
stock dropped whenever the operand exponent happened to be zero.

------------------------------
