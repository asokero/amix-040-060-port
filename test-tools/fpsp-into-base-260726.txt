FPSP PROMOTED INTO THE BASE LINK -- emulator verification, 2026-07-26
=====================================================================

WHAT CHANGED
------------
The Motorola 68040 FPSP stopped being a separate kernel variant and became part of
relink-040.sh, so every artifact built from the base carries it.

  relink-040.sh          + FPSP block (last step, after every byte patch)
                           FPSP=1 default; FPSP=0 builds the old no-FPSP kernel
  relink-040-fpsp.sh     RETIRED -> stub that exits 1 with a pointer
  relink-040-fpsp-xsvga.sh, relink-040-va2000.sh
                         FPSP layer REMOVED (they would have double-linked it);
                         their guard inverted -- they now REQUIRE FPSP in the base

Placement is deliberate: FPSP is ld -r'd in AFTER all byte patches.  `ld -r` puts the
base object's .text first, so every patch address survives -- but only in this order.

WHY (the argument, not just the tidiness)
-----------------------------------------
The 68040 implements a SUBSET of the FP instruction set in hardware and traps the rest.
Motorola ships FPSP because completing the ISA is the OS's job.  A 68040 kernel without
it is an incomplete 68040, not a kernel missing an optional extra.

Our own evidence that this mattered: with vector 55 (unimplemented DATA TYPE) left on
nullvect, the X server died of SIGILL --
    DBG SIG sig=4 pid=208 psargs=/usr/X/bin/Xsvga :0
-- and that was read as a graphics problem for a while.  The graphics-driver goal made an
FPU completeness gap look like a driver bug.

Second reason: the variant matrix.  FPSP+driver kernels were built by separate scripts with
their own default bases, which is exactly how the 2026-07-25 near-miss happened (graphics
kernels silently built from a 260724 base, containing none of that day's VM fixes).  FPSP in
base collapses two axes to one: base = VM + complete CPU; driver kernels = base + one driver.

NOT VERIFIED
------------
  * NO REAL HARDWARE.  Everything above is emulator only.
  * The loader/copyit path at the NEW image size was NOT stress-tested.  The base grew
    1.53 -> 1.72 MB, and the historical cold-boot corruption was a loader buffer OVERLAP
    at ~0.96 MB.  Three cold boots (2x 060, 1x 040) came up clean, which is a weak
    positive, not a proof.  On real HW: if the screen flashes white/red at handoff, that
    is the copyit checksum guard and it is THIS, not FPSP.
  * pgcold D/E, bmaptest, mlocktest, trunctest, disk truth, msync: NOT re-run on the FPSP
    kernels.  They passed on 260725-17/-18 and FPSP appends code without touching any
    patched address, but "should not matter" is not "was tested".
  * The graphics kernels (260725-19/-20) were NOT rebuilt.  They still carry their own
    FPSP layer from the old flow; rebuilding them on the new base is the next step and
    REALHW-VERIFY-260725.md's kernel table is stale until then.

1. LOADER / copyit AT THE NEW IMAGE SIZE -- risk was overstated, now quantified
------------------------------------------------------------------------------
I flagged this twice as an open risk on the strength of three clean cold boots, which is
weak evidence.  It is answerable exactly, because THE LOADER COMPUTES AND PRINTS THE
VERDICT ITSELF (unix_boot.c, the 2026-07-09 diagnostic), and the emulator's memory
geometry is IDENTICAL to the real Mercury machine (mem[0] 0x08000020..0x0a000000 = 32 MiB,
mem[1] 0x07000020..0x08000000 = 16 MiB).  So the margin transfers to real hardware.

Measured on the largest artifact, the RTG kernel 260726-03 (file 1 817 257 B):

    kernel: entry=08000000 tvaddr=08000000 tsize=000f04a0 dvaddr=080f04a0 dsize=0001a11c
    buffer: image=09e44550 copysrc=09e44584..09f4eb40 dest=08000000..0810a5bc
    no overlap (copy is safe)

  destination [0x08000000, 0x0810a5bc)  = 1 090 012 B at the BOTTOM of the 32 MiB region
  ELF buffer  [0x09e44550, 0x0a000000)  = 1 817 264 B at the TOP (MEMF_REVERSE working
                                          exactly as designed: top-of-region minus filesize)
  MARGIN between them = 30 646 164 B = 29.2 MiB

Overlap requires copy_size + file_size >= region_size, i.e. a kernel file of roughly
16 MiB on this configuration.  We are at 1.82 MiB: about 9x headroom.  Adding 68060SP
(~350 KB) would not move this meaningfully.

And there are THREE independent guards, all verified in source:
  * MEMF_REVERSE places the buffer at the top of the region (confirmed by the addresses)
  * copyit's direction choice is now correct in BOTH directions -- `cmpl a0,a1 / bcs
    copyfwd`: dest<src ascends, dest>=src descends from the tail (copyit.s:93-95)
  * a checksum over the DESTINATION is compared against the loader-computed source sum,
    and a mismatch flashes color0 white/red forever rather than jumping into a corrupt
    kernel (copyit.s:130-148)

Every boot in this session printed "no overlap (copy is safe)".  CONCLUSION: this is not a
live risk at the current or foreseeable image size.  The white/red-flash advice stays in the
run list as a diagnostic, but I was wrong to rank it as an open hazard.
