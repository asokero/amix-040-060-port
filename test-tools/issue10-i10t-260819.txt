WHAT THIS IS.  Every i10g/i10w capture of the store that lands 0x4AFC0000 at 0x80014AA0
forced that store to FAULT (write-protect), routing its completion through the 68040
deferred-write-back replay in src/wb040.s.  So the record could not separate world A
(the ordinary, non-faulting store already fabricates the value -- the 040 write-back
core) from world B (the value appears only because the write-protect forced the
deferred/replay path -- an artifact of the method).  i10t watches the same store on the
ORDINARY path: on the resolved tail of the demand-zero that first brings in the poison
page it sets T1 in the returning user frame, installs its own vector-9 handler (saving
the stock one to chain and restore), and single-steps that process with NO page
protected, latching the first transition of 0x80014AA0 into the poison.

RESULT: NULL, PLUS AN INSTRUMENT FINDING.  The staging was clean, the arm worked and the
stepping worked -- but the traced process died of SIGTRAP 159 steps in, at the first
syscall boundary after the arm, so the poison transition was never reached.  World A vs
world B is NOT measured by this run.

THE DEATH.  The armed `sh -n /cdrom/install/bin/setup.sh` died with

  Trace/Breakpoint Trap - core dumped
  WALL rc=133                          (128 + SIGTRAP)

and printed no `User BUS ERROR` line at all: the parse died far short of the 34 KiB /
38 KiB threshold at which the wall fires.  159 instructions is a handful of a parse that
needs millions.

THE READING (analysis, not measurement).  159 steps past the arm the process reached a
syscall boundary.  On m68k a TRAP instruction executed with T1 set processes the trap
exception and THEN a trace exception; that trace arrives from the syscall boundary and
is handled on the stock path (kernel syscall handling / stock vector-9 semantics), which
posts SIGTRAP to the process -- sh has no handler for it, so it cores.  The counters are
consistent with that: i10t_step_n stopped at 159 while i10t_on was still 1 and i10t_proc
unchanged, so the final trace never reached i10t_trace at all -- had it done so for this
process it would have incremented the counter.  i10t's handler covers straight-line USER
stepping only.  Single-stepping ACROSS syscalls needs kernel-side work PART FIVE does not
have: clear T in the trap-entry frame, and re-arm it at syscall exit for the armed
process alone.  That is the instrument's gap, and it is why this run is a null result
rather than a verdict.

CONTROL, SAME BOOT.  Immediately afterwards, with the instruments disarmed by kpoke
(i10t_want 1 -> 0 at 0710CD80, i10g_on 1 -> 0 at 0710CB70; the write-protect band was
already 0 for this run), the same command was run again on the same booted kernel:

  NOTICE: User BUS ERROR at 4AFC0003, PC:800023FC FAULT:6 PID:43 CMD:sh -n /cdrom/install/bin/setup.sh
  ... (the full flood) ...
  /cdrom/install/bin/setup.sh: no space

So under this exact kernel, on this exact boot, the corruption fires on the FULLY
ordinary path -- no write-protect, no trace bit, no instrument armed.  The null result is
the instrument's gap; the bug did not go anywhere.

WHAT THIS DOES NOT SAY.  It does not favour world A or world B.  Nothing was latched, so
there is no measured before/after, no culprit PC, and no source-register evidence for the
ordinary store.  The genesis verdict (docs/ISSUE10-SETUPSH-WALL-260819.md section 11)
stands exactly as it stood, with confound #1 still open.

NEXT.  The guest-side portable instrument is PARKED -- closing its gap means kernel
syscall-path surgery, a large change to make for one measurement.  The next confound-#1
probe moves EMULATOR-SIDE: an env-gated value watch in the bench Amiberry's 68040 MMU
data path that logs every data read returning 0x4AFC0000 and every data write landing it,
with PC, SR and the register file, and perturbs the guest not at all.  It also has a shot
at the bench half of confound #2: 0x4AFC is the UAE core's own ILLEGAL marker constant,
and both emulators that reproduce this wall are UAE-derived, so a common-mode emulator
defect is a live hypothesis such a watch can name.  For the port-level claim, 68040
SILICON remains the sole decider.
