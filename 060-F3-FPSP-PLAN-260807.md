# F3 — a floating-point support package for the 68060: plan

**Written 2026-08-07.** Goal: make the 68060 execute the FP instructions it does not retire in
hardware, instead of killing the process with SIGSYS. Closes ISSUE-34b's FP half.

Baseline: `68060-260806-06`, hardware-accepted 2026-08-07 (`REALHW-260806-06-ACCEPTANCE.md`).

## 1. The measured basis

From `060-FPU-STATE-260807.md`, measured on real silicon one instruction per child:

```text
fadd fsqrt fintrz          survive      retired in hardware
fsin fetox flogn fmovecr   SIGSYS (12)  nothing handles them
```

Two facts set the scope:

* **`fmovecr` is the common case, not an exotic one.** It loads the FPU ROM constants (0.0, 1.0,
  π), gcc emits it for ordinary FP literals, and the campaign plan's userland scan counted **287
  occurrences** of it in installed binaries (`FScc`: 26). `x = 1.0;` is enough to die.
* **Transcendentals are also live.** `fsin`/`fetox`/`flogn` all trap, so a package that only fixes
  constant loading leaves libm-using programs dead.

Cause is not in doubt: `prototypes/fpsp_glue040.s` gates every entry on `cmpl #40,cputype`, so on
an 060 the 68040 FPSP falls through to `nullvect` → SIGSYS.

## 2. What we already have

**Motorola's M68060 Software Package is on disk**, in the same NetBSD tarball the 040 FPSP came
from: `amix-playground/netbsd/syssrc.tgz`, path `usr/src/sys/arch/m68k/060sp/`. Contents that
matter:

| file | what it is | size |
|---|---|---|
| `dist/fpsp.sa` | full FP package: unimplemented instructions **and** data types **and** IEEE exceptions | **53 KiB** |
| `dist/pfpsp.sa` | partial: reduced module set, no transcendental emulation | 27 KiB |
| `dist/isp.sa` | integer package (F2 territory; we shipped a bespoke subset instead) | 6 KiB |
| `dist/fskeletn.s` | Motorola's example call-out section — the template for our glue | — |
| `dist/ftest.s` | **Motorola's own FP test suite** | — |
| `fnetbsd.S`, `netbsd060sp.S` | NetBSD's OS adaptation — a worked example, not our answer | — |
| `asm2gas`, `copyright.S` | the converter the 040 build already uses; licence notice that MUST be retained | — |

Kernel text today is `0xe4bb8` = 915 KiB, so the full package is **+5.8 %**.

And we have the precedent: `build-fpsp040.sh` + `prototypes/fpsp_glue040.s` already solve this exact
problem for the 040, including the 12 OS callbacks and the `ld -r` packaging into a SysV kernel.

## 3. The one real architectural difference

**The 040 FPSP is symbol-based; the 060SP is address-based.** This is the main technical risk and
it changes packaging, not maths.

The 060SP is a binary image with three sections:

```text
   [ Call-Out section  ] 128 bytes, 32 x 4-byte fields, WE fill these in
   [ Entry-Point section] 8 bytes per entry, fixed offsets from the top
   [ Code section       ]
```

Callers do not link against symbols — they jump to a fixed offset:

```text
	bra	_060FPSP_TOP + 128 + 0x30	| F-line handler (vector 11)
```

Entry points (offsets from the start of the entry-point section):

| offset | entry | vector |
|---|---|---|
| 0x30 | `_060_fpsp_fline` | **11** — unimplemented FP instruction ← *what our measurement needs* |
| 0x38 | `_060_fpsp_unsupp` | 55 — unimplemented data type |
| 0x40 | `_060_fpsp_effadd` | 60 — unimplemented effective address |
| 0x00…0x28 | `snan, operr, ovfl, unfl, dz, inex` | 48–54 — IEEE exceptions |

Call-outs we must provide (32 slots, addresses **relative to the call-out section start**):
`_060_real_{bsun,snan,operr,ovfl,unfl,dz,inex,fline,fpu_disabled,trap,trace,access}`,
`_060_fpsp_done`, and the memory family `_060_{imem_read,dmem_read,dmem_write,imem_read_word,
imem_read_long,dmem_read_{byte,word,long},dmem_write_{byte,word,long}}`.

On AMIX these map onto machinery that already exists and is hardware-proven: the `real_*` slots go
to the stock `nullvect`/`u_trap` signal paths, `_060_fpsp_done` to `ureturn`, and the memory family
to `copyin`/`copyout`. `fpsp_glue040.s` already implements the equivalent twelve.

## 4. Vector map and gating

Current state (campaign plan §6): ISP owns 61; FPSP owns 11, 48–55, 60; our 040 hooks sit on 11,
48 and 51–55; 49, 50, 60, 61 are still `nullvect`.

F3 adds an 060 branch to the *existing* shims rather than a second vector table:

```text
fpsp_vec11:   cputype == 40 -> 040 FPSP        (unchanged, byte-identical)
              cputype == 60 -> _060_fpsp_fline (new)
              otherwise     -> nullvect        (unchanged)
```

Campaign rule 1 is binding: the 040 path must stay byte-identical, and both emulator CPU configs
must boot before any hardware boot.

## 5. Milestones

### M0 — the instrument, first

A `nullvect` probe: record the vector number, faulting PC and a count, in `.data`, before anything
else changes. Rationale, and it is not bureaucratic:

* We still **cannot attribute** any program's SIGSYS. `wolf3d`'s "bad system call" and the `xv` /
  X11R5 crashes are *consistent* with F3 and unproven, because SIGSYS also has a legitimate
  producer (a genuinely absent syscall). The probe settles those three symptoms directly.
* It is how every later milestone is judged: "the SIGSYS stopped" is only evidence if we know which
  vector was producing it.
* KNOWN-ISSUES already specifies this probe. It is small and CPU-independent.

*Acceptance:* on the 060, `fp060probe` moves the counter by exactly 4 and reports vector 11 for
`fsin/fetox/flogn/fmovecr`; running `wolf3d` and `xv` names their vector.

### M1 — build the package body

`build-fpsp060.sh`, modelled on `build-fpsp040.sh`: convert with the same NetBSD `asm2gas`,
assemble with the GNU m68k toolchain, `ld -r` to one object, keep `copyright.S` linked in (licence
condition), and lay out `[128-byte call-out table][package image]` contiguously.

*Acceptance:* object builds; `m68k-cbm-sysv4-ld -r` accepts it; **the entry-point offsets are
verified by disassembling the entry table**, not assumed; measured text growth reported.

**Also decided here, by measurement rather than argument:** build `pfpsp.sa` as well and run
`fp060probe` against both. The probe already distinguishes them — whichever variant makes
`fmovecr` *and* `fsin/fetox/flogn` survive is the one we ship. Expectation: the full `fpsp.sa`,
since `pfpsp` drops the transcendental modules.

### M2 — glue and the vector-11 hook

`prototypes/fpsp_glue060.s`: the 32 call-out slots plus the `cputype == 60` branch in `fpsp_vec11`.
Counters in the F2 style: entry count, per-entry-point counts, and a **counted, state-preserving
fallback** to `nullvect` for anything the package declines — never a partial decode, never a silent
approximation.

*Acceptance, pre-registered:*
* `fp060probe`: all seven survive, and `fmovecr` returns the correct constant (the probe must be
  extended to check the *value*, not just survival — survival is not correctness, the lesson from
  `protfault`);
* `fputest060 fork` (Test C) **runs to completion** — it currently dies before its first `printf`,
  so FP context switching under load becomes measurable for the first time on this CPU;
* Motorola's `dist/ftest.s` assembled and run;
* battery 11/11, burst 96/96, `hat_pfnmiss_n` +2, on both emulator CPUs and then hardware;
* the 040 path byte-identical: emu-040 battery unchanged and every 060 counter still 0.

### M3 — data types and effective addresses (vectors 55, 60)

Hook `_060_fpsp_unsupp` and `_060_fpsp_effadd`. Denormals and packed decimal live here. Deferred
deliberately: nothing measured yet needs them, and M2's acceptance will show whether they do.

### M4 — IEEE exceptions (vectors 48–54)

Only if something needs them. The 040 side already hooks 48 and 51–55; matching that on the 060 is
mechanical once M2's call-out table exists.

### M5 — hardware acceptance

Full run list, as for `-06`: identity, `fp060probe`, `ftest`, battery, burst, and the power-cut
disk truth. Recorded as `REALHW-<id>-ACCEPTANCE.md`.

## 6. Decisions, with recommendations

**D1 — Motorola's package, or a bespoke emulator like F2?** → **Motorola's.**
F2 wrote its own vector-61 handler, and that was right *there*: the arithmetic already existed and
was validated (`lmul060.s`, 202 500 cases), and exactly one instruction form covered the whole
installed compiler. Neither holds here. The maths is transcendental-function emulation, which is
the part not to hand-roll, and Motorola ships a test suite for it. Keep bespoke as the fallback if
M1 shows the package cannot be linked or does not fit.

**D2 — full `fpsp.sa` (53 KiB) or `pfpsp.sa` (27 KiB)?** → decide in M1 **by running `fp060probe`
against both**, not by reading module lists. Expectation is the full package, because the measured
failures include transcendentals.

**D3 — where do the `real_*` call-outs land?** → the existing stock signal paths, exactly as
`fpsp_glue040.s` does. No new signal policy in this unit.

## 7. Risks

1. **Address-based interface.** A wrong offset jumps into the middle of the package. Mitigation:
   M1 verifies every entry offset by disassembly, and M2's counters must show each entry point
   being reached before any behavioural claim.
2. **Size.** +5.8 % kernel text. Mitigation: measured in M1; `pfpsp` is the fallback if it matters,
   at the cost of transcendentals.
3. **No 68040 in the machine.** Any regression of the 040 path can only be checked in the emulator.
   Mitigation: the 040 path is not touched — the gate is additive — and this is asserted by
   counters, not by inspection.
4. **`ftest.s` may need the same treatment as `fputest`**: it is Motorola assembly for their
   syntax, and the guest's own compilers are the thing under test. Cross-assemble it.

## 8. Not in scope

* ISSUE-42 (`wb040_replay` fault propagation) — separate, and 040-only.
* The 060SP **integer** package: F2's bespoke unit covers the measured userland. Replacing it with
  `isp.sa` is a later cleanup, not this unit.
* `FScc` (26 occurrences): note it, measure it in M0/M1, act only if it traps.
